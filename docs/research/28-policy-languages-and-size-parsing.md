### Cedar — parse and validation are two separate stages, and parse errors are a non-empty LIST

`cedar-policy-core/src/parser/err.rs` (Apache-2.0, read at source). The top-level parse error is an enum with exactly two arms:

```rust
pub enum ParseError {
    ToCST(#[from] ToCSTError),   // text → concrete syntax tree failed
    ToAST(#[from] ToASTError),   // CST → AST failed (structurally parseable, semantically invalid)
}
```

and errors are collected into `pub struct ParseErrors(NonEmpty<ParseError>)` — **the "at least one error" invariant is carried by the type**, via `NonEmpty`, so an empty error list is unrepresentable. Construction is `singleton` / `new(first, rest)` / `new_from_nonempty` / `from_iter` (all `pub(crate)`), plus `flatten` (returns `Option`, `None` for an empty input vector) and `transpose` (collect all `Ok`s or all the errors). `ParseErrors` implements `Deref<Target = NonEmpty<ParseError>>` and forwards `Display`/`Error`/`Diagnostic` to `.first()` — with the source comment `// intentionally showing only the first error; see #326`, i.e. the list is programmatically complete while the human string stays short.

Why the CST/AST split matters here: Cedar distinguishes "I could not structure this text at all" from "I structured it and the structure is illegal". Help text is attached per-variant with `#[diagnostic(help("..."))]` — e.g. `InvalidSingleEq` carries `"try using '==' instead"`, `InvalidEffect` / `"effect must be either `permit` or `forbid`"`, `ArbitraryVariable` / `"did you mean to enclose … in quotes"`, `FunctionCallOnMethod` / `"use a method-style call"`, `MethodCallOnFunction` / `"use a function-style call"`.

Evaluation/validation is a **second stage over an already-parsed artifact**: `Validator::new(schema)` then `Validator::validate(&self, pset: &PolicySet, mode: ValidationMode) -> ValidationResult`, where `ValidationMode` is `{ #[default] Strict, Permissive }`. `ValidationResult` carries **both** `validation_errors()` and `validation_warnings()` as iterators (and implements `Diagnostic`), with the doc "If a policy id included in the input policy set does not appear in the output iterator, then that policy passed the validator."

Map: our `compile()` is the parser+validator fused into one pass, and `PolicyError` is a single variant where Cedar has a two-arm `ParseError` plus a warnings channel.

### OPA / Rego — one parser for N grammars, gated by version, with errors sorted by source location

`v1/ast/parser.go` (Go, Apache-2.0 header verified). `func (p *Parser) Parse() ([]Statement, []*Comment, Errors)` is the single entry point; the dialect is selected by *options*, not by forking the parser:

- `p.po.Capabilities == nil` → `CapabilitiesForThisVersion(CapabilitiesRegoVersion(p.po.RegoVersion))`.
- `EffectiveRegoVersion() == RegoV1 && !Capabilities.ContainsFeature(FeatureRegoV1)` → `Errors{&Error{Code: ParseErr, Message: "illegal capabilities: rego_v1 feature required for parsing v1 Rego"}}`.
- New syntax is opt-in per module via `WithFutureKeywords(kws ...string)` / `WithAllFutureKeywords(yes bool)` / `WithCapabilities` / `WithSkipRules` / `WithProcessAnnotation`, and in-source via `import future.keywords.<kw>`. `futureImport` validates the path shape (`len(path)==1 || !path[1].Equal(InternedTerm("keywords"))` → `"invalid import, must be `future.keywords`"`; aliased `future` imports rejected; unknown keyword → `"unexpected keyword, must be one of %v"` with `util.Sorted(kwds)`).
- `ast/policy.go` pins the version table: `var Keywords = KeywordsForRegoVersion(DefaultRegoVersion)`, `KeywordsV0`, `KeywordsV1`, `KeywordsForRegoVersion(v RegoVersion)`, `IsInKeywords`. `ast/parser.go` (the thin facade) sets `const DefaultRegoVersion = RegoV0` and documents `RegoV0CompatV1` as "requires modules to comply with both the RegoV0 and RegoV1 syntax".

Error shape (`v1/ast/errors.go`): `type Errors []*Error` — a **go slice**, orderable — with

```go
type Error struct {
    Code     string       `json:"code"`
    Message  string       `json:"message"`
    Location *Location    `json:"location,omitempty"`
    Details  ErrorDetails `json:"details,omitempty"`
}
```

`(e *Error) Error()` renders `file:row: code: message` plus indented `Details.Lines()`. `Errors.Sort()` is `slices.SortFunc` on `a.Location.Compare(b.Location)` then `strings.Compare(a.Error(), b.Error())` — **deterministic ordering for diagnostics**, which matters the moment more than one rule can fire on one sentence. Codes are a closed vocabulary: `ParseErr = "rego_parse_error"`, `CompileErr`, `TypeErr`, `UnsafeVarErr`, `RecursionErr`, `FormatErr`. Corrective hints live at the raise site, not in a lookup table: `p.hint(...)` appears with concrete text at line 690 (`"if this is unexpected, try updating OPA"`), 732/739 (`"import a different path or use an alias"`), 1446 (`"`import future.keywords.every` for `every x in xs { ... }` expressions"`), 1609 (`"`import future.keywords.%s` for `%s` expressions"`), 1688 (`"`import future.keywords.in` for `some x in xs` expressions"`), and in `v1/ast/compile.go:7551` (`"var %[1]v is unsafe%[2]v (hint: `import future.keywords.%[1]v` to import a future keyword)"`).

Public parse/eval entry points: `ParseModule(filename, input string) (*Module, error)` → `ParseModuleWithOpts(filename, input, ParserOptions{})` → `ParseStatementsWithOpts(...)`, and `ParseBody(input)` / `ParseBodyWithOpts(input, ParserOptions{SkipRules: true})`. Empty input returns `nil, nil` by contract. Compilation is a separate call (`NewCompiler() *Compiler`) over the parsed AST.

Map: our three ordered rules (`RULE_TARGET_BYTES` → `RULE_DENY_UNDER_MTA` → `RULE_DENY_GLOBS`) already behave like an implicit version table, but nothing in `compile()` is a *keyed* set of enabled features, and `unmatched` carries no ordering guarantee beyond clause order.

### casbin — the anti-pattern: model parsing has no grammar, one opaque error string

`src/config.rs` (Apache-2.0 per in-tree `Cargo.toml license = "Apache-2.0"`; crates.io record says 2.20.0 while the tree's own version field reads 2.18.1). `Config::parse_buffer` is a line-scanner: skip empty lines and lines starting with `DEFAULT_COMMENT`/`DEFAULT_COMMENT_SEM`; `line.starts_with('[') && line.ends_with(']')` opens a section (`section = line[1..line.len()-1]`); `DEFAULT_MULTI_LINE_SEPARATOR` (`\`) joins continuations with `next_section` tracking. Then:

```rust
let mut kv = line.splitn(2, '=');
// ... if the split does not yield exactly 2 parts:
return Err(std::io::Error::other(format!("parse content error, line={}", line)).into());
```

That is the **entire** error taxonomy for `.conf`/`.csv` model files: one `io::Error`, carrying the offending line but **no line number, no column, no expected-token, no error class**. This is exactly the shape our note argues against, and it is useful precisely because it is from a widely deployed project — the cost of a weak grammar is paid in support burden, not in correctness.

casbin's *policy* side is typed, which is the contrast: `src/error.rs` defines `ModelError { R("Invalid request definition"), P("Invalid policy definition"), E("Unsupported effect"), M("Invalid matcher"), Other }` — **letter-coded variants that name which of the four model sections failed** — plus `RequestError::UnmatchRequestDefinition(usize, usize)` and `PolicyError::UnmatchPolicyDefinition(usize, usize)`, which carry **the arity of the actual vs. expected token list**. A `std::sync::Arc`-free `Assertion { key, value, tokens, policy, rm }` holds each parsed clause as a token vector. So casbin does have a parsed-artifact layer — it just never built a grammar *for the text that builds it*.

### rhai — compile and eval are distinct entry points with distinct error types

`src/api/compile.rs`: `Engine::compile(&self, script: impl AsRef<str>) -> ParseResult<AST>` (also `compile_with_scope`, `compile_expression`, `compile_into_self_contained`, `compile_scripts_with_scope`). `src/parser.rs:33`: `pub type ParseResult<T> = Result<T, ParseError>;` — **a dedicated alias for the parse failure axis.** Eval is a different axis: `Engine::eval_ast::<T>(&self, ast: &AST) -> RhaiResultOf<T>` and `Engine::eval::<T>(script) -> RhaiResultOf<T>` (the latter being literally compile-then-eval in one call).

The two axes never collapse: `src/types/error.rs:27` `pub enum EvalAltResult` has `ErrorParsing(ParseErrorType, Position)` at line 36 (Display at 139 = `"Syntax error: {p}"`), and `src/types/parse_error.rs` defines `LexError` (with `MalformedNumber`, `MalformedEscapeSequence`, `UnterminatedString`, `StringTooLong(usize)`, `ImproperSymbol(String, String)`, … and a `/// Convert a LexError into a ParseError` `#[cold]` method) and `ParseErrorType` (`BadInput(LexError)`, `MissingToken(String, String)`, `UnexpectedEOF`, `UnknownOperator(String)`, `MalformedCallExpr`, `AssignmentToConstant`, …). **A lexer failure is wrapped into a parse failure as `BadInput(LexError)` — a three-level containment chain (chars → tokens → nodes), each level with its own error enum.**

casbin (which embeds rhai for its matchers) then keeps the two axes visible in its own public error:

```rust
pub enum Error {
    ...
    RhaiError(#[from] Box<EvalAltResult>),   // eval failed
    RhaiParseError(#[from] ParseError),      // parse failed
}
```

**Parse failure and eval failure are distinct top-level variants of the embedding crate's error type.** That is the single most directly transferable finding in this section: our `PolicyError` currently has no eval-side counterpart at all, and no way to say "this clause parsed but could not be applied".

### koto — a three-tier error taxonomy with an explicitly RECOVERABLE middle tier

`crates/koto/src/lib.rs` (MIT per crates.io record) shows the intended call shape:

```rust
match koto.compile("1 + 2") {
    Ok(chunk) => match koto.run(chunk) {
        Ok(result) => match result { KValue::Number(n) => …, other => panic!(…) },
        Err(runtime_error) => …,
    },
    Err(compiler_error) => …,
}
```

`compile` and `run` are distinct methods with distinct error arms; the crates are split (`koto_bytecode`, `koto_parser`, `koto_runtime`, `koto_lexer`) so parse and execution are separate compilation units.

`crates/parser/src/error.rs` is the interesting part — **three enums by who is at fault and whether the caller can continue**:

1. `InternalError` — doc: "An error that represents a problem with the Parser's internal logic, rather than a user error" (`AstCapacityOverflow`, `ConstantPoolCapacityOverflow`, `NumberParseFailure`, `ChainParseFailure`, `UnexpectedToken`, …). A parser bug is a *different type* from bad user input.
2. `ExpectedIndentation` — doc: "**Having these errors separated out from [`SyntaxError`] is useful when working with interactive input, where an indented continuation can be started in response to an indentation error.**" Variants name the construct the user was mid-way through: `FunctionBody`, `MatchArm`, `ThenKeywordOrBlock`, `ElseIfBlock`, `CatchBody`, `ForBody`, `WhileBody`, `LoopBody`, `FinallyBody`, `SwitchArm`, `RhsExpression`, …
3. `SyntaxError` — a long flat `Expected*` enum (`ExpectedCloseParen`, `ExpectedExpression`, `ExpectedIfCondition`, `ExpectedMapColon`, `ExpectedCommaBetweenCallArgs`, …). All are `#[error("…")]`-attributed via thiserror.

**This is the precedent for our `CompiledPolicy::unmatched` being a first-class recoverable output rather than a debug field.** koto does not model "the user typed something I could not finish" as an error at all when the caller might continue; it gives it its own type whose variants name the enclosing construct. Our `unmatched: Vec<String>` names no construct and has no severity.

### pomsky — return the result AND the diagnostics in one call

`docs.rs/pomsky` (0.12.0, MIT OR Apache-2.0 per crates.io record; repo file `pomsky-lib/src/error.rs` **404s** — see Risks). The headline API is:

```rust
Expr::parse_and_compile(input, options) -> (Option<String>, Vec<Diagnostic>, Vec<Test>)
```

i.e. **parse and compile in one call, returning the compile output, a diagnostic list, and generated tests — not `Result<_, E>`.** A `None` result with a non-empty diagnostic list is representable, so "I produced nothing and here is why" does not need an error type to carry soft information.

The diagnostic types are first-class: module `diagnose` is described as "Crate containing diagnostics, i.e. errors and warnings"; `pomsky::diagnose::Diagnostic` is "A struct containing detailed information about an error, which can be displayed beautifully with miette"; `Severity` is an enum `{ Error, Warning }`; and `pomsky::ParseError` is a plain struct — `pub struct ParseError { pub kind: ParseErrorKind, pub span: Span }` — where `Span` is documented as "A source code location, marked by the start and end byte offset. If both are zero, this is considered as 'empty' or 'missing'". `CompileOptions { flavor: RegexFlavor::Java, ..Default::default() }` makes the dialect an explicit input.

Map: our `compile()` returns `Result<CompiledPolicy, PolicyError>` and smuggles soft failures into `CompiledPolicy::unmatched`. pomsky's shape says the honest signature is result + diagnostics, with severity as a property of the diagnostic rather than of the return type.

### starlark — features are boolean flags on ONE grammar, never a forked parser

`starlark_syntax/src/dialect.rs` (Apache-2.0 in-tree header). This is the strongest available evidence for the "extensible without forking" claim, now verified at source:

```rust
pub enum DialectTypes { Disable, ParseOnly, Enable }   // prohibit / allow-but-ignore / check at runtime

pub struct Dialect {
    pub enable_def: bool,                      // enabled by default
    pub enable_lambda: bool,                   // enabled by default
    pub enable_load: bool,                     // enabled by default
    pub enable_keyword_only_arguments: bool,   // disabled by default
    pub enable_positional_only_arguments: bool,// disabled by default
    pub enable_types: DialectTypes,            // disabled by default
    pub enable_load_reexport: bool,            // enabled by default "But they plan to change it"
    pub enable_top_level_stmt: bool,           // disabled by default
    pub enable_f_strings: bool,                // disabled by default
    pub _non_exhaustive: (),
}
```

Two details carry the design lesson. First, `_non_exhaustive: ()` with the comment "Like `#[non_exhaustive]`, but allows struct expression" (linking clippy#6559): the struct is **forward-extensible by construction** — a new switch can be added without breaking any caller that constructs a `Dialect` literal, which is exactly the thing `#[non_exhaustive]` forbids. Second, the constants: `Standard` (def/lambda/load/load_reexport on, keyword_only off, types `Disable`, top_level_stmt off, f_strings off), and `Extended` marked `#[doc(hidden)]` with the doc "**This option is deprecated. Extend `Standard` instead.**" — the project explicitly converged from "two named dialects" to "one base + flags". They are declared under `#[allow(non_upper_case_globals)]` with the source comment "These are morally enumerations, so give them enumeration-like names even though they are actually global constants".

The parse entry point takes the dialect as an argument: `AstModule::parse(filename: &str, content: String, dialect: &Dialect) -> crate::Result<Self>` and `AstModule::parse_file(path: &Path, dialect: &Dialect)`. Errors are `Error(WithDiagnostic<ErrorKind>)` with `pub enum ErrorKind { Fail, StackOverflow, Value, Function, Scope, Parser, Freeze, Internal, Native, Other }` (`anyhow::Error` payloads) — note `Parser` and `Internal` are **separate variants**, and `Error` is size-asserted (`const _: () = assert!(mem::size_of::<Error>() == mem::size_of::<usize>());`) with `Error::new_spanned(kind, span, codemap)` and `Error::span() -> Option<&FileSpan>`.

Map: `Dialect` is the shape our ordered rule chain wants to grow into — a keyed set of enable switches passed *into* the parser, where a disabled feature simply does not match. `Extended`'s deprecation notice is the cautionary half: named variants ossify; flags extend.

### sqlparser — the dialect trait: two required methods, ~60 defaulted feature switches

`src/dialect/mod.rs` (Apache-2.0, ASF header read in `src/lib.rs`). `pub trait Dialect: Debug + Any` has exactly **two required methods** — `fn is_identifier_start(&self, ch: char) -> bool;` (line 258) and `fn is_identifier_part(&self, ch: char) -> bool;` (line 261) — and roughly **sixty defaulted `supports_*() -> bool` predicates** carrying the entire dialect surface: `supports_filter_during_aggregation` (328), `supports_window_clause_named_window_reference` (340), `supports_partition_by_after_order_by` (357), `supports_group_by_expr` (382), `supports_in_empty_list` (446), `supports_in_unparenthesized_expr` (452), `supports_named_fn_args_with_{eq,colon,assignment,rarrow}_operator` (467–490), `supports_numeric_prefix` (496), `supports_numeric_literal_underscores` (501), `supports_lambda_functions` (538), `supports_triple_quoted_string` (591), and so on for sixteen concrete dialects (`AnsiDialect` … `TeradataDialect`).

**This is the whole argument for feature switches over separate grammars: a dialect that does not support a construct does not reject it with a bespoke error — it simply takes the default path, so existing input never re-parses differently.** The only mandatory surface is character classification.

The parse result type is deliberately narrow:

```rust
pub enum ParserError {           // src/parser/mod.rs:56 — exactly three variants
    TokenizerError(String),
    ParserError(String),
    RecursionLimitExceeded,
}
```

**Lexical failure and syntactic failure are distinct variants at the top of the error enum** — the same split Cedar makes with `ToCST`/`ToAST` and rhai makes with `LexError`→`ParseErrorType::BadInput`. Position reporting is localized: `Parser::expected(&self, expected: &str, found: TokenWithSpan)` (line 4719) formats `"Expected: {expected}, found: {found}"` using `found.span.start`; `expected_ref` (4727) and `expected_at` (4735) fall back through `self.tokens.get(index).unwrap_or(&EOF_TOKEN)`, so a missing token is reported against a synthetic EOF rather than an unwrap. `parse_statements()` (517) tracks `expecting_statement_delimiter`: it consumes `Token::SemiColon`, and when `self.options.require_semicolon_stmt_delimiter` is false it clears the flag; the loop breaks on `Token::EOF` or on a `Word` that is `Keyword::END`; otherwise `self.expected_ref("end of statement", self.peek_token_ref())`. There is also a dedicated recursion budget — `mod recursion` (79): `RecursionCounter { remaining_depth: Rc<Cell<usize>> }`, documented as "Explicitly requires only `alloc` and `core`, so recursion is limited even when the 'std' feature is disabled", with a `recursive-protection` feature and `DepthGuard`. The public entry points are `parse_sql(dialect: &dyn Dialect, sql: &str) -> Result<Vec<Statement>, ParserError>` (567) and `parse_sql_with_comments` (575) which additionally returns `comments::Comments`.

Round-tripping is documented as lossy in a stated way: `src/lib.rs` says AST→text drops comments and normalizes whitespace and identifier capitalization, `{:#}` pretty-prints, and "Starting with version `0.53.0` sqlparser introduced source spans to the AST" (issue #1548) — **span support was retrofitted, and its absence was tracked as a known gap, which is our situation exactly** (`CompiledPolicy::unmatched` holds a `String` with no offset).

### Hazel — size is a number plus a GUI enum; there is no typed grammar to be sensitive about

Vendor manual (proprietary; design reference only), read 2026-09-13. This **closes the open question** left by the previous pass ("Hazel matching case/unit-sensitivity"): the answer is that the question does not apply.

`/manual/hazel/attributes-actions/attribute-reference/` lists a `Size` attribute: "The size of the file. Because of the way macOS calculates sizes, this figure (the actual size) may be less than the amount of space the file occupies on disk." Note what this sentence does: Hazel's own documentation tells the user that its size predicate is the **logical** size, not the allocation — the same distinction our `Candidate.alloc_bytes` makes on the other side. `/manual/hazel/hazel-basics/about-folders-rules/` gives the only example of the condition's concrete syntax ("Size is greater than 100 MB"), and it is prose describing GUI state, not a parseable literal.

The Trash-auto-deletion page (`/manual/hazel/hazel-basics/manage-your-trash/use-automatic-deletion/`) is the most complete size *policy* statement in the manual:

- **Age policy**: a "Delete files sitting in the Trash for more than" checkbox + a number + a period pop-up ("Hours," "Days," "Weeks," "Months," or "Years").
- **Size policy**: a "Keep Trash size under" checkbox + a number + a unit pop-up ("MB," "GB," or **"% of disk capacity"**).
- **Ordering**: "delete files as necessary (in the order in which they were moved to the Trash) to keep that total under whatever limit you set" — a FIFO eviction, i.e. the *selection* order is a property of the policy, not of the sizing rule.
- **Oversized-file carve-out**: "any file dragged to the Trash that, all by itself, exceeds your specified size limit … The file will be left in the Trash and Hazel will ignore it when calculating the total Trash size (otherwise, the Trash would always be over the limit)." A single item larger than the whole budget is **excluded from the accounting rather than allowed to veto the policy** — a real edge case our target-seeking loop will hit (one 40 GB `node_modules` when the user asked for 25 GB).

So: **there is no unit token, no case question, no token-boundary question, and no parse error in Hazel's model.** The three unit choices are a closed GUI enum, and the third one is not a byte count at all. Cite it as the "no grammar" pole, next to systemd's "grammar with an explicit base" pole.

**Size-and-unit grammar — the primary sources.** This half of the lane has no predecessor coverage at all (see the NEW-vs-predecessors list above). Each implementation below is read for the same three questions: what is an *input* to the parse, what are its *error classes*, and where does the *unit token* end.

### systemd `parse_size` — the base is a required input, and the code says why

`src/basic/parse-util.c` (LGPL-2.1-or-later; design reference; read at source 2026-09-13). Signature:

```c
int parse_size(const char *t, uint64_t base, uint64_t *size)
```

with, verbatim in the body:

> Soo, sometimes we want to parse IEC binary suffixes, and sometimes SI decimal suffixes. This function can parse both. Which one is the right way depends on the context. … In either case we use just K, M, G as suffix, and not Ki, Mi, Gi or so (as IEC would suggest). **That's because that's frickin' ugly. But this means you really need to make sure to document which base you are parsing.**

and `assert(IN_SET(base, 1000, 1024))` (line 206). Two static tables `iec[]` (1024^n) and `si[]` (1000^n) each end with `{ "B", 1ULL }` and `{ "", 1ULL }` — **the empty suffix is a legal unit meaning "bytes"**, which our `UNITS` cannot express (our `parse_size` returns `Ok(None)` when `token_len == 0`).

Behavioural details worth copying: `p += strspn(p, WHITESPACE)` before every segment (so `"1 G"` parses); `l = strtoull(p, &e, 10)` with `errno` checked; `if (e == p) return -EINVAL` (digits required — the same guard as our `if i == digits_start { return Ok(None) }`); `if (*p == '-') return -ERANGE`; an optional fraction accepted only if a digit follows the `.` (`if (e == p) … // Ignore failure. E.g. 10.M is valid` — note the documented leniency, the *opposite* of our `Ok(None)` for `"25."`); `e += strspn(e, WHITESPACE)` between number and unit; a **linear scan from a monotonically advancing index** `for (i = start_pos; i < n_entries; i++)` with `start_pos = i + 1` after each segment, which is how `1G2M` sums while also forbidding `2M1G`; and an explicit overflow gate `if (l + (frac > 0) > ULLONG_MAX / table[i].factor) return -ERANGE;` plus `if (tmp > ULLONG_MAX - r) return -ERANGE;`. Failure is `-EINVAL` (bad shape) vs `-ERANGE` (magnitude) — **two error classes for a size parse, in 1990s C.**

Our `UNITS` table maps `kb→KIB`, `mb→MIB`, `gb→GIB`: **the SI-looking spellings are silently aliased to 1024^n.** systemd's comment is the argument against that being an accident of spelling.

### Kubernetes `resource.Quantity` — a documented grammar comment and a three-way error split

`pkg/api/resource/quantity.go` (Apache-2.0, read at source this session; 966 lines). The header comment states the grammar in prose and then the tradeoffs:

- "1024 = 1Ki but 1000 = 1k; I didn't choose the capitalization."
- Values are "silently capped at 2^63-1" and precision "preserves only down to nano".
- "**NEVER use floating point**" for the value; `1.5Gi → 1536Mi` canonicalization.

Three error variables, i.e. a **three-way failure taxonomy for one parse**: `ErrFormatWrong` (165), `ErrNumeric` (166), `ErrSuffix` (167). The scanner is hand-written with labelled loops — `parseQuantityString(str) (positive bool, value, num, denom, suffix string, err error)` at line 170 implements `Zeroes:` / `Num:` / `Denom:` / `Suffix:` — and `ErrFormatWrong` is raised on trailing junk. A permissive regex `splitREString = "^([+-]?[0-9.]+)([eEinumkKMGTP]*[-+]?[0-9]*)$"` is documented as "this is overly permissive, but that's OK-- it will be checked later", i.e. **two-phase: cheap split, then precise validation** — with `// TODO: we currently allow 1.G, but we may not want to in the future.` next to the deliberately disabled check.

Precision is computed, not assumed: `precision = maxInt64Factors - int32(len(num)+len(denom))` and `forceRecanonicalize = precision <= 0`. `ParseQuantity(str)` (line 287) short-circuits `len(str)==0 → ErrFormatWrong` and `str == "0"`, then `quantitySuffixer.interpret(suffix(suf))` → `!ok` → `ErrSuffix` (302), then `strconv.ParseUint(shifted, 10, 64)` → `ErrNumeric` (375). The BinarySI fast path is `mantissa = int64(int64(mantissa) << uint64(exponent))`.

**Transferable as-is:** an explicit digit-count guard feeding an overflow decision, and three error classes where we have one. **Not transferable:** the re-canonicalization and the sub-nano rounding — our `target_bytes` is a `u64` where 1 byte is the floor and rounding must therefore be deliberate (see the `frac_num * mult / frac_den` truncation in our `parse_size`).

### PostgreSQL `pg_size_bytes` — `have_digits`, unit tables, and a documented ambiguity

`src/backend/utils/adt/dbsize.c` (PostgreSQL License; read at source). Static tables:

```c
static const char *const size_pretty_units[] = { "bytes", "kB", "MB", "GB", "TB", "PB", NULL };
static const struct size_pretty_unit { const char *name; int len; bool is_decimal; int exponent; } …;
static const struct size_bytes_alias { const char *name; int exponent; } size_bytes_aliases[] = { {"B", 0}, {NULL} };
```

with the source comments "When adding units here also update the docs and the error message in `pg_size_bytes`" and "Additional unit aliases accepted by `pg_size_bytes`" — **the alias table is a separate structure from the unit table**, which is precisely the split our flat `UNITS` array does not make.

The scanner is staged and documented by part: (1) optional sign; (2) main digit string, setting `have_digits`; (3) optional `.` plus fractional digits — which also sets `have_digits`; on completion `!have_digits` → `errcode(ERRCODE_INVALID_PARAMETER_VALUE)` + `errmsg("invalid size: \"%s\"", str)`; (4) an optional `e`/`E` exponent, with the comment "Note we might one day support EB units, so if what follows 'E' isn't a number, just treat it all as a unit to be parsed" — **the `E` in `1E` is ambiguous between exabyte and exponent, so the parser resolves it by lookahead and documents the resolution.** The numeric slice is then handed to PostgreSQL's own `numeric_in` (`saved_char = *endptr; *endptr = '\0';` … restore), and the unit is matched with `pg_strcasecmp(strptr, unit->name) == 0` — **case-insensitive**, then against the alias table.

**UNVERIFIED:** the multiplication code past ~line 851 and the exact "no unit found" error text were not read; therefore whether `kB` is treated as 1000 or 1024 bytes is `[INFERENCE]` from the `is_decimal`/exponent columns and must not be asserted.

### `parse-size` (Rust, MIT) — the base and the "B suffix" policy are both configuration

`kennytm/parse-size` `src/lib.rs` (note: `src/parsing.rs` is 404), version 1.1.0, MIT. `#![no_std]`; documented as "an accurate, customizable, allocation-free library for parsing byte size into integer". Two enums make the two ambiguities explicit:

```rust
pub enum UnitSystem { Decimal, Binary }   // Decimal: 1 KB == 1_000; Binary: 1 KB == 1_024
pub enum ByteSuffix { Deny, Allow, Require }
```

`Config::new()` is `Decimal / 1 / Allow` as `const fn`; `with_binary()`/`with_decimal()`/`with_unit_system()` are also `const fn`. `ByteSuffix::Deny`'s doc: "The 'B' suffix must never appear. Parsing a string with the 'B' suffix causes `Error::InvalidDigit`"; `Require`: "… without the 'B' suffix causes `Error::InvalidDigit`." Documented behaviours: "The unit is case-insensitive. The 'B' suffix is also optional" (`5gb → 5_000_000_000`, `2ki → 2048`), "Fractional bytes are allowed, and rounded to nearest integer" (`0.333333 KB → 333`, `2.666666 KB → 2667`), "Underscores and spaces in the numbers are ignored to support digit grouping" (`" 69_420_000" → 69_420_000`), and binary/decimal prefixes through exabytes with `UnitSystem::factor(prefix)` returning `None` for anything outside `K M G T P E` ("The higher powers Z and Y exceed the `u64` range and thus considered invalid"). Its clap integration is documented as `#[arg(long, value_parser = |s: &str| parse_size(s))] pub size: u64`, with a FIXME citing clap-rs/clap#4939. `parse_size::Error` is `#[non_exhaustive]` with variants `Empty`, `InvalidDigit`, `PosOverflow` (docs.rs, 1.1.0).

**This is the crate-level shape of everything the size half of this note recommends**, and it is 7 KB, `no_std`, and dependency-free. It is on the record here as the candidate if the `Cargo.toml` freeze is ever lifted.

### coreutils `numfmt` / gnulib `xstrtol` — the caller supplies the radix and the valid-suffix alphabet

`src/numfmt.c` (GPL-3.0-or-later): `enum scale_type { scale_none, scale_auto, scale_SI, scale_IEC, scale_IEC_I }`; `--from` accepts `"none","auto","si","iec","iec-i"` and `--to` accepts `"none","si","iec","iec-i"`; `scale_IEC`/`scale_IEC_I` select base 1024, everything else 1000. The suffix alphabet is a string, one character per legal suffix:

```c
static char const zero_and_valid_suffixes[] = "0KkMGTPEZYRQ";
static char const *valid_suffixes = 1 + zero_and_valid_suffixes;   /* leading 0 is a placeholder */
static bool valid_suffix (char suf) { return strchr (valid_suffixes, suf) != NULL; }
```

with `suffix_power(char suf)` switching `'k'/'K' → 1`, `'M' → 2`, `'G' → 3`, … Note that `Z`, `Y`, `R`, `Q` are in the accepted alphabet even where the value cannot fit.

`gnulib/lib/xstrtol.c` (**GPL-3.0-or-later** — "either version 3 of the License, or (at your option) any later version"; **design reference only, NOT borrowable, state this plainly anywhere it is cited**). Its contribution is the *interface*: `__xstrtol(char const *nptr, char **endptr, int base, __strtol_t *val, char const *valid_suffixes)` takes **both** the radix and the suffix alphabet as arguments, and the scaling helpers are overflow-checked by construction — `bkm_scale(__strtol_t *x, int scale_factor)` uses `ckd_mul` and on overflow sets `*x = TYPE_MAXIMUM/MINIMUM` and returns `LONGINT_OVERFLOW`; `bkm_scale_by_power(__strtol_t *x, int base, int power)` loops `while (power--) err |= bkm_scale(x, base);`. **The "the caller decides the base and the suffix alphabet" pattern is thus 1990s GNU policy, independently re-derived by systemd, parse-size, and numfmt.**

### restic `forget` — retention as a typed quantifier, and the boundary the quantifier counts on

`doc/060_forget.rst` (BSD-2-Clause). The grammar is a set of independently parseable flags: `--keep-last n` ("keep the `n` last (most recent) snapshots"), `--keep-hourly n` / `-daily` / `-weekly` / `-monthly` / `-yearly` ("for the last `n` hours which have one or more snapshots, keep only the most recent one for each hour"), `--keep-tag` (commas are AND within a list, repeating the option is OR across lists, and it errors if a whole group would be removed), and `--keep-within duration` with **compact multi-unit durations**: "`2y5m7d3h` will keep all snapshots made in the two years, five months, seven days and three hours before the latest".

Two caveats are stated and are the valuable part:

> All calendar related options (`--keep-{hourly,daily,…}`) work on **natural time boundaries and *not* relative to when you run `forget`**. Weeks are Monday 00:00 to Sunday 23:59 … They also only count hours/days/weeks/etc which have one or more snapshots.

> **A value of `unlimited` will be interpreted as "forever", i.e. "keep all".**

plus "All duration related options ignore snapshots with a timestamp in the future". **`unlimited` as a keyword is the escape hatch our grammar has no equivalent for** — every one of our rules either matches or lands in `unmatched`.

### The natural-language → typed-target path, and where the unit token ends

This subsection is about our own compiler, and there is no predecessor coverage of it.

The concrete sentence shape to reason about is `腾出 25 GB，留最近 3 个备份，别动我这两周在跑的项目`. Today it compiles as: `split_clauses` (delimiters `'，' | '。' | '；' | ';' | ',' | '、' | '\n'`) → rule 1 `parse_target_bytes` on clause 1 (verb `腾出` / lowercase `free up`, then `parse_size`) → rule 2 `fragment_is_mta` on the residual of clause 3 (`contains("别动") && (contains("这两周") || contains("近两周") || contains("最近"))`) → rule 3 `别动 <tail>` → `glob_for_tail` → `deny_globs`. Anything left over is collected by `clause_gaps`/`unmatched_parts` into `CompiledPolicy::unmatched`. Rules 2/3 scan **residual fragments after the consumed span**, not clause starts — verified at source, and it is the reason `腾出 25 GB，顺便清理` yields exactly `unmatched == ["顺便清理"]`.

The size sub-grammar, read line by line (`parse_size`, `src/policy.rs:222-270`), is:

```
size        := ws* digits [ "." digits ] ws* unit_tail
unit_tail   := ascii_alpha+            (token_len = suffix.bytes().take_while(u8::is_ascii_alphabetic).count())
```

and the **unit-token boundary rule is stated in the `UNITS` doc comment but enforced only implicitly**: "A unit token only counts when the character after it is NOT ASCII-alphabetic — `25 goals` must not read as 25 GiB." Mechanically that is `take_while(is_ascii_alphabetic)` — the token *is* the maximal alphabetic run, so `goals` is one token, is not in `UNITS`, and becomes `Err(PolicyError::UnrecognizedUnit("goals"))` (this exact case is pinned by `tests/plan_tests.rs::policy_single_letter_unit_needs_token_boundary`). The doc comment is therefore **normative prose describing an emergent behaviour of the scanner**; nothing in the type system or the table encodes it.

Three further facts about the sub-grammar, all verified by reading:

1. `token_len == 0` → `Ok(None)` ("number without a unit"). So `腾出 25` is *unmatched*, not a byte target.
2. `whole == u64::MAX` on parse failure (`rest[digits_start..i].parse().unwrap_or(u64::MAX)`) and a subsequent `checked_mul(mult) == None` → `Ok(None)` — the source comment says "Absurd magnitude (u64 overflow) keeps the old soft path" and "Only an unknown UNIT is a hard error". **A 30-digit number is therefore softer than `25 XB`.**
3. The fraction denominator is `10u64.pow((j - frac_start) as u32)`. From `library/core/src/num/uint_macros.rs` (`pub const fn pow(self, exp: u32) -> Self` → `if intrinsics::overflow_checks() { self.strict_pow(exp) } else { self.wrapping_pow(exp) }`, and `strict_pow` → `match self.checked_pow(exp) { None => imp::overflow_panic::pow(), Some(a) => a }`): **with overflow checks on (debug, and any `-C overflow-checks=on` build) an exponent ≥ 20 panics; in release it wraps silently.** `frac_num` is likewise `parse().unwrap_or(0)`. Since the exponent is just the count of typed fraction digits, `腾出 0.00000000000000000001 GB` is a one-line panic in debug. This is the single highest-severity finding of this lane and it is a *read* of std, not a run of the repo.

Two structural gaps follow from the same read:

- **`--min-bytes` never goes through this grammar at all.** `src/main.rs` declares `Cmd::Scan { roots, json, min_bytes: Option<u64> }` and `Cmd::Plan { scan_json, policy, min_bytes: Option<u64>, out }`; `run_plan` does `if let Some(mb) = min_bytes { pc.min_bytes = mb; }` under the comment `// CLI floor wins over the compiled default (last-mile knob, §3.6).`, and `run_scan` does `Thresholds { min_bytes: min_bytes.unwrap_or(Thresholds::default().min_bytes), .. }`. Both are raw `u64` bytes parsed by clap, never by `parse_size`. **`--min-bytes 50MB` is either a clap type error or a silently wrong number, while `腾出 50 MB` in the identical program parses units.** The NL path has a grammar; the CLI path does not.
- **`PolicyError` has one variant while the parse has at least four distinct failure classes** — unknown unit (hard `Err`), no digits (`Ok(None)`), no unit token (`Ok(None)`), magnitude overflow (`Ok(None)`). The severity assignment is currently "did we find a verb AND a number AND a unit?" rather than "what went wrong", which is why `25 goals` is fatal but `25` is not.

`CompiledPolicy` is where the rest of the sentence lands:

```rust
pub struct CompiledPolicy {
    pub constraints: PolicyConstraintsShape,
    pub applied_rules: Vec<&'static str>,   // "target_bytes" | "deny_under_mta" | "deny_globs"
    pub unmatched: Vec<String>,
}
```

and `PolicyConstraintsShape { target_bytes: Option<u64>, min_bytes: u64, allow_grades: Vec<Grade>, deny_globs: Vec<String>, deny_under_mta_secs: u64 }` with `Default` = `target_bytes: None`, `min_bytes: 50 * 1024 * 1024`. `Plan` stores the whole shape as `policy_snapshot`, so **`target_bytes` is persisted and machine-readable, while `unmatched` is not persisted at all** — a plan cannot be audited later for "what did the compiler not understand". In `src/plan.rs::build()` the running total that the target-seeking loop would compare against `target_bytes` is `acc_bytes`, and `PlanTotals` has no field for the target itself: `PlanTotals { quarantine_bytes, quarantine_entries, prune_bytes, prune_cmds, refused, snapshot_caveat }`. Also verified in `build()`: hardlink dedup uses `let mut seen_inodes: HashSet<(u64, u64)>` and `if seen_inodes.insert((c.dev, c.ino)) { quarantine_bytes += c.alloc_bytes; acc_bytes += c.alloc_bytes; }`, while `quarantine_entries += 1` sits **outside** that check — so entries and bytes are deliberately different counters, which is exactly the accounting unit ambiguity Hazel's "oversized file" carve-out resolves in a different way.

### Grammar improvements for the sentence `腾出 25 GB，留最近 3 个备份，别动我这两周在跑的项目` (risk-rated)

Each item is scoped to the size/unit sub-grammar of `src/policy.rs`, is implementable with std only (no `regex`, no new dependency — `Cargo.toml` frozen), and carries a risk rating for the *design*-level change, not for the typing effort.

| # | Improvement | Risk | Why |
|---|---|---|---|
| 1 | **Promote the existing doc comment to a normative production.** Write `size := ws* digits [ "." digits ] ws* unit ; unit := ascii_alpha+` as a real grammar block in the module docs and cite the byte offsets (`parse_size`, `src/policy.rs:222-270`) it compiles to. | **low** | The rule already holds (`take_while(is_ascii_alphabetic)` *is* the maximal-munch token rule) but exists only as prose in `UNITS`' doc comment. Making it normative costs a doc edit and gives the design document a citable production instead of an implementation detail. |
| 2 | **State the case policy explicitly and pin it.** `to_ascii_lowercase()` unifies `GB`/`gb`/`Gb` before the table lookup. Document that the policy is "case-insensitive ASCII, applied to the unit token only". Add one test for `25 gB`. | **low** | parse-size ("The unit is case-insensitive"), PostgreSQL (`pg_strcasecmp`) and coreutils (`"0KkMGTPEZYRQ"`) all agree; Kubernetes `Quantity` intentionally does **not** ("1024 = 1Ki but 1000 = 1k; I didn't choose the capitalization") because there cases carry meaning. Our table has no case-meaningful entry, so case-insensitivity is free — but it should be *stated*, not left to be re-derived. |
| 3 | **Document that `kb`/`mb`/`gb` mean 1024^n today.** The `UNITS` table aliases the SI spellings onto the binary multiples; systemd's comment ("you really need to make sure to document which base you are parsing") is the precedent for this being a documented property rather than an accident. | **low** | Pure documentation. The alternative — renaming the aliases to reject `gb` — is a **high**-risk user-facing break and should not be done silently. |
| 4 | **Give `parse_size` an explicit base** (`fn parse_size(rest: &str, base: SizeBase) -> …` with `SizeBase { Decimal, Binary }`), so `KB = 1000` and `KiB = 1024` become distinguishable and the choice is an input, not a table property. | **med** | This is the systemd/parse-size/numfmt/xstrtol convergence. It is **med**, not low, because it changes an observable expectation: with a decimal base, `腾出 50 GB` selects a different byte count than today and `tests/plan_tests.rs::policy_english_free_up_works` would need its expectation updated. That is a deliberate behaviour change and must be labelled as one. |
| 5 | **Decide multi-unit concatenation and document the decision.** `腾出 1G2M` currently parses as… nothing usable (the second segment is not consumed, so the tail lands in `unmatched`). | **med** | systemd accepts and sums (`start_pos = i + 1`); Kubernetes rejects; restic's `2y5m7d3h` is the summed form *for durations*. For a byte target the summed form has no user need and makes the boundary rule harder to state. Recommend: **reject, in writing** — one number, one unit. |
| 6 | **Guard the fraction before the exponentiation.** `frac_den = 10u64.pow((j - frac_start) as u32)` panics in debug for ≥20 fraction digits. Options: cap accepted fraction length, or replace with a checked-multiply loop, or use `checked_pow`. | **med** (defect severity **high**) | The panic is verified at source in std, and the input is one typed line. Precedent: humantime's `Error::NumberOverflow` on the identical computation (`denominator.checked_mul(10).ok_or(Error::NumberOverflow)?`) and its comment about needing a separate precision-limit error. Rated **med** only because the fix is one expression and the reachable path needs 20 typed digits. |
| 7 | **Add a retention quantifier production** — `留最近 3 个备份` → a `keep_last: Option<u32>`-shaped field on `PolicyConstraintsShape` plus selection semantics in `plan::build()`. | **med→high** | The grammar is trivial (`verb ws* digits ws* 个? quantifier`); the risk is entirely in the *semantics*: restic's documentation is explicit that calendar-related keeps "work on natural time boundaries and *not* relative to when you run `forget`" and "only count hours/days/weeks/etc which have one or more snapshots". Getting that wrong makes "keep the last 3" mean something different every run. It also interacts with `decide()`'s "keep ≥1 entry" floor and with `ancestor_git_head_mtime`. |
| 8 | **`unlimited` as an explicit keyword** (restic: "A value of `unlimited` will be interpreted as 'forever', i.e. 'keep all'"). | **med** | The grammar cost is one token; the reason it is med is that "keep all" means *no target*, which is the state the compiler deliberately avoids creating accidentally (the doc comment's Bug 1 rationale). It should be a *named* state, never a fallback. |
| 9 | **Percent-of-capacity as a distinct result type** — `腾出 30% 的空间` cannot be a `u64` at compile time. | **high** | `plan::build(cands, pc, vols)` already receives `volumes: &[VolumeInfo]`, so the resolution point exists; what does not exist is a type that says "target = fraction × capability". Hazel ships this as one of exactly three unit choices ("MB," "GB," or "% of disk capacity"), which is external evidence that users ask for it. High risk: it moves the target from a constant to a per-volume computation, which touches `decide()`'s signature. |
| 10 | **Compact multi-unit retention durations** (`2y5m7d3h`) replacing the `TWO_WEEKS_SECS` constant. | **high** | restic's `--keep-within duration` is the precedent and its month/year approximations (30.44 d / 365.25 d) match humantime's `Month`/`Year`. High risk because `deny_under_mta_secs` is currently a plain `const` consumed by `fragment_is_mta`-gated rules; making it parsed means the "这两周" literal becomes one entry in a duration grammar, and duration units collide with the *byte* unit alphabet (`m` = minute vs `mb` = mebibyte). That collision is the real reason to rate it high. |
| 11 | **Make the severity of an unrecognized clause first-class.** Today: a bad unit token is a hard `Err` (fatal, whole sentence rejected) while an equal-length unrecognized free-text fragment is soft (`unmatched`, plan proceeds) — the split is "did we find a verb AND a number AND a unit", which is not a principle. | **high** | Cedar (two-arm `ParseError` + `ParseErrors(NonEmpty<_>)`), pomsky (`Severity { Error, Warning }`, diagnostics returned alongside the result), OPA (`Errors` with `Code` + sorted `Location`) and koto (`ExpectedIndentation` as its own recoverable type) all model severity/class explicitly. Changing ours changes the fail-closed contract the doc comment calls Bug 1, so it must be argued deliberately, not refactored in. |

**On the placeholder clause `留最近 3 个备份` specifically:** note that `fragment_is_mta` requires the possessive/negative verb `别动` — "「这两周」 alone is a description, not a protection". The same discipline should apply to any new quantifier rule: `留最近 3 个` must require its own verb (`留`/`keep`), otherwise a stray `3` in prose silently becomes a retention policy. The existing rule chain already gets this right; the recommendation is to state it as a rule-writing convention in the module docs.

## Risks & open questions

1. **The `10u64.pow` panic is verified at source but was never triggered in this repository.** I read `library/core/src/num/uint_macros.rs` (`pub const fn pow` → `strict_pow` under `intrinsics::overflow_checks()`, and `strict_pow` → `imp::overflow_panic::pow()` on `None`) and reproduced the arithmetic by hand (`10^20 > u64::MAX`). I did **not** run the project (forbidden by the lane boundaries) and there is no existing test with a ≥20-digit fraction. **State the finding as "verified at source in std; reachable from `parse_size` by inspection", not as an observed crash.**
2. **`unmatched`'s severity contract is unstated anywhere I could find.** `compile()`'s doc comment explains the Bug 1 rationale for `Err` on an unknown unit, but nothing states when a fragment *should* be fatal. Until that is written down, backlog rows 3/12 are design decisions, not bug fixes.
3. **`--min-bytes`'s failure mode is not fully determined.** I verified the option is `Option<u64>` at both `Cmd::Scan` and `Cmd::Plan`, is assigned verbatim to `PolicyConstraintsShape::min_bytes`, and is never routed through `parse_size`. Whether `--min-bytes 50MB` is rejected by clap's `u64` parser or by an outer wrapper is not something I read; **do not claim a specific error message.**
4. **pomsky's source was not reachable.** `pomsky-lib/src/error.rs` returned 404 on both attempts; only docs.rs (0.12.0) and the crates.io record were read. Everything attributed to pomsky in this note comes from its generated docs — treat the exact field/method spellings as docs.rs-verified rather than source-verified.
5. **bytesize's internals are entirely unread.** `src/parser.rs`, `src/parse.rs` and `src/lib.rs` all 404 on the paths tried; only the docs.rs crate page, the `KB`/`KIB` constant pages and the crates.io record were read. 6. **PostgreSQL `pg_size_bytes`'s multiplication stage and no-unit error text were not read** (past ~line 851). Whether `kB` means 1000 or 1024 bytes there is `[INFERENCE]` from the `is_decimal`/exponent columns; **do not assert it.** The parts I do claim — `have_digits`, the two tables, the `E`-ambiguity comment, `pg_strcasecmp` — were read verbatim.
7. **casbin's in-tree version is 2.18.1 while crates.io's newest is 2.20.0.** The `Cargo.toml license = "Apache-2.0"` field was read from the tree; the version delta is recorded rather than resolved. 8. **Two copyright-encumbered sources are cited as design references only and must never be ported**: gnulib's `lib/xstrtol.c` and coreutils' `src/numfmt.c`, both **GPL-3.0-or-later**, and systemd's `src/basic/parse-util.c`, **LGPL-2.1-or-later**. Their *ideas* (caller-supplied base, suffix alphabet, two-class errors) are independently present in MIT/Apache-2.0 projects (`parse-size`, `bytesize`, upstream Rust std), so only those permissive sources may be translated.
9. **Open question: should `unmatched` be a hard error when the sentence contains a size verb at all?** The current rule makes `腾出 25` (no unit) soft while `腾出 25 goals` is fatal. If the design document argues the verb is the signal of intent, the `Ok(None)`-on-no-unit path becomes a defect; if it argues the unit is the signal, the current behaviour is right. This is the single decision that backlog rows 3 and 12 hinge on and it is not answerable from the code alone.
10. **Open question: unit-alphabet collision between byte and duration units.** Any duration grammar (`2y5m7d3h` per restic) introduces `m` for months/minutes into the same sentence that already accepts `m` as mebibytes. `parse_size` only ever looks at a token immediately after a number following a size verb, so a collision is currently impossible — but a duration parse for `deny_under_mta_secs` would have to be lexically separated from the size parse, which is a design constraint that has to be stated before anyone implements backlog row 4's `base` parameter or row 11's retention field.
