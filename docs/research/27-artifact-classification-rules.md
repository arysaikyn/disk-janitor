# Artifact-Classification Rulesets — Research Note

How production artifact-cleaners *express* a rule (compiled const / TOML / XML / TypeScript object / Go slice / Ruby / CLI flag), how they decide a path is derived-but-regenerable, and whether the rule carries any age or cost dimension · researched 2026-09-13

Scope: the **rule architecture** of kondo 0.9.0, cargo-sweep 0.8.0, npkill 0.12.2, node-prune, czkawka/Krokiet 12.0.2, BleachBit 5.0.0 CleanerML, `pip cache purge`, `brew cleanup`, `nix store gc` / `nix-collect-garbage` (Nix 2.36.0), `docker system|image|builder prune` (docker/cli 29.8.1 + moby engine), fastlane `clear_derived_data` 2.239.0, and jemishavasoya/dev-cleaner 1.2.0. Every version, license, and API claim below was read from the project's own `LICENSE`/`COPYING`/`Cargo.toml`/`package.json`/`__init__.py`/`.version`, from the actual source file, or from a primary API/dedicated manual page, on **2026-09-13**; each is attributed in `## Sources`. Facts marked **[INFERENCE]** are reasoned, not read.

**Additivity statement (NEW vs predecessor notes).** Notes `01` (kondo line 70, cargo-sweep line 77, npkill line 84, node-prune line 92; comparison table lines 17–20; crates table line 119; risks 130–135) and `03` (cargo-sweep flags line 54, `pip cache purge` line 62, Xcode tiers lines 69–80, `brew cleanup` lines 87–90, Docker lines 98–102; risks 143–145) already cover the **tool landscape**, per-tool path/tier tables, delete calls, walkers, licenses, and worker pools. This note deliberately does **not** restate those tables. Its NEW axis is four questions asked of each tool: **(a) where does the rule live** (compiled const vs external data file vs source code), **(b) is the rule age-aware** (mtime / atime / ctime / none), **(c) how is regeneration cost encoded** (or not at all), and **(d) what is the user extension point**. Every NEW finding below is marked; facts already established by `01`/`03` are cited by line and left there. Note `02` (renamex_np/EXDEV taxonomy) and `21` (DaisyDisk UX principles) share no ground with this lane.

## Findings

### BleachBit 5.0.0 — CleanerML: the only declarative, user-editable, XSD-validated ruleset in the survey

BleachBit is the outlier: its rules are **external XML data files**, validated against a public XSD, loaded at runtime, and extendable by the user without recompiling. Verified: `bleachbit/__init__.py:32` `APP_VERSION = "5.0.0"`; `COPYING` is the GPL v3 text ("GNU GENERAL PUBLIC LICENSE / Version 3, 29 June 2007").

**A complete rule, in full** (`cleaners/bash.xml`, read verbatim) — two options, two actions, no metadata beyond labels:

```xml
<cleaner id="bash" os="unix">
  <label>Bash</label>
  <description>Shell</description>
  <option id="history">
    <label>History</label>
    <description>Delete the command history</description>
    <action command="delete" search="file" path="~/.bash_history"/>
  </option>
  <option id="tmp">
    <label>Temporary files</label>
    <description>Delete the temporary files</description>
    <action command="delete" search="glob" path="~/.bash_history-*.tmp"/>
  </option>
</cleaner>
```

**The schema** (`doc/cleaner_markup_language.xsd`, 212 lines, read in full). Structure is `cleaner[@id, @os]` → `<label>`, `<description>`, `<running type=exe|pathname same_user>`, `<var name>` → 1..n `<value search=…>`, then 1..n `<option id>` → `<label>`, `<description>`, optional `<warning>`, 1..n `<action>`, and an optional `<localizations><path>` block. The two attributes that matter for rule architecture:

- `action/@command` — a **closed 23-value enum** (verified by extracting every `<xs:enumeration value=…>` between lines 123 and 162 of the XSD): `apt.clean`, `apt.autoclean`, `apt.autoremove`, `chrome.autofill`, `chrome.databases_db`, `chrome.favicons`, `chrome.history`, `chrome.keywords`, `delete`, `dnf.autoremove`, `dnf.clean_all`, `ini`, `journald.clean`, `json`, `mozilla.favicons`, `mozilla.url.history`, `office_registrymodifications`, `process`, `sqlite.vacuum`, `truncate`, `win.shell.change.notify`, `winreg`, `yum.clean_all`. This is the **action** half of the rule — and note the split inside it: `delete`/`truncate` are *generic* filesystem actions, while `chrome.history`, `sqlite.vacuum`, `journald.clean`, `winreg` are *application-aware* actions that need a backend implementation keyed to the enum value.
- `action/@search` — a **closed 6-value enum** (`xsd:163-173`): `deep`, `file`, `glob`, `walk.all`, `walk.files`, `walk.top`. This is the **scoping** half: `file` = one exact path, `glob` = shell-expanded pattern, `walk.all` = the directory and its contents, `walk.files` = contents only, `walk.top` = one level.

Other `action` attributes: `address`, `cmd`, `name`, `parameter`, `path`, `regex`, `nregex`, `wholeregex`, `nwholeregex`, `type`, `wait`, `section`, plus the `operatingSystem` group (`@os`). The `@os` enum is `bsd | darwin | linux | netbsd | openbsd | freebsd | unix | windows`.

**The `<var>` indirection layer is the only abstraction in the format.** `CleanerML.py:239-265` `handle_cleaner_var` reads `<value>` children, filters by `os_match()`, and — when `value_element.getAttribute('search') == 'glob'` — calls `expand_glob_join(value_str, '')` before merging into `self.vars`. Cleaners then reference `$$name$$` inside `path` attributes (e.g. `cleaners/chromium.xml` defines `<var name="base">` with five per-OS `<value>` rows, then writes `<action command="delete" search="walk.all" path="$$base$$/ShaderCache"/>`). So a rule can name a *family of roots* once and reuse it across many actions. This is the closest thing in the whole survey to our ancestor-probe indirection.

**NEW — the format is completely age-blind.** `grep -c -i -E "mtime|age|older|days" doc/cleaner_markup_language.xsd` → **0**. `grep -rn -i -E "st_mtime|getmtime|older_than|mtime" bleachbit/*.py` → **zero hits**. There is no attribute anywhere in CleanerML that could express "older than N days". Every rule is a *location* rule, never a *staleness* rule. Deletion timing is entirely the user's click.

**NEW — darwin is schema-legal but unused.** `CleanerML.py:109-110` widens the accepted set (`if platform == 'darwin': current_os = ('darwin', 'bsd', 'unix')`), so macOS cleaners are *loadable*. But `grep -rl 'os="darwin"' cleaners/` → **0 files**, against usage counts of linux 120, windows 82, freebsd 13, unix 14, openbsd 10, bsd 1 (93 XML files, 240 `os=` attributes). `cleaners/safari.xml` exists but is `os="windows"` only (Safari for Windows). Conclusion: BleachBit's schema anticipated macOS; its rule corpus never followed. Any macOS borrowing is schema-level, not data-level.

**NEW — the extension point is a directory.** `__init__.py:116` `personal_cleaners_dir = os.path.join(options_dir, "cleaners")` and `__init__.py:125` `system_cleaners_dir = '/usr/share/bleachbit/cleaners'` (darwin branch). A user drops a `.xml` into their options dir and the tool loads it. Combined with the XSD, this is a **published plugin contract**: third-party rules are validated by the same schema the shipped ones are.

**NEW — there is a running-process gate, expressed as data.** `<running type="exe">chrome.exe</running>` lives in the cleaner's own XML. `Cleaner.py:85-89` `add_running(detection_type, pathname, same_user=False)`; `Cleaner.py:154-172` `is_process_running()` implements exactly two tests — `'exe'` → `_is_process_running(pathname, same_user)` (a process-table lookup), and `'pathname'` → "does any glob match of this path exist" (a lockfile-exists heuristic). The gate is enforced where it matters: `Worker.py:160` `if self.really_delete and backends[operation].is_process_running():` → prints "%s cannot be cleaned because it is currently running. Close it, and try again." and **skips the whole cleaner**. Note the shape: the guard is checked **after** the dry-run scan and **before** any deletion, at the operation level, not per-file. `Action.py:443-451` `class Delete(FileActionProvider)` with `action_key = 'delete'` simply yields one `Command.Delete(path)` per resolved path — the delete action itself carries no safety logic at all; safety is externalized into `<running>` + the worker gate.

**Rule shape in one line:** *declarative XML (action × scope) + a glob indirection table + a data-declared process guard; no age, no cost, no grade.*

### kondo 0.9.0 — compiled `&'static [&'static str]` rule tables, plus a real age gate

Verified: `kondo-lib/Cargo.toml` `version = "0.9.0"`, `license = "MIT"`. Note `01` line 70 already documents the 23/24-ecosystem `ProjectType` table and its `PROJECT_*_DIRS` consts (`lib.rs:9-33` marker-file consts; `lib.rs:35+` dir arrays). NEW facts this session:

- **The rule is a compile-time const array and nothing else.** `lib.rs:163-195` `pub fn artifact_dirs(&self) -> &[&str]` is a single `match` over `ProjectType` returning `&PROJECT_*_DIRS`. There is no data file, no config, no runtime override. Adding an ecosystem means editing `lib.rs` and recompiling. (24 match arms are present; the smaller "23 types" figure in `01` predates one addition.)
- **NEW — the only user-facing rule knob is a global age filter, not a list editor.** `kondo/src/main.rs:49-51`: `#[arg(short, long, value_parser = parse_age_filter, default_value = "0d")] older: u64`, with `parse_age_filter` (`main.rs:127-141`) accepting `m/h/d/w/M/y` (MONTH = 4 weeks, YEAR = 365 days). Enforcement is `main.rs:199`: `if last_modified_int < project_min_age { continue; }`. So kondo's answer to "how do I make this safe for my running projects?" is **a time threshold applied to a computed project mtime**, not a bigger exclusion list.
- **NEW — that mtime is computed, not read.** `lib.rs:209-228` `pub fn last_modified` seeds an `ignore::WalkBuilder::new(&self.path)` walk with the project directory's *own* `metadata().modified()`, then folds every entry's mtime to a **max**. `last_modified` is therefore "the newest thing anywhere in this project", which is the same semantic as our `DirAgg.max_mtime` feeding `Thresholds::hot_mtime` — except kondo compares it to a *user-supplied day count* rather than a fixed hot window. **[INFERENCE]** kondo needs the walk because it has no per-directory aggregate; our `candidates_from_batch` already folds `max_mtime` bottom-up, so the borrowing is the *exposed knob*, not the computation.
- Dry-run exists (`main.rs:62` `-n/--dry-run`, conflicts with `--all`), and `--same-filesystem` (`main.rs:47`) constrains the walk. Deletion stays `fs::remove_dir_all` (`lib.rs:317-329` `pub fn clean`) with error-per-directory logging — permanent, no quarantine, as `01` records.

### cargo-sweep 0.8.0 — atime-based keep criteria and an explicitly chosen comparison operator

Verified: `Cargo.toml` `version = "0.8.0"`, `license = "MIT"`. `01` line 77 and `03` line 54 already cover the flag surface and the unmaintained banner. NEW facts:

- **NEW — the age signal is atime, not mtime, and it is a min-fold.** `src/fingerprint.rs:109-122` `fn last_used_time(fingerprint_dir: &Path) -> Result<Duration, Error>` takes the **minimum** `accessed()` across a `.fingerprint/<dir>`'s entries, seeded with `Duration::from_secs(3_155_760_000)` (the source comment reads "100 years!"). Minimum, not maximum: cargo-sweep asks "when was the *oldest* thing in this fingerprint last touched", so a single stale file ages the whole fingerprint. **This is the opposite fold from kondo's max** — and the opposite of ours (`DirAgg.max_mtime`). Two tools, two legitimate answers: max answers "is anyone still working here", min answers "has this specific build artifact gone cold". Our `Thresholds::hot_mtime` is a max-fold question, so min-fold is not a candidate replacement — but it is the right shape for a *future* per-entry staleness signal.
- **NEW — the boundary is a strict `<`.** `fingerprint.rs:147-165` `load_all_fingerprints_newer_than(fingerprint_dir, keep_duration)` keeps a directory when `last_used_time(&path)? < *keep_duration`. The keep-set is therefore "strictly younger than the cutoff"; exactly-at-the-cutoff is kept. Our `plan.rs::decide` target gate uses `acc_bytes >= t` (reached ⇒ stop) which is the mirror-image inclusive boundary, and `quarantine_entries > 0` guarantees ≥1 entry survives. The subtle point worth importing: **when a threshold decides deletion, the comparison operator is a user-visible semantic** and should be chosen deliberately, not inherited from whatever `<`/`<=` was typed.
- **NEW — two mutually exclusive keep-criteria in one dispatch.** `src/main.rs:224-231`: `Criterion::File` → `Timestamp::load(paths[0], dry_run)?` (the `--stamp` workflow: keep everything built since a recorded timestamp) versus `Criterion::Time(days)` → `Duration::from_secs(days * 24 * 3600)`; `main.rs:234` dispatches both into the same `remove_older_than(project_path, &keep_duration, dry_run)`. A third mode, `--installed`/`--toolchains`, bypasses duration entirely (`main.rs:180-181`) and keeps by toolchain identity. Public entry points: `hash_toolchains()`, `remove_not_built_with()`, `remove_older_than()`, `remove_older_until_fits(path, target_size, dry_run)`. **The architectural lesson is that three different *kinds* of keep-criterion (time / marker / identity) converge on one deletion routine** — the criterion is data, the deletion is code.

### npkill — a one-string rule on npm, a full profile+config system on `main`

**Partition this finding by which artifact you read; the two are not the same program.** npm registry metadata for `npkill` gives `dist-tags.latest = 0.12.2`, published **2024-06-08T15:24:31Z**, tarball shasum `3dcaa1bdf769412c9f17ef6927e324cb21e01133`, `"license": "MIT"`. That published tarball has **no** `profiles` module, **no** `.npkillrc`, and **no** risk analysis; `dist-tags.next = 0.12.2-1` was checked and has none either. The GitHub `main` branch — still version-labelled `0.12.2` in its own `package.json` — contains all three. Any claim about npkill therefore has to name the branch; I report the released surface as the shipping rule and `main` as the direction of travel.

**Released 0.12.2 — the rule is one CLI string.** `DEFAULT_CONFIG.targetFolder = 'node_modules'` (`lib/constants/main.constants.js:19`), overridden by `-t, --target` — singular, one value (`lib/constants/cli.constants.js:59-62`). `01` line 84 called this a basename safety gate; read literally it is weaker than that. The actual gate:

```js
isSafeToDelete(path, targetFolder) { return path.includes(targetFolder); }   // files.service.js:45
```

That is a **substring** test on the whole path, not a basename test, and it is the only pre-delete validation in the release. Its companion is a second, independent heuristic — `isDangerous(path)` (`files.service.js:58-65`) — three path regexes: a hidden segment anywhere (`/(^|\/)\.[^/.]/`), `/Applications/<x>.app/`, and `AppData\`. Danger does **not** block deletion; it only drives the `⚠️` marker (`results.ui.js:101,127`) and a stats counter. So the released tool's entire "is this rule-bound and safe?" structure is: one substring, one display-only danger flag.

**Age exists but is display-only, and it is a *directory-activity* signal.** `getRecentModificationInDir` recurses the candidate, skips nested `node_modules`, folds files to the **max** `mtimeMs/1000` (`files.service.js:66-70`), and returns a number or `-1`. `modificationTime` then drives `FOLDER_SORT['last-mod']` (`constants/sort.result.js:4-17`, `null` sorts last) and the `Nd` age column (`results.ui.js:121-122`). It is **never compared to a threshold** — no age gate exists, so a 2-year-old `node_modules` and a 2-hour-old one are equally eligible; age only changes the sort order. This is the same max-mtime semantics our `agg.max_mtime` uses, which makes it a useful cross-check for `classify_dir`'s `hot` test rather than a new idea.

**`main` — the ruleset became a typed object plus a user file.** `src/core/constants/profiles.constants.ts` defines `DEFAULT_PROFILE = 'node'` (line 4), `BASE_PROFILES` with **17** named profiles (lines 7, 38, 55, 68, 72, 77, 82, 87, 92, 96, 101, 106, 110, 115, 120, 125, 130: `node, python, data-science, java, android, swift, dotnet, rust, ruby, elixir, haskell, scala, cpp, unity, unreal, godot, infra`), a generated union `ALL_TARGETS = [...new Set(...flatMap(p => p.targets))]`, and `DEFAULT_PROFILES = { ...BASE_PROFILES, all: {...} }` (lines 147–158) whose `all` profile ships its own warning *inside* the `description` string. A profile is exactly two fields — `PROFILE { targets: string[]; description: string }` (`profile.interface.ts`) — so **the machine-readable half is a bare string list and the regeneration knowledge is untyped prose**. Node's list is 25 targets covering caches that live outside any project (`.vite`, `.turbo`, `.nx`, `.parcel-cache`, `.eslintcache`, `.swc`, `deno_cache`, …) — a *toolchain-cache* taxonomy, where kondo's is a *project-artifact-dir* taxonomy. `docs/profiles.md` supplies per-target regeneration prose ("`.next` … Regenerated on the next `next dev` or `next build`", same shape for `.turbo`, `.nyc_output`, `.venv`, `.dvc`), and opens by stating the matching granularity outright: **"Only directory base names are matched (the last path segment) (more advanced heuristics will be implemented in the future)."**

**`main` — the user extension point is `.npkillrc`, and user profiles override built-ins.** `INpkillrcConfig` (`npkillrc-config.interface.ts`) exposes `rootDir, exclude, sortBy, sizeUnit, excludeSensitiveResults, dryRun, checkUpdates, defaultProfiles`, and `profiles?: Record<string, PROFILE>`. Search order is `--config <path>` → `./.npkillrc` → `~/.npkillrc` (`docs/npkillrc.md` §Location). `ProfilesService.getProfiles('all')` is literally `{ ...DEFAULT_PROFILES, ...this.userDefinedProfiles }` — **user-defined wins on name collision**, with `getProfileByName` checking user first. `profile-validator.ts` requires `description` to be a non-empty string and `targets` to be a non-empty string array. In `cli.controller.ts:271-345` the config is applied per-field: `exclude` is **merged** (`[...new Set([...this.config.exclude, ...result.config.exclude])]`) while every scalar is **assigned**; `--profiles` and `--targets` are mutually exclusive (parse errors out), and `--profiles` with zero values prints a listing that tags entries `(user-defined)` / `(default)`.

Two further `main`-only findings worth stealing: `isSafeToDelete` was **rewritten from substring to exact basename** — `targets.some(t => t === path.basename(filePath))` (`utils/is-safe-to-delete.ts`), i.e. the maintainers themselves closed the `path.includes()` hole, and it is re-checked at delete time (`cli.controller.ts:906`), not only at scan time. And `files.service.ts:150-197` is a genuine **sensitivity classifier** returning `{ isSensitive, reason }` (`RiskAnalysis` in `folder.interface.ts:9-14`), whose rules are the interesting part: top-level hidden dirs under `$HOME` are sensitive *except* `.npm`/`.pnpm`; `~/.config` and `~/.local/share` are sensitive; `~/.cache` is sensitive-but-deletable; `/Applications/<x>.app/`; Windows `AppData\Roaming` and `AppData\Local` (except `.cache`/`.npm`/`.pnpm`) and `Program Files`. That is a **keep-list-style danger taxonomy layered on top of a delete-list** — the inverse composition of our `PathClass` + `Refusal` design.

**The dry-run is a fake.** Both branches run `fakeDeleteDir`, which sleeps `Math.random()*4000+200` ms and returns `true` (published `files.service.js:5-9`; `main` `npkill.ts:119-121` selects it on `options?.dryRun`). Nothing is measured and nothing is simulated beyond the delay, and the caller marks the folder `status = 'deleted'` and re-renders stats. It proves the *control flow* is dry-run-aware and nothing more — contrast docker's dry-run below, which runs the real operation in a non-committing mode and returns a computed summary.

### node-prune — a Go slice with a documented precedence ladder and last-write-wins overrides

`internal/prune/prune.go` (350 lines, read in full); `LICENSE` = MIT "Copyright (c) 2017 TJ Holowaychuk". `01` line 92 covers the yarn-derived lists and the channel-worker deletion pool. NEW — the **matching precedence**, which is the most directly borrowable thing in this tool. `func (p *Pruner) prune(path string, info os.FileInfo) bool` at `prune.go:268-306`:

1. `p.excepts` globs, matched with `filepath.Match(glob, info.Name())` → return **false** (never prune).
2. `p.globs` → return **true** (always prune).
3. `if info.IsDir()` → `_, ok := p.dirs[info.Name()]` — **only directories are looked up by basename**.
4. `p.files[info.Name()]` — file basename.
5. `p.files[path]` — file exact full path (an escape hatch for path-anchored rules).
6. `p.exts[filepath.Ext(path)]` — note `filepath.Ext` **includes the leading dot**, so the 9 `DefaultExtensions` entries are `.md`, `.js`, `.coffee`, `.tgz`, `.swp`, … .
7. otherwise keep.

Exceptions outrank globs outrank dir-basename outrank file-basename outrank dir-vs-file disambiguation. `dir` match aborts the descent with `filepath.SkipDir`. **The ordering is explicit policy**: a broad `globs` rule cannot override a narrow `excepts` protection, because the exception is tested first. Our `plan.rs::decide` has the same property at a coarser grain (hard evidence refusals precede policy deny-globs precede selection caps), and our deny-glob walk (`while let Some(cur) = p.parent()`) is the ancestor-aware version of node-prune's rule 5. The *specific* thing node-prune adds that we lack: **the dir-vs-file distinction baked into the rule table** (`p.dirs` is only consulted for directories, `p.files` for both) — our `PathClass` is already directory-shaped (`classify_dir` returns `None` unless `dir.kind == Kind::Dir`), so we have this by construction.

NEW — **overrides are whole-list replacements, not merges.** `WithFiles(s)` is literally `v.files = toMap(s)`. There is no "append one entry". **[INFERENCE]** this is the simplest possible extension semantics and it makes user configuration auditable (what you typed is exactly what runs), at the cost of forcing users to restate defaults. Our `PolicyConstraintsShape.deny_globs` is an additive list by contrast.

NEW — **no age dimension at all**: `prune.go` contains no `ModTime()` call in the match path. `dirStats(path)` re-walks solely to compute sizes.

### czkawka / Krokiet 12.0.2 — a compiled default list that the GUI edits at runtime

`czkawka_core/Cargo.toml`: `name = "czkawka_core"`, `version = "12.0.2"`, `license = "MIT"`. `krokiet/Cargo.toml`: `name = "krokiet"`, `version = "12.0.2"`, `license = "GPL-3.0-only"`. **License note carried forward from the field: the repo root has no `LICENSE` file** — `raw.githubusercontent.com/qarmin/czkawka/master/LICENSE` → **404**, `LICENSE_MIT` → **404**; the GitHub API reports `license.spdx_id = "NOASSERTION"` and the root holds `LICENSE_MIT_EVERYTHING_OUTSIDE_ANY_CARGO_APP_LIBRARY` + `LICENSE_CC_BY_4_ICONS`. The **per-crate `Cargo.toml` `license` fields are the authoritative evidence**, and they differ per crate — borrow `czkawka_core` (MIT), not `krokiet` (GPL-3.0-only). Default branch is `master`.

NEW — this is the only Rust project in the survey whose **rule list is compiled in *and* runtime-editable**:

- `czkawka_core/src/tools/temporary/mod.rs:1-60`: `pub const TEMP_EXTENSIONS: &[&str]` — 14 entries `#, thumbs.db, .bak, ~, .tmp, .temp, .ds_store, .crdownload, .part, .cache, .dmp, .download, .partial` — plus `pub const DEFAULT_TEMP_EXTENSIONS_STR: &str = "#,thumbs.db,.bak,~,.tmp,.temp,.ds_store,.crdownload,.part,.cache,.dmp,.download,.partial"`, whose doc comment reads "Used by UIs to pre-populate the extensions field and as the reset value". The parameters struct is `pub struct TemporaryParameters { /// Full list of extensions/suffixes treated as temporary files. … }`.
- `krokiet/src/settings/mod.rs` round-trips that list through user settings: line 592 `settings.set_temporary_files_sub_extensions(custom_settings.temporary_files_extensions.clone().into())`, line 802 read-back, line 927 in the defaults/export map.
- **NEW — the two constants have distinct jobs and this is the design to copy**: a typed default (`&[&str]`) for code, a serialized default string for UI pre-fill and reset, and a `Parameters` field that is the *live* value. Defaults are not mutated; the reset path re-derives from the string. **[INFERENCE]** our `path_class(&str)` match arms are the equivalent of `TEMP_EXTENSIONS`, and we have no equivalent of the other two.

NEW — the matching predicate is `ends_with`, not extension equality. `czkawka_core/src/tools/temporary/core.rs`: the name is lowercased via `to_ascii_lowercase()`, then `if !self.params.extensions.iter().any(|f| file_name_lowercase.ends_with(f.as_str())) { return None; }`. That is what lets `~`, `#`, and `.ds_store` behave as *suffixes* rather than extensions. Each surviving entry carries `modified_date: get_modified_time(&metadata, …)` and `size: metadata.len()` — the age is **recorded for display and never filtered on**. `check_files()` BFS-es `folders_to_check`; `check_folder_children()` honors `recursive_search`, `directories.is_excluded_dir`, `excluded_items.is_excluded`, and `#[cfg(target_family = "unix")] directories.exclude_other_filesystems()`. Empty list is a hard stop, not an empty result: `if self.params.extensions.is_empty() { critical = Some("No temporary file extensions defined. Add at least one extension to search for."); return WorkContinueStatus::Stop; }`.

Contrast worth recording: the sibling tool `czkawka_core/src/tools/bad_extensions` is a **rename-fixer**, not a cleaner — `fix_bad_extensions()` (`bad_extensions/core.rs:201-222`) computes `entry.path.with_extension(&entry.proper_extension)` and calls `std::fs::rename`, refusing when the target exists, and the source carries `const MAX_EXTENSION_LENGTH: usize = 10` with the comment "Text longer than 10 characters is not considered as extension". `bad_names` is likewise a renamer (`check_and_generate_new_name(path, checked_issues)`, `restricted_charset_allowed`, `deunicode` normalization). Both are *transform* rules, not *delete* rules, and neither has an age dimension.

### `pip cache purge` — no ruleset file at all; the rule is the command

`src/pip/_internal/commands/cache.py` (256 lines, read in full); version `__version__ = "26.3.dev0"` (`pip/__init__.py`); `LICENSE` = MIT, "Copyright (c) 2008-present The pip developers".

NEW — there is **no rule data structure**: `class CacheCommand(Command)` with `ignore_require_venv = True` and `handler_map = {dir: get_cache_dir, info: get_cache_info, list: list_cache_items, remove: remove_cache_items, purge: purge_cache}`. `purge_cache()` is one line: `remove_cache_items(options, ["*"])`. The wildcard is the rule.

`remove_cache_items` then carries all the policy: `files = self._find_wheels(options, args[0])`; `if args[0] == "*": files += self._find_http_files(options)`; then the delete loop is `bytes_removed += os.stat(filename).st_size; os.unlink(filename)` — **size is measured immediately before the unlink**, and reported at the end as `"Files removed: %s (%s)"` plus `"Directories removed: %s"`. Afterwards it prunes empty structure with `subdirs_without_files(_cache_dir(options,"http"))` and `…("http-v2")`, `subdirs_without_wheels(…, "wheels")` (each `rmdir`-ing, with an inner `file.unlink(missing_ok=True)`), and finally removes the legacy `selfcheck.json` with the in-tree comment "selfcheck.json is no longer used by pip." **No age dimension, no dry-run, no cost model, no preview.** The command *is* the configuration. The one thing worth noting architecturally: pip splits **location discovery** (`_cache_dir(options, …)`) from **selection** (the wheel-name/HTTP-file finders) from **destruction** (the unlink loop), and the `--dry-run` a user might want simply does not exist — the closest affordance is `pip cache list`. That is the low-water mark in this survey and the reason our `--min-bytes` + preview-before-confirm shape is unusual.

### `brew cleanup` — two independent age defaults and a **two-clock** staleness test

`Library/Homebrew/cleanup.rb` (1085 lines; **the default branch is `main` — `master` returns 404**); `LICENSE` = BSD 2-Clause "Copyright (c) 2009-present, Homebrew contributors". `03` lines 87–90 already cover `--prune=all` / `--prune=<days>` default 120 and `-n/--dry-run`. NEW:

- **NEW — the actual predicate is a conjunction of mtime AND ctime** (`cleanup.rb:55-69` `def prune?(pathname, days)`): `return false unless days`; `return true if days.zero?`; `return true if pathname.symlink? && !pathname.exist?` (a dangling symlink is always prunable); otherwise `days_ago = (DateTime.now - days).to_time; pathname.mtime < days_ago && pathname.ctime < days_ago`. **Both clocks must be old.** This is the single most transferable safety idea in the lane: `touch`ing a file (or restoring it from a backup, or copying it) bumps mtime but also ctime, so it is not a bypass; but a *metadata-only* operation that preserves mtime is caught by the ctime leg. **[INFERENCE]** our `Thresholds::hot_mtime` currently folds only `DirAgg.max_mtime`. A file whose mtime was set backwards (or whose directory was restored with preserved timestamps) reads as cold to us; adding a ctime leg would close that.
- **NEW — two different defaults for two different questions.** `cleanup.rb:22` `CLEANUP_DEFAULT_DAYS = T.let(Homebrew::EnvConfig.cleanup_periodic_full_days.to_i.freeze, Integer)` — from `env_config.rb:259-263` `HOMEBREW_CLEANUP_PERIODIC_FULL_DAYS`, description "If set, `brew install`, `brew upgrade` and `brew reinstall` will cleanup all formulae when this number of days has passed", **default 30**. `cleanup.rb:295` `@days = T.let(days || Homebrew::EnvConfig.cleanup_max_age_days.to_i, Integer)` — from `env_config.rb:255-258` `HOMEBREW_CLEANUP_MAX_AGE_DAYS`, "Cleanup all cached files older than this many days", **default 120**. `line 23` adds a third: `GH_ACTIONS_ARTIFACT_CLEANUP_DAYS = 3`, used at `line 74-82` `def stale?(entry, scrub: false)` for `:gh_actions_artifact`. So there are **three age classes** in one tool: 3 days (CI artifacts), 30 days (opportunistic cleanup during upgrades), 120 days (explicit cache cleanup), selected by *entry type*. `line 633` `logs_days = [days, CLEANUP_DEFAULT_DAYS].min` takes the stricter of two when cleaning logs.
- **NEW — staleness is decided by comparing a *cached artefact's version* against the *installed* version, not by time.** `cleanup.rb:159+` `stale_formula?` parses `pathname.basename` with `/\A.*(?:--.*?)*--(.*?)#{Regexp.escape(pathname.extname)}\Z/` and calls `Formulary.from_rack(HOMEBREW_CELLAR/formula_name)`; a download for a version that is no longer installed is stale regardless of age. `cleanup.rb:114` `cleanup_threshold = (DateTime.now - CLEANUP_DEFAULT_DAYS).to_time` applies only to cask `version.latest?` downloads. **Two rule kinds coexist**: version-identity rules (deleted immediately when outdated) and age rules (deleted only past a threshold).
- **NEW — same "*both* clocks, and a documented performance trap."** `formula_cache_paths` carries the in-tree comment that globbing per formula "rescans the entire cache each time, which is quadratic for `brew cleanup`, so index the cache by name prefix once instead" — it indexes by `path.basename.to_s.partition("--")`. Rule evaluation over a large cache is a hot loop; the index is part of the design.
- Cache *shape* is also data: `cleanup.rb:55-69` region includes `nested_cache?(pathname)` and `content_addressed_cache?(pathname)` (via `Homebrew::PackageManagerCache::DIRECTORIES` / `CONTENT_ADDRESSED_DIRECTORIES`) and `go_cache_directory?(pathname)` — the last with the comment "Go makes its cache contents read-only to ensure cache integrity, which makes sense but is something we need to undo for cleanup." **A cleaner that knows the cache is read-only by design, and says so in the rule.** That is the same class of fact as our `FlagBlock` evidence.

### Nix `store gc` / `nix-collect-garbage` — reachability, not classification

`src/libstore/gc.cc` (988 lines, read in full); `src/libstore/profiles.cc` (326 lines); `src/nix/store-gc.cc` (54), `src/nix/store-delete.cc` (69). Version **2.36.0** from `.version` on `master` (`version.json` → 404). License: **LGPL-2.1** ("GNU LESSER GENERAL PUBLIC LICENSE / Version 2.1, February 1999") — *not* GPL, which matters for borrowability.

Nix inverts the whole problem. There are no junk path names: `gc.cc:357` `void LocalStore::collectGarbage(const GCOptions & options, GCResults & results)`, `:361` `bool shouldDelete = options.action == GCOptions::gcDeleteDead || options.action == GCOptions::gcDeleteSpecific;`, and `:363` declares the three sets `roots`, `dead`, `alive`. Everything reachable from a root is alive; everything else is dead. **Regenerability is computed from the dependency graph, never declared in a rule table.**

NEW — the traversal's bail-out conditions are the safety model, and they are enforced *inside* the BFS (`gc.cc:596-660`). `markAlive(p)` inserts `p` and its whole filesystem closure (`computeFSClosure(p, closure, flipDirection=false, includeOutputs, includeDerivers)`). Then `while (auto path = pop(todo))` returns early — marking the *start* path alive — if the visited path is already `alive.contains(*path)` (with the log line "cannot delete '%s' because '%s' is alive"), or is in `roots` (log: "cannot delete '%s' because it's a root"), or is a temp root, or (under `SpecificPaths` without `deleteReferrers`) is not in the requested set. Death is only concluded after the entire reachable subgraph has been walked.

NEW — **the re-check immediately before deletion** is the pattern directly relevant to us (`gc.cc:716-750`). `if (!dead.insert(path).second) continue;` then, guarded by `shouldDelete`, a **second** `tempRoots.contains(hashPart)` test whose in-tree comment is verbatim: *"Re-check tempRoots before deleting and set pending to synchronise with addTempRoot. Between the BFS and this deletion loop, new temproots may have been added via the GC socket by a concurrent process (e.g. an evaluator calling addTempRoot). The BFS only checks tempRoots when it first visits a path, but the 'pending' mechanism only blocks the socket handler for the single path currently being visited, not for paths already queued for deletion."* On a hit, `debug("not deleting '%s' because it became a temporary root after initial scan", …)`, `markAlive(path)`, `continue`. Then `invalidatePathChecked(path)`, `deleteFromStore(path.to_string(), true)`, `referrersCache.erase(path)`, with a `catch (PathInUse & e)` that prints `"BUG: …"` rather than proceeding. **Deciding and deleting are separated in time, and the decision is re-validated at the moment of the mutation.** Our `plan.rs::decide` → `Executor::apply` split has the same time gap; our TOCTOU armor is `apply` re-probing flags, but we do **not** re-check the mtime/lock evidence that produced the verdict.

NEW — root sources (`gc.cc:293-313`): `findRootsNoTemp` = `findRoots(stateDir/gcRootsDir, …)` + `findRoots(stateDir/"profiles", …)` + `findRuntimeRoots(roots, censor)`; `findRoots(censor)` = that plus `findTempRoots`. `findRuntimeRoots` is notable: it is a **socket-fetched set** — `requestRuntimeRoots(config, socketPath)` (`:315-329`) connects to `gcSocketPath` and reads NUL-delimited lines, i.e. running processes *push* their live roots to the collector. `addIndirectRoot` (`:47-50`) canonicalizes `stateDir/gcroots/auto/<hash>`. **Roots are a live, externally-fed set, not a static list** — the maximal version of "don't delete what something is currently using".

NEW — generations carry a creation time and the deletion rules differ in how much they keep. `profiles.cc:42` `gens.push_back({.number = *n, .path = path, .creationTime = lstat(path).st_mtime});` — the **mtime of the generation directory is the creation time**. `profiles.cc:175-184` `deleteOldGenerations(profile, dryRun)` deletes every generation except `curGen`, with **no age criterion**. `profiles.cc:186-213` `deleteGenerationsOlderThan(profile, time_t t, dryRun)` uses `older = [&](auto & g) { return g.creationTime < t; }`, finds the first older generation, then `++i` — explicitly **keeping one older generation as a rollback point**, and asserting monotonic creation times. `profiles.cc:218-231` `parseOlderThanTimeSpec` requires a trailing `'d'` and `days >= 1`, returning `time(nullptr) - days*24*3600`. So Nix encodes reversibility *in the selection rule*: never delete the last-applicable fallback. **Our `plan.rs::decide` does the analogous thing with `quarantine_entries > 0 // keep ≥1 entry`** — target-bytes can be reached but never at the cost of the last selected entry.

NEW — budget knobs, both verified. `src/nix/store-gc.cc`: `struct CmdStoreGC : StoreCommand, MixDryRun` with flag `--max` — description "Stop after freeing *n* bytes of disk space. Cannot be combined with --dry-run.", `handler = {&options.maxFreed}`; `run()` throws `UsageError("options --max and --dry-run cannot be combined")`, sets `options.action = dryRun ? GCOptions::gcReturnDead : GCOptions::gcDeleteDead; options.pathsToDelete = GCOptions::WholeStore{};` and registers as `{"store","gc"}`. The budget is enforced inside the deletion loop (`gc.cc:564-570`): `deleteStorePath(realPath, bytesFreed, isKnownPath); results.bytesFreed += bytesFreed; if (results.bytesFreed > options.maxFreed) { printInfo("deleted more than %d bytes; stopping", options.maxFreed); … }` — an **overshoot-allowed, stop-after-crossing check**, evaluated per deleted path. `gc.cc:963` shows auto-GC computing `options.maxFreed = gcSettings.maxFree - avail` from a free-space floor — the same "target bytes" idea. `src/nix/store-delete.cc`: `GCOptions options{.action = GCOptions::gcDeleteSpecific};` with flags `--ignore-liveness`, `--skip-alive/--skip-live` (which flips the action to `gcDeleteDead`), `--also-referrers`; registered `{"store","delete"}`.

**What this comparison establishes.** No tool in the survey encodes regeneration cost as data, and none computes regenerability from evidence the way we do — but **two** of them (kondo, cargo-sweep) put an age gate in the *rule evaluation path*, and **one** (brew) hardens it with a second clock. Our `classify.rs::grade_for` / `regen_for` pair, fed by `EvidenceKind` at `Strength` levels, is the only evidence-graded design here; the borrowable parts are therefore *behavioural*, not structural. In our terms: BleachBit's `search`×`command` split maps onto our **evidence** (`classify_dir` emitting `Evidence`) vs **action** (`plan.rs::decide` choosing `PlanAction`), and its `<var>` table maps onto our ancestor probe (`classify::probe_ancestry` / `classify/macos.rs::probe_ancestry`) — both are separation-of-concerns precedents, not formats to adopt.

**One clear recommendation.** **Externalize nothing: the ruleset stays compiled Rust.** Every candidate format is strictly worse for our situation — BleachBit's XML is GPL-3.0 and age-blind, so we could borrow neither its files nor its semantics; a TOML ruleset would add a parser, a schema, and a validation story we would have to maintain and test, while the one thing it buys (user-added paths) is already served by `PolicyConstraintsShape::deny_globs` for subtraction; and `czkawka_core` proves the runtime-editable-list pattern is worth having only when a GUI settings pane exists to edit it, which is exactly the one case we can satisfy more cheaply — our `path_class()` arms are 20 lines of `match`. The four borrowings worth making are **behavioural**: (1) BleachBit's rule = **scope × action** split, which we already honour (`evidence` vs `PlanAction`) and should keep honest by never letting a rule express an action directly; (2) czkawka's **default-const + serialized-default-string + live-parameters-field** triple, mapped onto a `--extra-class-suffix` CLI override surface for `path_class()`; (3) docker's **dry-run that returns the confirmation string**, mapped onto the Tauri preview so the preview cannot drift from the mutation; (4) brew's **mtime ∧ ctime** two-clock test, mapped onto `Thresholds::hot_mtime`.

## Risks & open questions

1. **No surveyed tool encodes regeneration cost, so `Regen { command, cost_secs, network }` has no precedent to copy.** The nearest analogue is npkill `main`'s `PROFILE.description` — free prose ("Regenerated on the next `next dev` or `next build`") that no code reads. Our `cost_secs: Option<u32>` makes explicit what every other tool leaves to the user's judgement, which is the right call but means **we cannot validate our cost numbers against anyone else's**. The design document should present this as a deliberate original contribution, not as an industry-standard field.

2. **Our `Refusal::MtimeHot` reasoning rests on a single clock.** `Thresholds::hot_mtime` (600 s) folds `DirAgg.max_mtime` only. Homebrew's `prune?` shows a production-grade tool insisting on two clocks. Until backlog item 2 lands, a path whose mtime was set backwards (or preserved by a copy tool) reads as "cold" when its ctime says otherwise. This is the one place where a *surveyed* tool is stricter than we are.

3. **The `.npkillrc` drift is a general warning about rule architectures outrunning releases.** The GitHub `main` branch of npkill is version-labelled `0.12.2` while containing a profile system, a config-file layer, a validator, and a rewritten safety gate that the published `0.12.2` tarball does not have. Anyone citing "npkill supports user profiles" from the repository would be describing software no user can install. **Open question for our own repo:** if our ruleset ever diverges from a released binary, how do we keep the design document's claims tied to the artifact a reader can actually run? [INFERENCE] The safe practice is to cite a tag or a published artifact, never a branch head — which is why this note names the tarball for npkill and `main` explicitly where `main` is the only source.

4. **Licence borrowability is not uniform across a single project.** czkawka's two crates are MIT (`czkawka_core`) and GPL-3.0-only (`krokiet`), and the repo root carries *neither* a `LICENSE` nor a `LICENSE_MIT` file (both `raw.githubusercontent.com` fetches returned 404; the GitHub API reported `spdx_id = "NOASSERTION"`). Nix is LGPL-2.1, not the GPL a reader might assume from "Nix is GPL". BleachBit is GPL-3.0 throughout. **Any borrowing must be checked per-file, per-crate, per-project** — the per-crate `Cargo.toml` `license` field is the authoritative evidence, and this note cites it rather than the repository root.

5. **XML crates would only matter if the recommendation were reversed.** `roxmltree` and `quick-xml` are recorded as evaluation-only; with "externalize nothing", neither should enter `Cargo.toml`. If a future reviewer argues for a data-file ruleset, the counter-arguments are already assembled: a parser plus a schema plus a validator plus a merge policy plus a listing UI (the full `.npkillrc` surface, roughly four files and three failure modes in npkill `main`), in exchange for user-added paths that `PolicyConstraintsShape::deny_globs` already provides subtractively.

6. **The `--max` × `--dry-run` incompatibility is a product decision we have not made.** Nix refuses the combination outright (`UsageError("options --max and --dry-run cannot be combined")`); Docker's dry-run *computes a byte total* and is perfectly compatible with `--keep-storage`. We currently have `target_bytes` (a free budget) and a preview step that reports numbers, so our behaviour is Docker-like. **Open question:** should `janitor plan --target-bytes N --dry-run` be legal? Our answer should be stated, not inherited.

7. **[INFERENCE] The survey's age signals are mutually contradictory, which is itself the finding.** kondo max-folds mtime ("is anyone still working here"), cargo-sweep min-folds atime ("has this artifact gone cold"), brew conjoins mtime ∧ ctime, npkill max-folds mtime but only for sorting, and czkawka records mtime without ever filtering. There is no consensus to copy — so our `max_mtime` choice must be defended on our own terms (it answers "is this project alive", which is exactly what the MTA policy 「别动我这两周在跑的项目」 needs), not by appeal to precedent.
