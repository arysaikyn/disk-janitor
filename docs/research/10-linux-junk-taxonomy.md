# Linux-Junk Taxonomy — Research Note

Canonical taxonomy of Linux-machine disk junk: system half (package-manager caches, journal,
`/boot`, `/tmp`) + user half (`~/.cache`, Flatpak/Snap, container engines, dev caches).
Per path: official clean/regen command, risk tier (SPEC §3 grades PureCache / RebuildableFromSource /
Redownloadable / Expensive / HandsOff ≡ safe / rebuildable / re-downloadable / expensive / hands-off),
and distinguishing evidence. · researched 2026-08-30

## Findings

### 0. Cross-cutting evidence signals (Linux deltas feeding classify/)

Signals 1–7 of note 03 §0 (lockfile, orphan manifests, mtime, file locks, git, CAS stores,
hardlinks) carry over unchanged. Linux adds:

| Signal | How to read it | Verdict impact |
|---|---|---|
| **Privilege boundary** | path under `/var/*`, `/boot/*`, `/var/lib/*` ⇒ root-owned; `$XDG_CACHE_HOME` etc. ⇒ user-owned | root paths can never be silently moved/purged; plan/ must route through a privileged helper (sudo/polkit) or mark action as `requires-elevation` in the manifest [S1][S2] |
| **Package-manager ownership** | `pacman -Qo <file>` / `dpkg -S <file>` answers "who owns this" | owned files under `/usr`, `/etc` are NOT junk even if stale; unowned files there are `lostfiles` candidates surfaced for review, never auto-deleted [S5][S6] |
| **Distros already schedule cleanup** | `paccache.timer` (weekly, keeps 3), `systemd-tmpfiles-clean` (aging per `tmpfiles.d`), journald `SystemMaxUse` (10% of fs, cap 4G) | scanner must READ existing policy before proposing; a cache already governed by an official timer is either untouched or delegated to that command — re-implementing risks fighting the distro [S3][S12][S24] |
| **`CACHEDIR.TAG` marker** | cache dirs marked per the Cache Directory Tagging spec (Gradle marks `caches`, `wrapper/dists`, `daemon`, `jdks`) | strong "this subtree is cache" prior for backup-exclusion and scan pruning; not a verdict by itself [S28] |
| **FS matrix for atomicity** | `renameat2(RENAME_NOREPLACE)` support: ext4 ≥3.15, btrfs/tmpfs ≥3.17, xfs ≥4.0, many more ≥4.9; `EXDEV` across mounts | quarantine same-volume rule (SPEC §7) now has a *kernel/FS* dimension, not just same-`st_dev`; scan must resolve the mount of every candidate [S26] |
| **Sparse images (containers)** | Docker Desktop `Docker.raw`; `st_blocks·512` (allocated) ≪ `st_size` (apparent, e.g. 64G) | freed-byte accounting must use allocated size; never delete the image file itself [S18] |

### 1. Debian/Ubuntu — apt family

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/cache/apt/archives/*.deb` (+`partial/`) | downloaded .deb pool | `apt-get clean` "removes everything but the lock file"; `apt-get autoclean` only removes files "that can no longer be downloaded" (keeps reinstall-able ones); re-download on next install | PureCache (safe) | root-owned; `clean` clears both `archives/` and `archives/partial/` [S1] |
| `/var/lib/apt/lists/` | repo metadata (`Packages.gz` etc.) | `apt-get update` re-fetches (network, MBs) — or `apt-get distclean` removes all but `Release*` for image finalization | Redownloadable | regenerated by every `update` [S1] |
| `/var/lib/dnf` n/a — apt counterpart `/var/lib/apt` | transaction state, not cache | none | HandsOff | package DB; loss breaks dpkg/apt [S1] |

`apt-get autoremove` removes "packages that were automatically installed to satisfy dependencies …
now no longer needed"; `apt-get autopurge` = autoremove + config purge. apt(8) explicitly warns:
check the list, `apt-mark manual` to keep a liked orphan [S1]. Verdict engine should *invoke*
autoremove (it is transactional & dependency-aware) rather than compute orphans itself.

### 2. Fedora/RHEL — dnf family

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/cache/dnf/` (per-repo `packages/`, metadata, `dbcache`) | downloaded RPMs + repo metadata | `dnf clean packages` (cached RPMs), `dnf clean metadata` (forces full metadata re-download), `dnf clean dbcache`, `dnf clean all`; re-download on next transaction | PureCache (safe) | dnf4 docs: "Cache Files /var/cache/dnf"; dnf5 `clean` has same types [S7][S9] |
| `~/.cache/libdnf5` | per-user DNF5 cache (non-root runs) | same `dnf5 clean` targets | PureCache | regular-user `cachedir` default [S10] |
| `installonly` kernels | see §6 | — | HandsOff | `installonlypkgs` never auto-removed by autoremove [S8][S10] |

`dnf autoremove` removes leaf packages installed as deps no longer required; "Installonly packages
(e.g. kernels) are never automatically removed" [S8]. `installonly_limit` default **3**, minimum **2**
("1 is explicitly not allowed since it complicates kernel upgrades due to protection of the running
kernel"), 0 = unlimited — this is the official knob for how many kernels live in `/boot` [S10].

### 3. Arch — pacman family

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/cache/pacman/pkg/*.pkg.tar.zst` | downloaded package pool, **kept forever** — pacman "does not remove the old or uninstalled versions automatically" | `paccache -r` (default keep 3; `-rk1` keep 1; `-ruk0` purge uninstalled); `pacman -Sc` remove uninstalled-only + unused sync DBs; `pacman -Scc` wipe all (Arch Wiki warns: kills downgrade/reinstall-without-download ability) | PureCache (safe) — but `-Scc` is the aggressive mode worth gating | cache is also the local fallback for downgrades; `CacheDir` configurable in pacman.conf, must not be a symlink (breaks pacman self-upgrade) [S2][S3][S4] |
| `/var/cache/pacman/pkg/*.part` | partial downloads | `find … -iname "*.part" -delete` (Arch's own remediation for corrupted-download errors) | PureCache | zero-cost regen [S4] |
| `paccache.timer` | weekly systemd timer (pacman-contrib) keeps default `-r` | enable instead of manual cleaning | — | official policy already exists [S3] |

`paccache` also supports `--min-atime/--min-mtime` retention and a dry-run `-d` — the model CLI for
"versioned cache pruning" semantics we mirror in plan/ [S3].

### 4. Systemd journal

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/log/journal/` (persistent, default `Storage=persistent`) or `/run/log/journal/` (volatile) | structured binary journal files (`.journal`/`.journal~`) | `journalctl --vacuum-size=<N>` removes oldest **archived** files until below size; `--vacuum-time=` age cut; `--vacuum-files=` count cut; combine with `--rotate` to archive active files first. `journalctl --disk-usage` reports the number to show | PureCache (safe) — logs, not user data; but active files are never removed by vacuum | journald self-caps: `SystemMaxUse`/`RuntimeMaxUse` default 10% of the fs, `SystemKeepFree` 15%, both capped 4G — so an untuned system rarely exceeds ~10% anyway [S11][S12] |

Key subtlety for the verdict engine: `--vacuum-size` "has only an indirect effect on the output shown
by `--disk-usage`, as the latter includes active journal files while the vacuuming operation only
operates on archived journal files" [S11] — predicted-freed bytes must therefore be estimated from
*archived* file sizes only, and the engine must *invoke* journalctl rather than unlink `.journal`
files (journald owns them; WAL-style corruption risk if deleted underneath the daemon).

### 5. `/tmp`, `/var/tmp`, and `~/.cache` (XDG)

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/tmp` | often a tmpfs mount — "the default is half of your physical RAM" (`size=50%`), may swap; contents vanish on unmount/reboot | `systemd-tmpfiles --clean` per `tmpfiles.d` aging rules; no regen concept — recreation on demand | PureCache (safe) — but see caveat | if tmpfs, "everything stored therein is lost" on unmount and bytes never hit disk at all ⇒ freed-byte accounting is 0 even though `du` shows size; kernel docs also warn oversizing tmpfs deadlocks via OOM [S13] |
| `/var/tmp` | large/persistent tmp (survives reboots, distros clean aged files, e.g. `d /var/tmp 1777 root root 30d`) | `systemd-tmpfiles --clean`; per-dir Age from `/usr/lib/tmpfiles.d/*.conf` (vendor) overridable in `/etc/tmpfiles.d/` | PureCache (safe) with per-dir policy read | cleanup rules live in vendor `tmpfiles.d` (e.g. `d /run/screens 1777 root screen 10d`); read them rather than hard-coding an age [S14] |
| `$XDG_CACHE_HOME` default `$HOME/.cache` | spec-defined "user-specific non-essential (cached) data" | no global clean command — per-app semantics apply | PureCache *in intent* (XDG prior), actual tier = per-child-app rule | same conclusion as note 03 §8: the XDG definition is a prior, not a verdict; mtime<10-min rule still gates [S15] |

XDG also matters for *where* Linux dev caches live: pip `~/.cache/pip` (respects `XDG_CACHE_HOME`,
cache layout is an implementation detail, `http-v2` format since pip 23.3; `pip cache purge/remove`),
uv `$XDG_CACHE_HOME/uv` or `$HOME/.cache/uv` (buckets, hardlinks into venvs — same-volume rule;
"it is *never* safe to modify the cache directly", only `uv cache clean/prune`), npm `~/.npm`
(`_cacache`, self-healing, never GC'd by npm itself; `npm cache clean --force` / `npm cache verify`),
Go `$HOME/.cache/go-build` build cache ("safe for concurrent invocations", periodically prunes
unused data) and module cache `$GOPATH/pkg/mod` (read-only dirs ⇒ `go clean -modcache` is "usually
the best way to remove" it — `rm -rf` fails on the 0500 permission trick; "no maximum size, and the
go command does not remove its contents automatically") [S16][S17][S21][S22]. The macOS mirrors
(`~/Library/Caches/…`) of note 03 map 1:1 onto these `.cache` paths on Linux.

### 6. Old kernels in `/boot` — HandsOff

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/boot/vmlinuz-<ver>`, `initramfs-<ver>.img`, module trees `/usr/lib/modules/<ver>/` | bootable kernel versions; boot loader "needs access to the kernel and initramfs" to boot at all | none for a janitor tool — removal goes through the *package manager* (`apt purge linux-image-…`, `dnf remove kernel-<ver>`, `pacman -R linux-lts`) or the `installonly_limit` knob, never file-level deletion | **HandsOff**: deleting the running kernel's files or the only fallback bricks the boot path; dnf5 docs: limit "1 is explicitly not allowed … protection of the running kernel from removal" | Arch boot docs: loader must load kernel+initramfs from `/boot`; installonly semantics per distro [S2][S8][S10][S25] |

Policy: Disk Janitor *surfaces* the `/boot` usage figure and the distro tool command that would
reclaim it (`installonly_limit=2` in dnf.conf etc.), but never proposes a file move under `/boot` or
`/usr/lib/modules`. Also flags root-owned `/boot` ⇒ privilege boundary applies.

### 7. Orphaned packages

| Mechanism | What it finds | Official command | Tier | Evidence |
|---|---|---|---|---|
| apt orphans | auto-installed, no longer needed | `apt-get autoremove [-s]` (simulate first), `autopurge` for configs; user must sanity-check list, `apt-mark manual` keeps an item | Rebuildable→package action (not file quarantine) | apt(8) explicitly warns to check the list [S1] |
| dnf orphans | leaf packages installed as deps | `dnf autoremove`; installonly (kernels) excluded by design | same | [S8] |
| pacman true orphans | deps no longer required by any installed package | `pacman -Qtdq` to list (arch Wiki's canonical detect); `pacman -Qdtq \| pacman -Rns -` to remove recursively w/ configs; `-Qdtt` includes optional-deps; empty stdin is expected when none | same | `-Rns` may drop optional deps of kept packages — Wiki suggests `-Rn` loop variant to avoid that [S5][S6] |

### 8. Flatpak & Snap

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/lib/flatpak` (system) / `$HOME/.local/share/flatpak` (user): `repo/` (OSTree), `app/`, `runtime/` | OSTree checkouts of apps+runtimes; uninstalling "removes the ref … and purges any objects no longer needed"; reinstall "pulls from the remote repository again" | `flatpak uninstall --unused` removes "unused refs on the system" (docs: runtimes/extensions not used by installed apps); `flatpak repair` prunes invalid objects + re-installs deployed refs (needs root for system install); `flatpak uninstall --delete-data` also clears `~/.var/app/<id>` | Redownloadable (runtimes are multi-GB network re-pulls ⇒ treat size warnings seriously); `repo/` itself = HandsOff as a file tree | per-user installs also exist ⇒ scan must enumerate installations (`/etc/flatpak/installations.d/`); `--unused` is the official janitor verb [S23][S24] |
| `~/.var/app/<app-id>/` | per-app writable home (config+data) created when sandboxed app runs | `flatpak uninstall --delete-data` (or per-app) — "unowned" app data also removable with `--delete-data` and no ref | HandsOff (user data) | not a cache; contents may be user documents [S23] |
| `/var/lib/snapd/snaps/*.snap` | SquashFS revision archives — `refresh.retain` (2–20, default 3 on Ubuntu Core, 2 on classic) governs how many revisions are kept | none — snapd GCs old revisions automatically per `refresh.retain` (`sudo snap set system refresh.retain=3` is the official knob); re-download via `snap refresh` if a revision is gone | Redownloadable | canonical docs; `snap remove <snap> --purge` skips the data snapshot [S20][S25] |
| `/var/lib/snapd/cache` | snapd working cache "to minimise download size and speed-up refreshes" | none documented — snapd manages | PureCache | snapd-owned; do not unlink [S25] |
| `/var/lib/snapd/snapshots/` + `~/snap/<name>` | user/system data snapshots; auto-created on snap removal, retained 31 days (Ubuntu Core: disabled by default) | `snap forget <set-id>` deletes; `snapshots.automatic.retention` knob (value > 24h, or `no` to disable) | PureCache (auto snapshots) — but `forget` is irreversible; surfaces as reclaimable-with-confirm | retention knob is the official policy point; deletion of `~/snap/<name>` data on remove is automatic, snapshot survives 31d [S25] |

### 9. Docker & Podman (rootful `/var/lib/docker`, rootless XDG)

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| `/var/lib/docker/` (daemon `--data-root` default) | overlay2 layers, containers, volumes, build cache — the engine's *whole persistent state* | `docker system prune` (stopped containers, unused networks, dangling images, unused build cache; `-a` for all unused images; `--volumes` only for *anonymous* volumes; `until=`/`label=` filters); `docker system df [-v]` is the sizing verb | **HandsOff as a filesystem tree** — everything is delegated to docker verbs: images re-pull (GB, network), but *containers with writable layers and named volumes are not regenerable* | dockerd reference fixes the path; prune semantics documented per-flag; privileged helper required (root/docker group) [S18][S19] |
| `$XDG_DATA_HOME/containers/storage` rootless default (`$HOME/.local/share/containers/storage`), rootful `/var/lib/containers/storage` | podman/buildah/cri-o graphroot (overlay/vfs/btrfs/zfs) | `podman system prune [--all] [--volumes] [--build] [--filter until=|label=]`; `podman system df` reports RECLAIMABLE (docs note it "can be incorrect" when images share layers — matches our hardlink discount problem) | HandsOff as tree; same verb-delegation rule; rootless paths are user-owned but *contain* container state = not junk | containers-storage.conf(5) defines `graphroot`, `rootless_storage_path`, `runroot /run/containers/storage`; prune warns `--build` "is not safe … can interfere with builds in progress" — an mtime/active-build check must gate it [S27][S29] |

Both engines are the strongest Linux argument for the SPEC design: the only *safe* reclaim path is
the engine's own transactional command with typed confirm, run through the plan manifest — a
quarantine-move of `/var/lib/docker` would corrupt the DB while the daemon runs.

### 10. distrobox / toolbox (containers sharing `$HOME`)

| Path | What it is | Official regen/clean + cost | Tier | Evidence |
|---|---|---|---|---|
| container root + host `$HOME` bind | distrobox mounts the host home *into* the box; "the `--home` flag … will NOT prevent the mount of the host's home directory, but will ensure that configs and dotfiles will not litter it" | `distrobox rm [--force] [--all]` recreates via `distrobox create` (image pull, minutes) | HandsOff for anything under `$HOME` seen *from the host* (it's the user's real home, not junk); container-only state = `distrobox rm` action | host-side scan cannot distinguish "file written by distrobox guest" from "user file" ⇒ both converge on: never auto-act inside `$HOME` [S30][S31] |
| `DBX_CONTAINER_HOME_PREFIX` boxes' own homes (e.g. `~/dbx/<name>`) | per-box custom HOME | `distrobox rm --rm-home` deletes the mounted home when it differs from the host's | RebuildableFromSource (recreate box) — but may contain guest-side project state | `--rm-home` is explicit, non-default ⇒ mirror that gating [S30] |

Practical verdict: for distrobox/toolbox the only safe Linux-native behavior is to *detect* the
boxes (`distrobox list`) and offer `distrobox rm` as a plan action; host-path classification inside
their mounts is out of scope by design (privacy invariant also applies).

## Platform delta vs macOS

Carries over unchanged from note 03 / SPEC:

- Core loop scan → classify → plan → apply (atomic quarantine move) → purge → restore, with the
  SPEC tier vocabulary mapping 1:1 (PureCache = safe, RebuildableFromSource = rebuildable,
  Redownloadable = re-downloadable, Expensive = expensive, HandsOff = hands-off).
- Evidence signals 1–7 of note 03 §0 (lockfile, orphan manifests, mtime, file locks, git, CAS
  stores, hardlinks) apply as-is; the macOS mirrors (`~/Library/Caches/…` of note 03) map 1:1 onto
  these `.cache` paths on Linux (pip, uv, npm, Go).
- Hardlink discounting and the same-volume quarantine rule (SPEC §7) — but see the FS-matrix delta
  below for the Linux kernel/FS dimension.

Must be re-implemented for Linux:

- Privilege boundary: root-owned paths (`/var/*`, `/boot/*`, `/var/lib/*`) can never be silently
  moved/purged — plan/ must route through a privileged helper (sudo/polkit) or mark the action
  `requires-elevation` in the manifest [S1][S2].
- Ownership checks: `pacman -Qo <file>` / `dpkg -S <file>` gate every verdict under `/usr`, `/etc`;
  unowned files there are `lostfiles` review candidates, never auto-deleted [S5][S6].
- Policy reading: distros schedule cleanup already (`paccache.timer`, `systemd-tmpfiles-clean` per
  `tmpfiles.d`, journald `SystemMaxUse`) — the scanner must read existing policy and delegate
  instead of re-implementing it [S3][S12][S14].
- Verb delegation: the engine *invokes* transactional commands (`apt-get autoremove`,
  `journalctl --vacuum-*`, `docker/podman system prune`, `flatpak uninstall --unused`) rather than
  computing orphans itself or unlinking engine-owned files [S1][S11][S19][S23].
- Freed-byte accounting: allocated size (`st_blocks·512`), never apparent `st_size` (sparse
  `Docker.raw`-style images); tmpfs-backed `/tmp` contributes 0 reclaimable bytes even when `du`
  shows size [S13][S18].
- FS-aware atomicity: `renameat2(RENAME_NOREPLACE)` support is a kernel/FS matrix (ext4 ≥3.15,
  btrfs/tmpfs ≥3.17, xfs ≥4.0, many more ≥4.9); `EXDEV` across mounts — scan must resolve the
  mount of every candidate, not just compare `st_dev` [S26].
- Distro-family enumeration: apt / dnf(+dnf5) / pacman differ in cache paths, clean verbs, and
  orphan semantics; Flatpak needs per-installation enumeration (`/etc/flatpak/installations.d/`)
  [S7][S9][S10][S23][S24].

Impossible on Linux (no macOS-equivalent workaround):

- File-level quarantine of engine state dirs (`/var/lib/docker`, `/var/lib/containers/storage`):
  a quarantine-move corrupts the DB while the daemon runs — only the engine's own transactional
  verbs are safe, run through the plan manifest with typed confirm [S18][S19][S27][S29].
- File-level moves under `/boot` or `/usr/lib/modules`: deleting the running kernel's files or the
  only fallback bricks the boot path; only distro package-manager verbs apply (`installonly_limit`,
  `apt purge linux-image-…`, `dnf remove kernel-<ver>`, `pacman -R linux-lts`) — Disk Janitor
  surfaces the usage figure and the command, never acts [S2][S8][S10][S25].
- Distrobox/toolbox guest-vs-user file attribution inside a shared `$HOME` is impossible from the
  host — host-path classification inside their mounts is out of scope by design (privacy invariant
  also applies) [S30][S31].

## Risks & open questions

- **Privilege elevation UX is unresolved**: every root-half path (`/var/cache/*`, `/var/log/journal`,
  `/var/lib/snapd`) needs sudo/polkit; the manifest format for `requires-elevation` actions and the
  privileged-helper protocol (SPEC §7 neighbor) are not yet designed [S1][S2].
- **Distro-matrix breadth**: apt / dnf4 / dnf5 / pacman differ in cache layout, clean verbs, and
  orphan semantics; the note covers the big three families but not zypper, apk, portage, nix —
  scanner needs a per-family plug-in shape rather than hard-coded paths [S1][S7][S9][S10][S2].
- **dnf4 vs dnf5 coexistence**: both CLI families are live in Fedora/RHEL; `~/.cache/libdnf5`
  appears for non-root runs; commands must be probed at runtime, not assumed [S7][S9][S10].
- **`journalctl --vacuum-size` underestimates freed bytes** (active files are never vacuumed);
  predicted-freed must be estimated from *archived* file sizes only, and the engine must invoke
  journalctl — never unlink `.journal` files under the daemon [S11].
- **Podman `system df` RECLAIMABLE can be incorrect** when images share layers (official docs) —
  the same hardlink-discount problem as macOS; do not trust engine-reported reclaimable numbers
  for typed confirms without a local re-count [S29].
- **`podman system prune --build` is officially "not safe" mid-build** — an mtime/active-build
  gate must precede it; the same gate likely applies to docker's build-cache prune [S27].
- **Snap snapshot `forget` is irreversible** and auto-snapshots are created silently on removal —
  surface as reclaimable-with-confirm only; retention defaults differ per image (31 days; disabled
  by default on Ubuntu Core) [S25].
- **distrobox `--rm-home` deletes a whole custom home** (`~/dbx/<name>`) — must remain explicit,
  non-default, and typed-confirm like the upstream flag [S30].
- **Arch pacman cache is the downgrade fallback**: aggressive `-Scc` kills the ability to
  downgrade or reinstall without re-download; default plan actions should mirror `paccache -r`
  (keep 3), not `-Scc` [S2][S3][S4].
- **Flatpak per-user vs system installs** both exist; scan must enumerate installations
  (`/etc/flatpak/installations.d/`) before proposing `--unused` anywhere [S23].
- **Unverified in salvage**: dnf5-specific clean verb coverage vs dnf4 for `dbcache`/`metadata`
  types is recorded from both doc families ([S7][S9]), but the combined behavior on a system with
  both installed is untested — flag for a live-matrix QA pass.
