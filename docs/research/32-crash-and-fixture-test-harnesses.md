### 1. tigerbeetle — VOPR: deterministic simulation + a doctrine for *how much* to inject

The headline claim is not the framework, it is the **fault budget doctrine**, written at the top of `src/testing/storage.zig`:

> `//! In-memory storage, with simulated faults and latency.` … `//! Storage injects faults that a fully-connected cluster can (i.e. should be able to) recover from.` … `//! - superblock: One read/write fault is permitted per area (section, free set, …). An additional fault is permitted at the target of a pending write during a crash.`

The transferable rule: **inject only faults your recovery path is contractually required to survive, and cap them per area.** Our SPEC §5.2 contract is narrower than a cluster's (quarantine exists ⇒ roll forward; intent without result and nothing moved ⇒ drop the tail), so the analogue is: at most one torn line, at most one missing rename, never both for the same entry. Without this cap a simulator produces unrecoverable states and the test becomes a generator of false positives.

Mechanics worth naming: `Options` carries `read_fault_probability`, `write_fault_probability: Ratio`, `crash_fault_probability`, and `fault_atlas: ?*const ClusterFaultAtlas`; the fault bitmap is `faults: std.DynamicBitSetUnmanaged`, one bit per sector. `memory` is documented as "always contains the pristine data as-written — it does not include storage faults", i.e. the simulator keeps a clean reference image separate from the faulted one — the same trick redb's `CrashState.durable` and SQLite's real file under the write-list both use. On a write with a crash fault, the simulator calls `storage.fault_sector(write.zone, sectors.random(&storage.prng))`. Replica restarts disable faulting (`storage.faulty = false`) for the first startup so that "did we break recovery" is not confused with "did we break boot".

Swarm testing is named explicitly in `src/testing/fuzz.zig`: `random_enum_weights()` — *"This is swarm testing: some variants are disabled completely, and the rest have wildly different probabilities."* This is the cheapest idea in the whole note: for a struct/enum with N variants, most normalised-random generators waste runs on combinations that a user never hits; swarm sampling zeroes a random subset per run so the *rare* configuration gets tested properly.

VOPR's own scheduling constants are also instructive: `replica_crash_probability = ratio(2, 10_000_000)`, `replica_crash_stability = prng.int_inclusive(u32, 1_000)`, `crash_fault_probability = ratio(80..100, 100)`. Crashes are *rare but habitual*, and once a replica crashes it stays down for a while — the opposite of a naive uniform sampler that crashes every step. **[INFERENCE]** the stability window exists so the system is exercised in its crashed state, not just across the transition into it.

**NEW vs 08:** 08 covers durability syscalls; VOPR's contribution here is the *fault budget doctrine* and *swarm sampling*, neither of which appears anywhere in 01–21.

### 2. cberner/redb — the trait-object crash backend (highest-value borrowable pattern)

`tests/crash_consistency.rs` is a regression test for a real, documented data-loss bug: `grow()` extended the file with `set_len` and a later commit wrote the grown layout into the header shared by both commit slots; if the header persisted but the extension did not, every subsequent open failed `Corrupted("File truncated below stored layout")` — permanent loss, despite the previous durable state being intact.

The mechanism is the key part, and it is *not* a kill point:

```rust
struct CrashState {
    live: Vec<u8>,          // every write is applied here immediately
    durable: Vec<u8>,       // contents made durable by a completed sync
    last_header: Vec<u8>,   // most recent write to offset 0 (reaches page cache even when sync doesn't complete)
    syncs: u64,
    freeze_from: Option<u64>, // once syncs reaches this, syncs stop advancing durable
}
```

`impl StorageBackend for CrashBackend` overrides `len`, `read`, `set_len`, `sync_data`, `write`. `sync_data()` increments `syncs` and, only while `state.syncs < freeze_from`, copies `live` into `durable`. `write()` records offset-0 writes into `last_header`. `crash_image()` then returns *"everything durable, with the header write overlaid (it reached the page cache) but the file length and post-grow data left at their durable values"*. The test runs the workload twice: pass 1 on a probe backend just to **count** the syncs up to the interesting moment; pass 2 with `freeze_at(total_syncs)` to reproduce the crash, then re-opens the recovered `crash_image()` against a fresh `InMemoryBackend` and asserts the previously-committed row survives plus `check_integrity()` is clean.

Three ideas to steal, in order of value:

1. **Count-then-freeze.** You cannot name the sync index you want ahead of time; you run once, observe the count, then re-run with the freeze set. This generalises cleanly to "crash at the Nth `sync_boundary()`".
2. **The page-cache overlay.** `last_header` encodes the real-world asymmetry that a write can reach the cache while the following sync does not complete. Our WAL has exactly this shape: an appended line sits in the page cache, and `F_FULLFSYNC` failure means it is gone on power loss but visible to a `kill -9` restart. Our current tests model only the `kill -9` case.
3. **Corruption as a distinct axis.** `tests/check_integrity_failure.rs` uses `struct PatchBackend { inner: Arc<RwLock<Vec<u8>>> }` implementing the same trait, with `fn corrupt_first_occurrence(&self, needle: &[u8]) -> bool` flipping all bits (`*b ^= 0xFF`) of the first match, and asserts the DB **refuses further writes** after a failed integrity check rather than allocating against a broken allocator. Our analogue: flip a byte inside a committed `wal.jsonl` payload and assert `ledger::record_iter` skips the line (CRC) and `recover()` does not roll forward on a corrupt record.

`fuzz/fuzz_targets/fuzz_redb.rs` extends the same backend into a fuzzer: `struct FuzzerBackend { inner: FileBackend, countdown: Arc<AtomicU64> }` with `fn check_countdown(&self)` returning `Err(io::Error::from(ErrorKind::Other))` when the countdown hits zero — the fuzz bytes decide *which* I/O call fails. It carries a `COUNTER_TABLE` so a reference `BTreeMap` can be kept in sync as the model oracle, and caps `MAX_PERSISTENT_SAVEPOINTS = 10` because savepoints slow the fuzzer.

Licensing: `Cargo.toml` declares `license = "MIT OR Apache-2.0"`, `version = "4.2.0"`, `edition = "2024"`, `rust-version = "1.90"`; dev-deps include `tempfile = "3.5.0"` and `redb2_6 = { version = "=2.6.0", package = "redb" }` for backwards-compat testing against the previous minor.

### 3. SQLite — the write-list VFS, the fork-kill loop, and the signature oracle

Three independent techniques, all public domain, all still shipping.

**(a) `src/test6.c` — crash VFS.** Header (read verbatim): *"This file contains code that modified the OS layer in order to simulate the effect on the database file of an OS crash or power failure. This is used to test the ability of SQLite to recover from those situations."* Design, stated in the file: every `xWrite` is stored in an in-memory `WriteBuffer` placed at the end of a **global ordered write-list** instead of going to the file; every read first hits the real file and then overlays the write-list. `xSync()` is the decision point — an OS crash may be simulated, in which case `exit(-1)` is called (line 346) and the call never returns. For each buffered write, one of: (1) written correctly, (2) nothing, (3) garbage written to all or part of the overlapping sectors. Device characteristics change that: with `IOCAP_ATOMIC` set, option 3 is **never** selected (line 244 guards it); `IOCAP_ATOMIC512` plus aligned 512-byte writes makes each sector all-or-nothing; `IOCAP_SAFEAPPEND`/`IOCAP_SEQUENTIAL` selects a random write-list entry and discards everything after it. The Tcl bridge is `sqlite3_crash_enable 1 $dfltvfs` + `sqlite3_crashparams $blocksize $dc $crashdelay $cfile`, driven by `proc crashsql` at `test/tester.tcl:1752` where `-file` is documented as **compulsory** — you must name the file being written at crash time.

The device-characteristic axis is the part we have zero representation of: our `renamex_np(RENAME_EXCL)` either happens or does not. Real APFS either writes the whole rename or none of it, so **our** correct characteristic is `IOCAP_ATOMIC`-like for the rename, and torn only for the JSONL append. Worth one sentence in the design doc: we model the torn case only where the filesystem permits tearing.

**(b) `test/crashtest1.c` — fork + random-delay SIGKILL.** Header: *"The main process first constructs a test database, then starts creating subprocesses that write to that database. Each subprocess is killed off, without a chance to clean up its database connection, after a random delay."* Loop: `for(i=0; i<10000; i++){ pid = fork(); if (pid==0) { sched_yield(); do_some_sql(parent); return 0; } usleep(rand()%10000 + 1000); kill(pid, SIGKILL); waitpid(...); }`. On detecting `SQLITE_CORRUPT` the child kills the parent so the run aborts loudly rather than being recorded as a pass. The child snapshots `test.db` + `test.db-journal` into `-saved` copies whenever a journal exists, so a corrupt result can be dissected after the fact.

**(c) `test/crash.test` — the signature oracle.** *"testing the ability of the database to use its rollback journal to recover intact (no database corruption) from a power failure during the middle of a COMMIT."* `set repeats 100`; `proc signature {} { return [db eval {SELECT count(*), md5sum(a), md5sum(b), md5sum(c) FROM abc}] }`. Each iteration crashes at a different journal-sync / db-sync ordinal (`crashsql -delay 1|2|3 -file test.db-journal -seed $seed`) and then asserts `signature` is *byte-identical* to the pre-crash capture. The sweep across `-delay` is the entire point: crash on the 1st sync, the 2nd, the 3rd, etc., and demand the same observable state every time.

### 4. spacejam/sled — random kill offset, and property-testing the fail-point schedule

`tests/crash_tests/mod.rs` opens with six lines that do more work than our 779-line file for one specific bug class:

```rust
fn spawn_killah() {
    thread::spawn(|| {
        let runtime = rand::rng().random_range(0..60_000);
        thread::sleep(Duration::from_micros(runtime));
        exit(9);
    });
}
```

A background thread kills the process at a random microsecond in the first 60 ms. Per-test directory constants (`crash_sequential_writes`, `crash_batches`, `crash_iter`, `crash_tx`, `crash_metadata_store`, `crash_heap`, `crash_object_cache`) under `crash_test_files`, and after restart `tree_to_string` walks the whole tree to verify content. The runner `tests/test_crash_recovery.rs` is a `harness = false` binary that re-executes itself via `const TEST_ENV_VAR: &str = "SLED_CRASH_TEST"` (the identical self-re-exec protocol our `CRASH_CHILD` uses), runs `N_TESTS = 100` iterations, and installs a `ShredAllocator` global allocator that fills allocations with `0xa1` and deallocations with `0xde` — so use-after-free reads show up as recognisable garbage.

`Cargo.toml` gives `[profile.test] panic = "abort"`, `debug = true`, `overflow-checks = true` — a deliberate choice: under `abort`, a panic mid-write is indistinguishable from a kill, widening the crash surface. `fault-injection = "1.0.10"` is a **non-dev** dependency (it is used by production code paths behind internal test features), and the feature set is `testing-shred-allocator`, `testing-count-allocator`, `for-internal-testing-only`, `monotonic-behavior`.

`tests/test_tree_failpoints.rs` is the second technique: `#![cfg(feature = "failpoints")]` gates a quickcheck model whose `Op` enum includes `FailPoint(&'static str, u64)` and `Restart`, with `impl Arbitrary for Op` choosing a fail point only ~1 time in 30 (`if g.gen_bool(1. / 30.) { return FailPoint(fail_points.choose(g).unwrap(), g.r#gen::<u64>()); }`) and a hardcoded list of ~27 named points (`"write_config crc"`, `"write_config fsync"`, `"write_config rename"`, `"write_config dir fsync"`, `"snap write mv"`, `"pwrite partial"`, …). The properties under test are therefore about *schedules of fail-point firings interleaved with restarts*, not about data.

### 5. tikv/fail-rs (`fail` 0.5.1) — the library form of what we hand-rolled

`FAIL_AT`/`KILL_AT` is our own fail-point mechanism: ~5 hand-placed call sites, env-configured, `exit(137)`. `fail` is the mature version of the same idea, and the differences are the interesting part.

`Cargo.toml` (read verbatim): `version = "0.5.1"`, `license = "Apache-2.0"`, `repository = "https://github.com/tikv/fail-rs"`, `edition = "2021"`, deps `log 0.4`, `once_cell 1.9.0`, `rand 0.8`, `[features] failpoints = []`, `[package.metadata.docs.rs] all-features = true`. Two properties we do not have:

1. **Compiled out by default.** Generation is behind the `failpoints` Cargo feature, so release binaries carry no fail-point code at all. Our `KILL_AT` env read is always compiled in.
2. **Runtime-configurable actions, not just exit.** `FAILPOINTS=read-dir=panic cargo run --features fail/failpoints` — the README describes points as able to "exhibit a variety of behavior, including panics, early returns, and sleeping … controlled both programmatically and via the environment, and can be triggered conditionally and probabilistically", citing FreeBSD's `failpoints(9)` as the inspiration. Public API surface read from `src/lib.rs`: `FailScenario::setup()` (`:556`) / `teardown()` (`:592`) as the RAII test guard, `pub fn list() -> Vec<(String, String)>` (`:625`), `pub fn eval<R, F: FnOnce(Option<String>) -> R>(name, f) -> Option<R>` (`:634`), `pub fn cfg<S: Into<String>>(name, actions: &str) -> Result<(), String>` (`:672`), `cfg_callback` (`:681`), `remove` (`:699`), `FailGuard::new` (`:721`), `with_callback` (`:730`), macros exported at `:822` and `:843`.

The analogue worth stealing immediately is `cfg()`: it lets a single test drive *several* failure schedules in-process without re-exec, which is exactly the shape our `ENV_LOCK` + child-re-exec design pays for. Caveat: crate last updated 2022-10-08, so treat it as stable-but-dormant.

`fault-injection` 1.0.10 (komora-io, MIT OR Apache-2.0, 323 K downloads) is the lighter alternative, and its README describes the mechanism exactly: `fallible!(do_io())` decrements a global `FAULT_INJECT_COUNTER` (default `u64::MAX`) and returns `io::Error` of kind `Other` when it hits zero, annotating the error with crate/file/line via `set_trigger_function`; a `SLEEPINESS` knob injects pseudo-random delays for "a basic form of concurrency testing".

### 6. albertito/libfiu — `LD_PRELOAD` fault injection, and a license caveat

README (read verbatim): *"It provides functions to mark 'points of failure' inside your code (the core API), and functions to enable/disable the failure of those points (the control API)."* The core API is compiled into the code under test; the control API is used by the test. Repo root contains `.clang-format`, `.gitlab-ci.yml`, `LICENSE`, `Makefile`, `README.md`, `bindings`, `doc`, `libfiu`, `preload`, `tests`, `utils`; Python bindings live in `bindings/`; default branch is `master` (`main` and `develop` both 404).

**License caveat, important.** `README.md` states "It's in the public domain, see the LICENSE file", but the `LICENSE` file itself (read verbatim) is *"BOLA - Buena Onda License Agreement (v1.1)"* — a permissive but non-OSI, non-SPDX license, and GitHub reports `license: NOASSERTION`. Do not list libfiu in the design doc's dependency table as "public domain"; describe it as "custom permissive (BOLA v1.1), no SPDX identifier".

### 7. tokio-rs/turmoil-fs — the closest thing to what we actually need, and it is unpublished

`crates/turmoil-fs/README.md` (read verbatim) opens with the exact problem statement our tests have:

> *"Tests that touch the real filesystem are nondeterministic — `fsync` timing, page-cache flushes, and dirty-writeback scheduling all vary run to run. Crash-consistency failures (a crash between `write` and `fsync`, a torn write, a write that returned success but was never persisted) are hard to provoke on a real kernel."*
>
> *"A mocked `File` returns the bytes you prime it with; it doesn't distinguish 'in the page cache' from 'on stable storage', so it can't tell you what would survive a crash."*

The model: *"writes land in per-host pending state, `fsync` promotes them to durable, and a simulated crash discards the pending state. With a seeded RNG driving the pending/sync interleaving, crash-consistency scenarios become deterministic and replayable."* `src/lib.rs` documents the crash semantics precisely: **"Files that were never synced are deleted entirely. Pending writes to synced files are lost; durable data survives."** — and, crucially, it also models **orphaned directory entries**: on crash, `persisted_files.retain(|path, _| self.synced_entries.contains(path))` removes files whose data was synced but whose *directory entry* was not, because "In POSIX, both are required for a file to survive a crash." Our WAL/`renamex_np` design has exactly this hazard (`fsync` the file, forget the parent dir) and currently cannot test it.

API, verified from source line numbers in `src/lib.rs`:

- `FsBuilder::seed(u64)` (`:2312`), `sync_probability(f64)` (`:2318`), `corruption_probability(f64)` (`:2336`), `on_corruption(hook)` (`:2360`), `block_size(u64)` (`:575`, asserts `bytes > 0`) — "Block size for torn write simulation (None = atomic writes)" (`:384`).

### 8. apple/foundationdb — deterministic simulation and Buggify

`documentation/sphinx/source/testing.rst` describes simulation as *"enabled by and tightly integrated with flow, our asynchronous runtime for C++ coroutines. Flow supports both production execution and deterministic simulated execution."* It *"conduct[s] a deterministic simulation of an entire FoundationDB cluster within a single-threaded process. Determinism is crucial in that it allows perfect repeatability of a simulated run"*; the docs estimate *"roughly one trillion CPU-hours of simulation"* at a ~10:1 real-to-simulated time ratio, simulating machine count/type, drive performance, drive space filling, and the network, and injecting *"connection failures, degradation of machine performance, machine shutdowns or reboots, machines coming back from the dead"*. The named adversarial pattern is **swizzle-clogging**: pick a random subset of nodes, clog (stop) their network connections one by one over a few seconds, then unclog them in a random order. **[INFERENCE]** for a single-process tool like ours the closest analogue is a scripted *ordering* of failures rather than a probability for each — e.g. "torn WAL tail on volume A, then crash, then a successful apply on volume B".

The transferable mechanism is `flow/include/flow/Buggify.h` (Apache-2.0, verified by reading the header: *"Copyright 2013-2026 Apple Inc. … Licensed under the Apache License, Version 2.0"*):

- `struct BuggifySection { const char* file; int line; }` (`:38`) plus `struct BuggifySectionHash` (`:45`) — the identity of a buggify site is `(file, line)`, hashed into a per-type `std::unordered_map<BuggifySection, bool>`.
- `inline double P_EXPENSIVE_VALIDATION{ 0.05 };` (`:36`) and, from `__GENERATE_BUGGIFY_VARIABLES` (`:52-53`), `P_##TYPE##_BUGGIFIED_SECTION_ACTIVATED{ 0.25 }` and `P_##TYPE##_BUGGIFIED_SECTION_FIRES{ 0.25 }`.
- `inline bool buggify(double probability = P_GENERAL_BUGGIFIED_SECTION_FIRES, ...)` at `:92`, `EXPENSIVE_VALIDATION` at `:98`, `CLIENT_BUGGIFY` at `:102`.

The design point: **a two-stage, per-section coin flip**. First a per-run, per-section decision whether this site is "active" at all (25 %), then per-execution firing (25 %). Combined with `flow/DeterministicRandom.h`, every section's decision is stable and replayable. A one-stage `if rng.chance()` per site would make site decisions independent within a run; the two-stage version produces the swarm-style "most sites are off, a few fire consistently" distribution. Their CTest integration also uses `UNIT_TEST_SEED` (default 1; `0` means random and the chosen seed is printed) and `UNIT_TEST_TIMEOUT` (default 600 s) — a **seed that is printed on failure** is the single cheapest thing to copy from this whole section.

Listing loom/shuttle in the design doc as "evaluated and rejected with reason" is worth a line; installing them is not.

**Note on our existing torn-tail test.** `tests/execute_tests.rs::recover_parks_torn_tail_after_mid_purge_crash` (`:1230`) is already the strongest test in the suite: it hand-writes a truncated final WAL line (`br#"{"v":1,"seq":99,"kind":"result","rec":{"op_id":"purge-torn""#`) and asserts `recover()` reports `rr.torn_tail`, parks the bytes into `wal.jsonl.torn` with exact byte equality, preserves the committed intent+result pair, and surfaces no expired-grace entry. **[INFERENCE]** this is precisely SQLite's `test6.c` option (3) — "garbage written to part of the overlapping sectors" — achieved without any VFS, by writing the torn bytes directly. ## Risks & open questions

1. **The `MidPurge` asymmetry is a correctness smell, not just a test gap.** `Executor::apply` (`src/execute.rs:532`) accepts an explicit `kill_at: Option<KillPoint>` and falls back to the env (`kill = kill_at.or_else(parse_kill_env)` at `:537`); `Executor::purge` (`:730`) takes **no** `kill_at` parameter and reads the env directly (`let kill = parse_kill_env();` at `:752`). Consequence: any test that wants to crash purge must mutate the **process-global** environment and serialise against every other test via `static ENV_LOCK` (`tests/crash_injection.rs:37`), while apply-based tests can pass the point in directly. Adding `kill_at: Option<KillPoint>` to `purge` would remove the lock's reason to exist for those cases. **[INFERENCE]** this was a deliberate scope cut; it is worth one line in the design doc either way.
2. **`ENV_LOCK` serialises the parent, not the child — verify this holds if row 1 is adopted.** The comment in `tests/crash_injection.rs` states children get their env via `Command::env` (a copy plus override) "so they never race". That is true for `spawn_crash`, but a *random-offset* sweep spawns many children whose kills land at arbitrary times; if any child is ever spawned without an explicit `DISK_JANITOR_HOME` override it will inherit whatever the parent has at that instant. Confirm every spawn path passes both `env` values explicitly before increasing concurrency.
3. **A simulated filesystem is only trustworthy if its laws are right — and we cannot verify APFS's.** redb's `crash_image()` and turmoil-fs's `Fs::crash()` both encode specific assumptions about what reaches stable storage. Our real-world equivalent (note 08: `F_FULLFSYNC` ≈ 4 ms vs `fsync` ≈ 0.075 ms on APFS) tells us the platform's actual behaviour, but the *ordering* guarantee of `renamex_np` + directory-entry sync on APFS is not something any OSS source can settle. **Open question:** does APFS make the rename atomic *and* durable, or atomic-but-cached? If cached, our crash model needs the orphaned-dirent case that turmoil-fs models and our tests do not.
4. **`fail` needs our source to contain the macro.** Fail-point libraries instrument by *calling* from production code; they cannot intercept `libc::renamex_np` from outside without an `LD_PRELOAD`-class shim, and `DYLD_INSERT_LIBRARIES` is blocked by SIP on macOS. So row 7 means editing `src/execute/macos.rs`, which is a production file — it must be feature-gated so the default build is byte-identical. Explicitly out of scope for a research pass; flag it before anyone implements it.
5. **`quickcheck`'s `Unlicense OR MIT` and `libfuzzer-sys`'s `(MIT OR Apache-2.0) AND NCSA` are license-audit items, not blockers** — but if the submission's 技术选型 table lists every dependency's license, these two are the ones that will need a footnote. The rest of the recommended set (`proptest`, `proptest-state-machine`, `fail`, `assert_cmd`, `tempfile`) is uniformly MIT OR Apache-2.0, matching the rest of our tree.
6. **libfiu's license is misdescribed upstream.** Its README claims public domain; its `LICENSE` file is BOLA v1.1, a custom permissive license with no SPDX id, and GitHub reports `NOASSERTION`. If it appears in any dependency table, it must be labelled accurately.
7. **`sled` is `1.0.0-alpha.124` and its `tests/test_tree_failpoints.rs` is gated by `#![cfg(feature = "failpoints")]`, a feature that no longer appears in its `Cargo.toml`.** The file is therefore either dead code or gated by an undocumented mechanism. Cite it for the *technique* (quickcheck over fault schedules), not as a working example — marked UNVERIFIED.
