### 2. File-locking primitives — std 1.89 already owns this, so four candidate crates lose on weight

Our single-writer gate is `src/ledger.rs:451-477::Store::open` — `std::fs::OpenOptions{read,write,create,truncate(false)}` on `<home>/janitor.lock` then `lock.try_lock()`, matching `Ok(())` / `Err(TryLockError::WouldBlock)` → `bail!("another janitor instance is running …")` / `Err(TryLockError::Error(e))`. The in-tree comment at `src/ledger.rs:459-461` records that the `fs4`/`nix::fcntl::Flock` candidates "were never adopted".

**Verified at source this session (drops the previous `[INFERENCE]` flag):** in `rust-lang/rust` `library/std/src/fs.rs`, `File::lock`, `lock_shared`, `try_lock`, `try_lock_shared` are all annotated `#[stable(feature = "file_lock", since = "1.89.0")]`, and `pub enum TryLockError { Error(io::Error), WouldBlock }` carries the doc "The standard library will not return an `ErrorKind::WouldBlock` error inside `TryLockError::Error`" — which is exactly the discrimination our `Store::open` match depends on. In `library/std/src/sys/fs/unix.rs` the impls are `cvt(unsafe { libc::flock(self.as_raw_fd(), libc::LOCK_EX | libc::LOCK_NB) })` etc., with `libc::LOCK_EX`/`LOCK_SH`/`LOCK_NB`/`LOCK_UN`; the file also contains `libc::fcntl(fd, libc::F_FULLFSYNC)` on the Apple sync path. So on macOS our lock **is** `flock(2)`, and std is a strictly smaller dependency than any of the four candidates:

### 3. Atomic replace — `tempfile` is the borrowable precedent, and its `NOREPLACE` path independently confirms our syscall

Both of our publish paths use exactly this dance: `src/ledger.rs:664-700::Store::checkpoint` (`NamedTempFile::new_in(&self.home)` → `tmp.as_file().sync_all()` "sync wal compaction temp" → `tmp.persist(&wal_path)` → reopen wal handle → `sync_boundary()`) and `src/agent.rs:692-699::persist_snapshot` (`NamedTempFile::new_in(dir)` → `tmp.persist(&path)`).

Read at source in `tempfile-3.27.0/src/file/imp/unix.rs::persist(old_path, new_path, overwrite)`:

- `overwrite == true` → plain `rename(old_path, new_path)`.
- `overwrite == false`, cfg-gated for `android | linux | macos | ios | tvos | visionos | watchos | redox`: `rustix::fs::renameat_with(CWD, old_path, CWD, new_path, RenameFlags::NOREPLACE)` inside a `static NOSYS: AtomicBool` latch — `Err(Errno::NOSYS) => NOSYS.store(true, Relaxed)`, `Err(Errno::INVAL) => {}` (fall through), `Err(e) => return Err(e.into())`.
- Fallback when the latch is set: `hard_link(old_path, new_path)?` then "Ignore unlink errors. Can we do better?" `let _ = unlink(old_path);`.

And in `rustix-1.1.4/src/backend/libc/fs/types.rs`, the `#[cfg(apple)] bitflags! { pub struct RenameFlags: ffi::c_uint { /// `RENAME_SWAP` const EXCHANGE = bitcast!(c::RENAME_SWAP); /// `RENAME_EXCL` const NOREPLACE = bitcast!(c::RENAME_EXCL); … } }` — i.e. **on apple, rustix's `NOREPLACE` *is* `RENAME_EXCL`**. That is independent confirmation that `src/execute/macos.rs::rename_no_replace` (`libc::renamex_np(from, to, RENAME_EXCL | RENAME_NOFOLLOW_ANY)`) is the right primitive; the crate name differs, the kernel flag does not.

**API-shape detail worth recording** (source-verified, and a common trap): in `tempfile-3.27.0/src/file/mod.rs`, `persist` and `persist_noclobber` exist on **both** `TempPath` (char offsets 6 247 / 8 129) and `NamedTempFile` (25 131 / 27 400); `NamedTempFile::persist_noclobber` merely delegates to `TempPath::persist_noclobber` via `into_temp_path()`, so the two are the same operation. The `TempPath::persist` doc says "If a file exists at the target path, persist will atomically replace it" and then "neither the file contents nor the containing directory are synchronized, so the update may not yet have reached the disk when `persist` returns". The ordering of those sentences is easy to misread: **atomicity yes, durability no.** Our `Store::checkpoint` is correct precisely because it calls `sync_all()` on the temp before `persist` and `sync_boundary()` on the parent after — note 08 §1/§3 already owns that argument; this is confirmation, not a new finding.

The stronger trap is on the *noclobber* variant, which the doc comments state outright: `persist_noclobber` "is not guaranteed to be atomic on all platforms… While it will never overwrite a file at the target path, it may leave the original link to the temporary file behind leaving you with two hard links in your filesystem pointing at the same underlying file", with three named causes — (a) no permission to `unlink` the original, (b) a crash mid-persist, (c) filesystem unmounted during the operation. `TempPath::persist_noclobber` adds "This method is not atomic. It can leave the original link to the temporary file behind." **Consequence for us: never route `Store::checkpoint` through `persist_noclobber`** — the hard-link fallback (source line: `hard_link(old_path, new_path)?` then `let _ = unlink(old_path);`) can leave the WAL reachable under two names, which for an append-only journal is a correctness hazard, not a cosmetic one. `persist` (overwrite path, plain `rename`) is the only variant our two call sites should use.

### 5. Checksums — `crc32fast` is the right call on M1 Pro, and our envelope already uses the right entry point

`crc32fast-1.5.1/src/lib.rs` doc: "This crate contains multiple CRC32 implementations: … An optimized implementation for `aarch64` using `crc32` instructions" and "Calling the `Hasher::new` constructor at runtime will perform a feature detection to select the most optimal implementation for the current CPU feature set." In `src/specialized/aarch64.rs` the gated path is `is_aarch64_feature_detected!("crc")` → `#[target_feature(enable = "crc")]`, i.e. the hardware CRC32 instruction, with a `MIN_TRIPLE_QUADS` threshold (192 ⇒ the implementation switches away from the latency-bound `crc32d` chain for ~1.5 KiB+ inputs). Our `src/ledger.rs:198` calls exactly the recommended advanced entry point (`crc32fast::Hasher::new()`, not the one-shot `crc32fast::hash`) because the envelope at `src/ledger.rs:65-73` is built field-by-field: `{"v":1,"seq":N,"ts":…,"kind":…,"crc32":…,"prev_crc":…,"rec":…}`. **This is a confirmation of note 08 §4, not a new finding.** What is new is that `crc32fast` has **zero RUSTSEC advisories** and its `crc32()/pclmulqdq` + `aarch64 crc` detection means the choice is not leaving Apple-Silicon performance on the table — the alternative candidate `blake3 1.8.7` (209 726 B, `CC0-1.0 OR Apache-2.0 OR Apache-2.0 WITH LLVM-exception`) would be cryptographically stronger but 4.4× the crate size for a *corruption-detection* role, and the per-record cost is dominated by 64–200 B JSON envelopes where CRC32 throughput is irrelevant. `memmap2` was also considered (its `RUSTSEC-2026-0186` is patched exactly at `0.9.11`) and rejected: no `mmap` in the ledger path.

### 6. Volume/capacity facts — `sysinfo` 0.39.6's macOS backend *does* prefer the important-usage key

**Correction (2026-09-13, was the opposite claim).** This section previously asserted that `sysinfo` exposes "no purgeable/important-usage split". That was inferred from the *doc comments* on `src/common/disk.rs`: `is_read_only()` is documented as "Returns `true` if the disk is read-only." and `available_space()` as "Returns the available disk size, in bytes." The docs are the crate's **public** contract and say nothing about provenance — but provenance is what decides whether the number matches Finder, and the macOS backend answers it. `sysinfo-0.39.6/src/unix/apple/disk.rs:379-392`:

```rust
fn get_available_volume_space(disk_props: &CFDictionary) -> Option<u64> {
    // We prefer `AvailableCapacityForImportantUsage` over `AvailableCapacity` because
    // it takes more of the system's properties into account, like the trash, system-managed caches,
    // etc. It generally also returns higher values too, because of the above, so it's a more
    // accurate representation of what the system _could_ still use.
    unsafe {
        get_int_value(disk_props, kCFURLVolumeAvailableCapacityForImportantUsageKey)
            .filter(|bytes| *bytes != 0)
            .or_else(|| get_int_value(disk_props, kCFURLVolumeAvailableCapacityKey))
    }
}
```

Both keys are requested in the property list (`:112-113`, `:278-279`) and the result lands in `Disk::available_space` (`:124`, `:459-460`, `:523`). So on macOS `available_space()` **is** the Finder / About-This-Mac figure — free + purgeable — with a fallback to the raw key only when the important one reads 0. `is_read_only()` is still a `statfs` `MNT_RDONLY` read, exactly as the in-tree comment says.

Measured on this machine (`janitor scan`, 2026-09-13): `/` APFS reported `free_raw` 121.42 GiB against `free_important` 171.04 GiB — a 49.6 GiB purgeable delta. The two figures are genuinely distinct and both are now read in-tree: `free_raw` from a raw `libc::statfs` `f_bavail × f_bsize` call, `free_important` from `sysinfo`.

Consequence for the design document, revised: the Finder number needs **no** CoreFoundation call — `sysinfo` already delivers it on macOS, and `src/scan/platform/macos.rs` labels it accordingly. The remaining `TODO(M3)` is `NSURLVolumeAvailableCapacityForOpportunisticUsageKey` (important + opportunistic), which still has no sysinfo path. Correct primary source: `docs/research/04-rust-walk-and-metadata-crates.md:92` ("available-space preference logic (`kCFURLVolumeAvailableCapacityForImportantUsageKey` first)"), which had this right all along. Verified crate facts unchanged: `sysinfo` 0.39.6, MIT, MSRV **1.95** (the highest of any dependency we hold — above our `rustc 1.97.1`, so fine, but it is the binding constraint if the toolchain is ever pinned lower), 241 117 B, published 2026-07-09. In the lock trees `sysinfo` is a **direct** root dependency; `rustix` is transitive (`tempfile`, `xattr`) and, in the Tauri tree, also via `async-io`/`polling`/`zbus`.

### 8. LLM feature crates — `async-openai` is one minor behind, and that is deliberate

`async-openai` ours = **0.41.3** (published 2026-07-31, MIT, MSRV 1.75, 238 090 B — and its tarball ships **no license file**, only the crates.io field); `max_stable_version = 0.42.0` (2026-09-09, one day before the M1–M5 freeze). ### 9. Trash semantics — crate-level rejection (note 25 already reached it; the numbers here are new)

`trash 5.2.8`: MIT, MSRV **1.85.0**, 69 643 B, published 2026-09-08, repo `ArturKovacs/trash` pushed same day, 252★, not archived; tarball ships `LICENSE.txt`. Read at source in its `Cargo.toml`, the macOS dependency block is `objc2 = "0.6.2"` + `objc2-foundation = { version = "0.3.2", default-features = false, features = ["std","NSError","NSFileManager","NSString","NSURL"] }` + `percent-encoding = "2.3.1"` and the package `include = [… "build.rs"]`. So adopting it would pull a three-crate Objective-C bridge chain and a build script into a codebase whose entire macOS surface is currently `libc` + one `unsafe extern "C"` block. More decisive: the crate's purpose is the **user's `~/.Trash` Recycle Bin**, whereas our design quarantines by same-volume `renamex_np(RENAME_EXCL | RENAME_NOFOLLOW_ANY)` into `<mnt>/.Trash-janitor/` with a 72 h grace window and a purge gated on typing the exact byte count — a different lifecycle with its own restore path. **Verdict: do not add; this confirms `25-trash-quarantine-purge-semantics.md` line 162.** Only the MSRV/crate-size/objc2-chain/`build.rs` measurements are new here.

## Risks & open questions

1. **The `<10 KB` policy is ambiguous as written, and this note resolves it by interpretation.** `tokio` (920 101 B), `tracing` (463 135 B), `bytes` (75 667 B) and `walkdir` (23 951 B) are already in the root lock tree — `tokio`/`tracing`/`bytes` only because of `async-openai` under `feature = "llm"`. The policy therefore cannot mean total transitive weight; this note reads it as *source weight of a newly added direct dependency*. If the grader intends total-closure weight, then every verdict in §2/§9/§10 is unaffected (they are all rejections), but the `async-openai` feature itself deserves a sentence of justification in the design document.
2. **Constants defect is out of scope here by instruction.** §7 and backlog row 1 report it; no code was changed in this pass. If it is fixed, fix both copies of the vocabulary (one shared module) — otherwise the two tables drift apart again.
3. **`dua-core` 4.1.0 upgrade is owner-gated, not recommended unilaterally.** Evidence is strong (`Cargo.toml.orig` identical, changelog explicit), but the pin predates this research and the submission is due 2026-09-13 23:59. Unverified: whether `crossbeam.workspace = true` in 4.1.0 resolves to the lock's `crossbeam-0.8.5` or pulls a second major.
4. **`async-openai` 0.41.3 → 0.42.0 was not diffed.** Only the two publish dates (2026-07-31 vs 2026-09-09) and both licenses/versions were verified. Breaking-change risk is unknown; the recommendation to stay put is a scheduling judgement, not a compatibility finding.
5. **Four crates in this lane ship no license file inside the `.crate` tarball** — `flock 0.2.0`, `file-lock 2.1.11`, `async-openai 0.42.0`, and `dua-core` 4.0.0/4.1.0. For the two we already depend on (`dua-core`, and `async-openai` under the `llm` feature) the license is asserted only by the crates.io `license` field (`MIT` for both). This is a compliance-trail gap worth one line in the design document, not a blocker.
6. **`nix` 0.31.3's build-time closure was not exercised.** Its `Cargo.toml.orig` declares `[build-dependencies] cfg_aliases`; the connection between generated aliases and the emitted `cfg`s was not cross-checked without building. The macOS conclusion that matters (no `renamex_np`/`RENAME_EXCL`/`setiopolicy_np`, `renameat2` Linux-gnu-only) is source-verified and unaffected.
7. **`jwalk`, `fs2`, `fslock`, `named-lock`, `file-lock`, `atomicwrites` repository liveness was only checked for the crates where it changes the verdict.** `HyeonuPark/Flock` (1★, last push 2017-03-16, `license: null`) is the most damning; a project considering any of the others should re-check `pushed_at` rather than trusting this note's date.
8. **Not verified anywhere in this lane:** whether any of these crates' *transitive* dependencies carry advisories (`cargo-audit`/`cargo-deny` output was not run — no project-wide commands were permitted). The RUSTSEC findings in this note are per-crate advisory-file reads, not a lock-file scan. **This is the single largest gap in the lane** and the cheapest to close later with one `cargo audit` run.
