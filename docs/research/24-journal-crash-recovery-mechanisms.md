# Journal & Crash-Recovery Mechanisms in Production OSS — Research Note
Per-project journal mechanics (framing, checksum, commit marker, torn-tail resync, recovery model) read from each project's own source, then compared against our `ledger/` + `execute/` WAL design · researched 2026-09-13

Scope: this note examines the *journal/commit machinery* of 12 systems — borg 1.4 (segment transaction journal + master's `OBJ_MAGIC` packs), restic (pack/index as commit), rclone (`RemoveExisting` rename-aside), duplicacy (`.tmp` + rename storage layer), git-annex (journal + `parseLogLines`), sled (0.34.7 log/segment/snapshot), redb (2.6.0 dual commit slot), jammdb (0.11.0 dual meta page), sanakirja (1.4.3 versioned root pages + optional CRC), LMDB (`mdb.master` dual meta page), the Rust `wal` / `wal-rs` / `okaywal` crate family, cargo (`cargo-util` `write_atomic`, `.cargo-ok`), and SQLite WAL (`src/wal.c`). Every version, license and API claim below was read from a primary source (raw.githubusercontent.com file, the crate tarball from static.crates.io, the repo's own LICENSE/Cargo.toml, or the crates.io version API) on 2026-09-13; where a page could not be read it is marked UNVERIFIED in-line rather than inferred. Nothing outside this file was modified and no code was ported.

**Delta against note 08 (`docs/research/08-ledger-wal-crash-safety.md`, 2026-08-30).** Note 08 owns the macOS/materials theory and the *schema proposal*: §1 durability dance, §2 std `F_FULLFSYNC` mapping, §3 `renamex_np`/`RENAME_EXCL`/tempfile `persist`, §4 JSONL framing + crc32fast, §5 torn-write detection (the SQLite single-pass recovery algorithm, salt + cumulative checksum), §6 the `flock` vs `fcntl` vs OFD vs `lockf` comparison table, §7 SQLite WAL + git reference patterns, §8 the `ledger.jsonl` + `wal.jsonl` schema. **This note does not restate any of that.** What is NEW here is the same questions answered from each *other* project's own source: their record framing bytes, their commit-marker byte, their fsync call sites, and — the part 08 never covers — **what each system does at the moment it finds a bad record mid-file, and whether it truncates, skips, rewrites or abandons.** That torn-tail/abandon/fault-isolation axis turns out to be where our design has its weakest link (§ "Our design vs the closest analogue" (a)).

## Findings

### 1. borg 1.4 — segment journal with per-entry CRC and byte-sliding resync (the closest analogue)

`src/borg/repository.py` on branch `1.4-maint` (file fetched complete, 84 978 B). Constants at lines 32–47: `MAGIC = b'BORG_SEG'`, `TAG_PUT=0`, `TAG_DELETE=1`, `TAG_COMMIT=2`, `MAX_TAG_ID = 15` — with the comment at 42–46 that any tag id above `MAX_TAG_ID` is assumed corrupted so that `borg check --repair` can rewrite the entry.

Framing (`LoggedIO`, 1329–1339) is three fixed `struct.Struct` layouts: `header_fmt = '<IIB'` (9 B: crc32, size, tag), `put_header_fmt = '<IIB32s'` (41 B: crc32, size, tag, 32-byte key), `header_no_crc_fmt = '<IB'` (5 B), `crc_fmt = '<I'` (4 B). The commit marker is a **precomputed constant**: `_commit = header_no_crc_fmt.pack(9, TAG_COMMIT)` and `COMMIT = crc_fmt.pack(crc32(_commit)) + _commit` — i.e. a commit record is the 9-byte header whose CRC is the CRC of its own body, computable once at import. Read-side integrity at 1696: `crc32(data, crc32(memoryview(header)[4:])) & 0xffffffff != crc` → `IntegrityError`.

`write_commit(intermediate=False)` (1741) is the two-mode commit: the docstring says "Intermediate commits go directly into the current segment … Final commits go into a new segment", implemented as `fd = self.get_write_fd(want_new=not intermediate, no_new=intermediate)`; an intermediate commit `fd.sync()`s in place, then either way the crc+header commit record is written and `close_segment()` is called. `close_segment()` (1532) sets `self._write_fd=None` *first* — the comment says this is "to guard against reentry" — then bumps `self.segment`, zeroes `self.offset`, and closes the fd. So the commit marker is written by the same code path that closes the segment, and `write_commit` returns the just-closed segment number (`self.segment - 1`).

**The torn-tail policy is the distinctive part.** `recover_segment(segment, filename)` (1615) short-circuits when `getsize < MAGIC_LEN + 9` by rewriting only the MAGIC. Otherwise it mmaps `ACCESS_READ` over the whole segment and slides a byte at a time: `while len(d) >= 9: crc,size,tag = header_fmt.unpack(d[:9]); if size > MAX_OBJECT_SIZE or tag > MAX_TAG_ID or size < 9 or size > len(d) or crc32(d[4:size]) != crc: d = d[1:]; continue; dst_fd.write(d[:size]); d = d[size:]`. Two consequences worth naming: (1) it **never truncates at the first bad entry** — it re-syncs by advancing one byte and re-testing, so damage in the middle costs only that entry's bytes, and (2) it *rewrites the surviving entries into a new file* rather than repairing in place. The read-side counterpart is documented in `scan()`'s docstring at 1207: "the repository segments are valid (no CRC errors). if we encounter CRC errors in segment entry headers, rest of segment is skipped."

The commit/index protocol is where our design rhymes with borg. `replay_segments(index_transaction_id, segments_transaction_id)` (923) iterates `self.io.segment_iterator()`, skips `segment <= index_transaction_id`, breaks at `segment > segments_transaction_id`, calls `_update_index(segment, objects)` per segment, then `write_index()`, then `rollback()`. `_update_index` (947) handles `TAG_PUT`/`TAG_DELETE` and treats `TAG_COMMIT` as a no-op on the index. And `write_index()` (643) commits the derived index exactly the way we compact our WAL: `flush_and_sync(fd)` = `fd.flush(); os.fsync(fd.fileno())`, then `rename_tmp(file)` = `os.replace(file + ".tmp", file)`. **borg's durable segment journal is the source of truth; the index is derived and replaced atomically — the same "journal is truth, derived state excluded from the log" rule note 08 §7 draws from SQLite's `-shm`.**

`master` has replaced this mechanism, and the replacement is itself a finding. `src/borg/repoobj.py` line 61 `OBJ_MAGIC = b"BORG_OBJ"` with the comment at 73 "Fixed header size per blob: OBJ_MAGIC(8) + version(1) + chunk_id(32) + meta_size(4) + data_size(4)"; `src/borg/repository.py` line 42 `RESYNC_WINDOW_SIZE = 1024 * 1024`; `_parse_header` (381–399) validates magic, version, `offset + obj_size > pack_size` → "object extends past end of file", `obj_size > MAX_DATA_SIZE`; `_validation_problem` (401–415) rejects `hdr.meta_size > MAX_VALIDATED_META_SIZE` and requires `validate(hdr.chunk_id, obj)`; and `_find_header` (417–443) carries the key comment: "**A pack has no framing besides the object headers, so this searches for OBJ_MAGIC. That byte sequence also occurs inside payloads**, so a candidate is accepted only when its header parses and validate(chunk_id, obj) confirms the header and metadata slot at that position." Resync moved from *trying every byte offset with a CRC* (1.4) to *finding a magic word in a 1 MB window and then cryptographically authenticating the candidate* (master). Both are self-synchronizing; neither truncates.

### 2. restic — no journal at all; the index is the commit record

`internal/backend/local/local.go` (9 326 B, master, complete). `Save` (109–200): `tmpname := filepath.Base(finalname) + "-tmp-"`, `tempFile(...)`, `os.MkdirAll` + retry when the parent is missing, a deferred temp cleanup on error, `fileio.PreallocateFile(f, size)` whose failure is only logged, `wbytes, err := io.Copy(f, rd)`, a sanity check `if wbytes != rd.Length()` → "wrote %d bytes instead of the expected %d bytes", then `err = f.Sync()` with `syncNotSup := err != nil && (errors.Is(err, syscall.ENOTSUP) || isMacENOTTY(err))`, `f.Close()` (the comment notes "Windows doesn't like the reverse order"), `os.Rename(f.Name(), finalname)`, and finally `if !syncNotSup { err = fsyncDir(dir) }` under the comment "Now sync the directory to commit the Rename." This session I located the definitions that the previous pass could only cite by call site: **`internal/backend/local/local_unix.go`** (`//go:build !windows`, 1 153 B) defines `fsyncDir(dir string)` as `os.Open` + `d.Sync()`, swallowing `ENOTSUP`, `ENOENT`, `EINVAL` and `isMacENOTTY(err)`; `isMacENOTTY` is `runtime.GOOS == "darwin" && errors.Is(err, syscall.ENOTTY)` with the comment that the ExFAT driver on some macOS versions returns ENOTTY "inappropriate ioctl for device" for fsync (restic issue #4016). That same file defines `setFileReadonly` (chmod `mode&^0222`, tolerating `errors.ErrUnsupported` for CIFS/gvfs).

Content framing lives in `internal/repository/pack/pack.go` (12 644 B): `Packer.Add` (41), `Finalize()` (92), the header is built and then `encryptedHeader = binary.LittleEndian.AppendUint32(encryptedHeader, uint32(len(encryptedHeader)))` (105–109) — **the length is a 4-byte suffix appended last**, which is what makes the header findable by seeking from EOF; `headerLengthSize = 4` (253), `MaxHeaderSize = 16*1024*1024 + headerLengthSize` (258), and the reader (283–302) seeks to `EOF-4` and rejects `hlen > MaxHeaderSize-headerLengthSize` or `int64(hlen) > size-int64(headerLengthSize)` with "pack header size mismatch". `internal/repository/pack/blob.go`/`packedblob.go` are index-entry types (`Blob{restic.BlobHandle; Length, Offset, UncompressedLength uint}`, `PackedBlob{Pack restic.ID; Blob Blob}`), not framing. `internal/repository/repository.go` commits by index: `LoadIndex` (717), `loadIndexWithCallback` (722), `createIndexFromPacks` (764), and invalid packs are collected (`invalid = append(invalid, fi.ID)`, 799) and rebuilt from.

So restic's answer to "what is the commit?" is: **there is no journal; an object is committed iff the index says it exists, and an unreadable or oversized pack header simply makes that pack invalid and rebuildable from the others.** This is the strongest precedent for our `ReplayReport` accounting (`volumes_checked`, `rolled_forward`) — recovery is a *classification pass over durable artifacts*, not a log replay.

### 3. rclone — rename-aside with restore-on-failure (the destructive-op protocol)

`fs/operations/operations.go` (89 282 B, MIT). `RemoveExisting(ctx, f, remote, operation) (cleanup func(*error), err error)` at 1211–1259, doc comment: "This first detects if there is an existing file and renames it to a temporary name if there is. … It will revert the changes if there is an error or delete the existing file if not." Body: `doMove := f.Features().Move`; if nil → `"destination file exists already and can't rename"` (1227); then the suffix and its length guard (1230–1238): `// Avoid making the leaf name longer if it's already lengthy to avoid trouble with file name length limits.`, `suffix := "." + random.String(8)`, `if len(path.Base(remote)) > 100 { remoteSaved = TruncateString(remote, len(remote)-len(suffix)) + suffix } else { remoteSaved = remote + suffix }` — i.e. it keeps the 9-byte suffix by **truncating the leaf** rather than refusing; `doMove(ctx, existingObj, remoteSaved)` else `"failed to rename existing file"` (1243); the returned cleanup closure deletes the renamed file on success and on failure calls `doMove(ctx, existingObj, remote)` else logs `"failed to restore existing file after failed operation"` (1253–1257). Call sites: `Move` (423), `MoveTransfer` (431), `MoveBackupDir` (2009), `MoveCaseInsensitive` (2032), `SkipDestructive(ctx, srcFileName, "rename to "+dstFileName)` (2041). The server-side path (~452–498) reports `in.ServerSideMoveEnd(newDst.Size())`, `accounting.Stats(ctx).Renames(1)`, `fs.Infof(src, "Moved (server-side) to: %s", …)`. **Corroborates our quarantine-by-`renamex_np` choice: the production pattern for "replace a file that may need to come back" is rename aside, keep an undo closure, and only unlink on proven success.**

### 4. duplicacy — `.tmp` + `Sync()` + rename, with **no directory fsync** (the counter-example)

Go, master, full tarball. `LICENSE.md` is **not OSI-approved** — "Copyright © 2017 Acrosync LLC", "Free for personal use or commercial trial", "Non-trial commercial use requires per-computer CLI licenses … $50 per year", "Modification and redistribution are permitted, but commercial use of derivative works is subject to the same requirements". `DESIGN.md` is 5 lines (a link to the wiki) — no design content. (Neither may be used as a dependency or an authority.)

`src/duplicacy_filestorage.go` — note the filename: `src/duplicacy_file_storage.go` does not exist (404). `FileStorage.UploadFile` (150–220) is the entire storage durability story: `os.Lstat(dir)` (comment: "Stat() doesn't work for deduplicated disks on Windows") → `os.MkdirAll(dir, 0744)`; temp name `fullPath + "." + 8 random lowercase letters + ".tmp"`; `os.OpenFile(o.WRONLY|O.CREATE|O.TRUNC, 0644)`; `io.Copy`; **`file.Sync()` with `pathErr.Err == syscall.ENOTSUP` tolerated** (194–202); `file.Close()`; `os.Rename(temporaryFile, fullPath)` (208). On rename failure, if `os.Stat(fullPath)` succeeds it `os.Remove(temporaryFile)` and **returns nil** — last-writer-wins is an accepted outcome. **There is no directory fsync anywhere in the file.** Other methods: `ListFiles` 68, `DeleteFile` 93, `MoveFile` 103 (`os.Rename`), `CreateDirectory` 108, `GetFileInfo` 118, `DownloadFile` 132, `IsCacheNeeded` 224, `IsMoveFileImplemented` 227 → true, `IsStrongConsistent` 230 → true, `IsFastListing` 233 → false. The snapshot manager (`src/duplicacy_snapshotmanager.go`, 82 946 B) uploads via `manager.storage.UploadFile(0, path, …)` (2659, 2703) and skips in-flight temps in listings (`collection.AddTemporary(file)` 2453/2466; `!strings.HasSuffix(chunk, ".tmp")` 823; the comment `// Temporary files.` at 49). The extract path (`src/duplicacy_backupmanager.go` 1500–1555) verifies `hex.EncodeToString(hasher.Sum(nil)) != entry.Hash` → `"file corrupt (hash mismatch)"`, then `newFile.Close()`, `os.Remove(fullPath)`, `os.Rename(temporaryPath, fullPath)`. **Duplicacy is the proof that temp+sync+rename is necessary but not sufficient: without the parent-dir fsync the rename itself can be lost, and it tolerates a lost rename rather than paying for the barrier.**

### 5. git-annex — newline-heuristic append repair, line-skipping parser, no fsync

Hackage tarball `git-annex-10.20260901` (`github.com/joeyh/git-annex` is 404/dead). `git-annex.cabal` line 4 `License: AGPL-3` with `License-File: COPYRIGHT`; `COPYRIGHT` is Debian-format with `Files: *` → `AGPL-3+`, © 2010-2026 Joey Hess. **AGPL-3+ — read-only design reference, never a dependency.**

`Annex/Journal.hs` (383 lines). Header comment: "The journal is used to queue up changes before they are committed to the git-annex branch. Among other things, it ensures that if git-annex is interrupted, its recorded data is not lost. — All files in the journal must be a series of lines separated by newlines." `setJournalFile` (86–103) is atomic replacement via temp+move: `withOtherTmp` → `F.withFile tmpfile WriteMode` → `moveFile tmpfile dest` + `setAnnexFilePerm dest`, with the comment "The file in the journal is updated atomically. This avoids an interrupted write truncating information that was earlier read from the file, and so losing data." `checkCanAppendJournalFile` (119–130) refuses to append unless the journal file **already exists** ("that would overwrite whatever content the file has in the git-annex branch"). `appendJournalFile` (143–159) carries the torn-tail rationale verbatim: "Appends are not necessarily atomic, though short appends often are. So, when this is interrupted, it can leave only part of the content written to the file." — implemented by `hFileSize`, `hSeek h SeekFromEnd (-1)`, `B.hGet h 1`, and on a non-`\n` byte: `goodpart <- L.length . discardIncompleteAppend <$> L.hGet h sz; hSetFileSize h (goodpart)`. It warns "this should not be used when multiple lines need to be written to the file as an atomic unit". The read side, `getJournalFileStale` (183–216), is strict (`F.readFile'` forced) and applies the same repair in memory: `discardIncompleteAppend . L.fromStrict`. `discardIncompleteAppend` (219–226): `| L.null v = v | L.last v == nl = v | otherwise = L.dropWhileEnd (/= nl) v`. `JournalledContent` has a third constructor `PossiblyStaleJournalledContent` for the private journal, whose content is **concatenated** with the shared journal's on read, "the same as happens in a merge of two git-annex branches" — the private-journal split (`RegardingUUID`, `regardingPrivateUUID`, `privateUUIDsKnown`) keeps private-UUID data out of the shared branch, corroborating our path-blind chokepoint at the storage layer.

Two clean negatives: a `grep` for `fsync`/`F_FULLFSYNC` across `Utility/` and `Annex/` returned **nothing** — the only flush-adjacent call is `hFlush jlogh` in `Annex/Branch.hs`'s `genstream` (~767) — so **git-annex's journal has no explicit fsync at all** and delegates durability to git's index. And `Logs/Line.hs` (1–40) is the fault-isolation precedent our skip-and-continue contract needs: `parseLogLines :: A.Parser a -> A.Parser [a]`, doc comment "**If the parser fails to parse a line, that line is skipped, instead of the overall parse failing. This is generally a good idea in case a newer version of git-annex somehow changed the format of the log file.** Any combination of \r and \n are taken to be the end of the line." Implementation: `line <- A.takeTill isEndOfLine; A.skipWhile isEndOfLine;` then `case A.parseOnly parser line of Left _ -> dl; Right v -> D.snoc dl v` — a corrupt line cannot poison any later line, and the stated rationale is *forward compatibility with a newer writer*, the same argument behind our `FORMAT_V` / unknown-kind rule.

### 6. sled 0.34.7 — segment header with XOR'd CRC, in-log skip markers, snapshot-as-rename

Tarball `sled-0.34.7` (Cargo.toml `license = "MIT/Apache-2.0"`, both LICENSE files present). `src/pagecache/constants.rs` lines 9–12: `MAX_MSG_HEADER_LEN = 32` with the comment showing the layout (`crc: u32 4`, `kind: u8 1`, `seg num: u64 9 (varint)`, `pid: u64 9 (varint)`, `len: u64 9 (varint)`) and `SEG_HEADER_LEN = 20`.

The segment header is a 20-byte record whose validation is deliberately XOR-obfuscated so that a zeroed/garbage page cannot accidentally validate (`src/pagecache/logger.rs`, `impl From<[u8; SEG_HEADER_LEN]> for SegmentHeader`, 539–570): `crc32_header = arr_to_u32(buf[0..4]) ^ 0xFFFF_FFFF`, `lsn = arr_to_lsn(buf[4..12]) ^ 0x7FFF_FFFF_FFFF_FFFF`, `max_stable_lsn` likewise, `let crc32_tested = crc32(&buf[4..20]); let ok = crc32_tested == crc32_header;`. `Into<[u8; SEG_HEADER_LEN]>` mirrors it (`crc32(&buf[4..20]) ^ 0xFFFF_FFFF`). `read_segment_header(file, lid)` preads exactly 20 bytes and then asserts `segment_header.lsn >= Lsn::try_from(lid)`. This is exactly the "is this record valid, or is it just zeroes?" problem our newline test does not answer.

Messages inside a segment use a **variable-length** header, not the fixed 9/41-byte borg form: `pub struct MessageHeader { crc32: u32, kind: MessageKind, segment_number: SegmentNumber, pid: PageId, len: u64 }` (~476) with hand-written `serialize`/`deserialize`. `read_message` (~718) preads a `[0; 128]` window, asserts against `MAX_MSG_HEADER_LEN` ("tried to read a message from the red zone"), rejects an "impossibly long length" against the segment ceiling, returns `Ok(LogRead::Corrupted)` on CRC mismatch (~771), and returns `Corrupted` when `header.segment_number != expected_segment_number` (779–784).

Two behaviours are directly borrowable. First, **recovery markers live inside the log**: `MessageKind` (`src/pagecache/mod.rs` 100–138) is `Corrupted = 0` ("The EVIL_BYTE is written as a canary to help detect torn writes"), `Canceled = 1` ("Indicates that the following buffer corresponds to a reservation for an in-memory operation that failed to complete. **It should be skipped during recovery.**"), `Cap = 2` (padding to fill a segment: `MessageHeader { kind: MessageKind::Cap, pid: PageId::max_value(), segment_number, len: pad_len, crc32: 0 }` with the CRC patched into bytes 0..4 in `src/pagecache/iobuf.rs`), `BatchManifest = 3`, `Free`, `Counter`, `InlineMeta`, `BlobMeta`, `InlineNode`, `BlobNode`, `InlineLink`, `BlobLink`. The cancel path (`src/pagecache/reservation.rs` 120–122) writes `self.buf[4] = MessageKind::Canceled.into()` with the comment "don't actually zero the message, still check its hash on recovery to find corruption". So sled encodes *intent to ignore* and *padding* as first-class record kinds rather than relying on a length/EOF heuristic — the analogue of a torn-tail record being discoverable rather than inferred.

Second, **the snapshot is committed by rename and validated by a trailer**: snapshot = body + 8-byte `len_expected` + 4-byte crc32; `read_snapshot` (458) rejects `len <= 12` ("empty/corrupt snapshot file found") and `crc_expected != crc_actual` → `Err(Error::corruption(None))` (473–492); `write_snapshot` (~508) writes `snap.{:016X}.generating` and then renames; `read_snapshot_or_default` (442) uses the default only when the file is *absent* and errors when it is *corrupt*. `stable_lsn` monotonicity is asserted (291–303, 359–362) and `config.file.sync_all()` appears at 336, 425, 556.

Fsync policy is the interesting third point and it is Linux-optimised: `src/pagecache/iobuf.rs` (735–756) issues `libc::sync_file_range(fd, log_offset, total_len, SYNC_FILE_RANGE_WAIT_BEFORE|SYNC_FILE_RANGE_WRITE|SYNC_FILE_RANGE_WAIT_AFTER)`, falls back to `f.sync_all()?` when `err.raw_os_error() == Some(libc::ENOSYS)`, and on `#[cfg(not(target_os = "linux"))]` — i.e. on macOS — does `f.sync_all()?` unconditionally. `impl Drop for Log` (456–469, read in full) early-returns if `self.config.global_error().is_err()` ("don't do any more IO if we're crashing"), flushes the iobufs, and then `if !self.config.temporary { self.config.file.sync_all().unwrap(); }`. **sled batches sync into `sync_file_range` on Linux and pays a full `sync_all` per flush on macOS, exactly the platform split our per-intent `sync_data()` sits on.** `src/pagecache/segment.rs::truncate(at)` (1080) asserts `at % segment_size == 0` ("new length must be io-buf-len aligned") and then does `config.file.set_len(at).and_then(|_| config.file.sync_all())` — the one place sled *does* truncate, and only at a segment boundary. `src/pagecache/iterator.rs` tracks `max_lsn` which "may be set to the beginning of the first corrupt message encountered in the previous sweep of recovery" (54–58), logs `"read corrupted msg in LogIter::next as lid {} lsn {}"` (131), and bounds reads via `is_valid_lid` with `min_lid = seg_start + SEG_HEADER_LEN`, `max_lid = seg_start + segment_len - MAX_MSG_HEADER_LEN` (274–279).

### 7. redb 2.6.0 — dual 128-byte commit slot + one-byte "god byte" primary bit

Tarball `redb-2.6.0` (`Cargo.toml` line 16 `version = "2.6.0"`, `license = "MIT OR Apache-2.0"`, both LICENSE files present). **crates.io reports the latest published version as 4.2.0 — everything below is the 2.6.0 tarball actually inspected; do not conflate the two.**

`src/tree_store/page_store/header.rs`: `pub(super) const MAGICNUMBER: [u8; 9] = [b'r', b'e', b'd', b'b', 0x1A, 0x0A, 0xA9, 0x0D, 0x0A]` (46) followed by `GOD_BYTE_OFFSET = MAGICNUMBER.len()` (47); `PRIMARY_BIT: u8 = 1`, `RECOVERY_REQUIRED: u8 = 2`, `TWO_PHASE_COMMIT: u8 = 4` (61–63); `PAGE_SIZE = 4096` (80); `TRANSACTION_SIZE = 128`, `TRANSACTION_0_OFFSET = 64`, `TRANSACTION_1_OFFSET = 64+128`, `DB_HEADER_SIZE = TRANSACTION_1_OFFSET + TRANSACTION_SIZE` (55–58); `SLOT_CHECKSUM_OFFSET = TRANSACTION_SIZE - size_of::<Checksum>()` (78); magic check `if data[..MAGICNUMBER.len()] != MAGICNUMBER` (113).

`docs/design.md` (493 lines, in-tarball) gives the super-header layout (512 B = header + two 128-byte commit slots, diagram 39–57), names `primary_bit` (91), `recovery_required` (92), `two_phase_commit` (95–96: "the primary slot is guaranteed to be valid, and repair won't look at the secondary slot"), and states line 99: "**redb relies on the fact that this is a single byte to perform atomic commits**". The slot fields are enumerated at 120–127: 16 bytes user root checksum, 16 bytes system root checksum, 8 bytes last committed transaction id, 16 bytes slot checksum, where the root checksums are `XXH3_128` of the respective root pages (134/140) and line 144 "`slot checksum` is the XXH3_128bit checksum of all the preceding fields in the transaction slot." Lines 152–153 distinguish the two allocator states: "the former is valid only after a clean shutdown; the latter is usable even after a crash" (quick repair).

The commit protocol is documented in `src/transactions.rs` 1577–1610 and matches our mental model of "commit = one atomic, verifiable byte flip": **1-phase** = update the inactive commit slot → flip the god byte primary bit to activate it → `fsync`; **2-phase** = update the inactive slot → `fsync` → flip the god byte → `fsync`. The open-after-crash rule is stated once: "All data is written with checksums. When opening the database after a crash, **the most recent of the two commit slots with a valid checksum is used.**" The same doc block is candid about the limits — the checksum is xxhash, "a fast, non-cryptographic hash function", and an attacker with crash control and arbitrary write payload "can cause invalid data to be written with a valid checksum"; 2-phase commit narrows but does not close that (partial-commit attack requiring control of page flush order, crash injection during fsync, and knowledge of file contents), and even 2-phase commit cannot help when the drive lies about fsync. `set_two_phase_commit` (1614) is the switch (`set_quick_repair` 1596); `commit()` 1759, `commit_with` 1767, `commit_inner` 1783, `commit_inner_helper` 1800. Savepoint version/checksum-type changes are rejected (1389–1391). `src/tree_store/page_store/page_manager.rs` has `fn xxh3_checksum(data: &[u8]) -> Checksum` (302), writes the magic only after successful init (1123–1151, error "Not a redb database: magic number mismatch" at 1137), `self.storage.sync_file()?` (1325), and `rollback_all()` (220). The important asymmetry for us: **redb's default open-after-crash is a full repair** — walk the whole DB verifying checksums and reconstructing the allocator (1583–1590) — not a scan of a bounded log.

### 8. jammdb 0.11.0 — dual meta page selected by `tx_id`, FNV-1a hash (SHA3-256 in the legacy format)

## Our design vs the closest production analogue

Closest analogue, stated precisely: **borg 1.4's segment transaction journal** for the *append+per-record-checksum+replay* shape, and **LMDB/redb/jammdb's dual-slot metadata commit** for the *"what is the commit point"* question. Our verified design (read from `src/ledger.rs` and `src/execute.rs` this session): two JSONL files under `<home>` — `ledger.jsonl` (permanent R5 history) and `wal.jsonl` (crash journal, emptied at each checkpoint) — plus `<home>/janitor.lock`; `<home>` created 0700; single-writer gate = **std `File::try_lock()`** (`src/ledger.rs:451-476`; the comment records that std's `try_lock` stabilized in 1.89 and that `fs4`/`nix::fcntl::Flock` were considered and *not adopted*), `TryLockError::WouldBlock` → `"another janitor instance is running (flock held on {})"`. Envelope `{"v":1,"seq":N,"ts":…,"kind":…,"crc32":…,"prev_crc":…,"rec":{…}}` with `crc_of(rec_json, seq)` = crc32fast over `serde_json::to_vec(rec)` ++ `seq.to_le_bytes()` and `prev_crc` chaining **ledger-shaped records only**; `FORMAT_V = 1` (`:153`), WAL kinds `"intent"`/`"result"` (`:154-155`) with an independent WAL-local `seq`. `Store::wal_intent` (`:613`) writes and `sync_data()`s (`:639`, `F_FULLFSYNC` on apple) **before** the caller mutates the FS. `Store::checkpoint` (`:664`) folds valid WAL lines into the ledger unless the `op_id` is already present, `sync_data()`s the ledger at `:680` **before** dropping the journal, then compacts: `NamedTempFile::new_in(&home)` → `tmp.as_file().sync_all()` → `tmp.persist(&wal_path)` → reopen → `sync_boundary()` (dir `sync_all`, `:646-651`). `wal_has_torn_tail()` (`src/execute.rs:222`) is `fs::read` + `!d.is_empty() && d.last() != Some(&b'\n')`; `sanitize_wal_tail()` (`:231`) parks `data[cut..]` in `<path>.torn` via `as_encoded_bytes()`/`OsString::from_vec`, then `set_len(cut)` + `f.sync_all()`.

**(a) Per-line CRC + skip-and-continue is borg-shaped — but our torn-tail *test* is git-annex-shaped, and that is the weakest link.** Our per-record crc32 plus "a corrupt middle line does not poison later lines" is the same contract as borg's per-entry CRC with resync and git-annex's `parseLogLines`. But borg's read side (`scan()`, docstring at 1207) and borg's repair path *both* validate a checksum before deciding a record ends, whereas our `wal_has_torn_tail()` tests **only whether the file's last byte is a newline**. Across the twelve systems examined, exactly one other uses a newline presence test (git-annex `discardIncompleteAppend`), and git-annex discards the partial content *in memory* with **no sidecar file**; every other system that must decide "valid or not" at a boundary uses a checksum (borg crc32, sled crc32+canary, redb XXH3, jammdb FNV-1a, sanakirja CRC, okaywal crc32, LMDB magic+version). The failure mode is concrete: a WAL whose last line happens to end in `\n` but whose bytes were partially written (a short write that lands inside a line boundary is unlikely, but a *preallocated/zero-padded* tail or a torn write whose payload contains `\n` — JSON strings can contain `\n` escapes but a raw newline can appear anywhere in a torn region) validates as "not torn", and `replay` then feeds it to `classify`, which *does* CRC-check it and counts it `Corrupt` — so the damage is contained, but the recovery report's `torn_tail: Option<PathBuf>` field (populated from `RecoveryReport` at `src/execute.rs:113`) under-reports. **Verdict: the pattern is production-precedented, but the detection should be promoted from "does the file end in `\n`" to "does the last line's CRC validate", reusing `src/ledger.rs::crc_of`/`classify` rather than re-deriving it. Risk of the change: low. Cheapest meaningful hardening in this lane.**

**(b) `prev_crc` has no consumer-side enforcement — weaker than every chained design here, but borg is precedent that per-record CRCs need not chain.** Our chain (module docs, `src/ledger.rs:17-20`) is explicitly "consumer-verifiable; replay itself only validates per-line CRCs so that a corrupt middle line does not poison the lines after it". SQLite's checksums are cumulative by construction, redb's slot checksum covers all preceding fields, and sanakirja's CRC covers the page — all three make the *chain* the validity test. But borg's read-side check is also local: `crc32(data, crc32(memoryview(header)[4:]))` validates one entry with no cross-entry linkage, and borg's cross-entry integrity comes from `TAG_COMMIT` plus the index rather than a hash chain. So our position is defensible *and* the chain is currently dead weight at runtime: `replay` (`:709`) returns records "whose `prev_crc` chain is broken" without surfacing the breakage. **Verdict: do not make the chain a gate (that would make one corrupt line poison every later operation — the exact thing SPEC §5.2 forbids); do surface chain-break count in `RecoveryReport` next to `skipped_corrupt`, so a lost/reordered record is observable. Precedent: SQLite's cumulative checksum reports, it does not discard the WAL.**

**(c) Per-intent `sync_data()` is the strictest fsync policy of any system examined — and it is a named latency cost.** restic issues one `f.Sync()` per *pack*, tolerant of `ENOTSUP`/ENOTTY; duplicacy one per file, `ENOTSUP` tolerated, and no dir fsync at all; LMDB's `MDB_NOMETASYNC` skips the data sync while still fsyncing meta, and `MDB_NOSYNC` skips both; sled batches into `sync_file_range` on Linux and only `sync_all`s on flush/`Drop`; git-annex has **no fsync anywhere** we could find. Our `wal_intent` syncs on **every intent record**. Note 08 §Risks already flagged the ~4 ms/`F_FULLFSYNC` cost against a 10 000-file scan; the corpus adds the missing half — **the systems that skipped the per-record sync did it by making the *commit marker* the durability boundary, not the record** (redb flips one god byte then fsyncs once; jammdb writes one meta page then `sync_all`s once; LMDB writes one meta page). Our equivalent commit boundary is `checkpoint()`, and it is already the cheap path. **Verdict: keep per-intent sync for `apply`/`purge`/`restore` (each intent authorizes a real FS mutation and a lost intent means an unrecorded move — categorically different from a lost cache write), and treat any future batching as an *op-group* sync at `src/execute.rs:717`'s `sync_boundary()` call site, never a per-record relaxation.**

**(d) Our temp→sync→rename→sync-parent compaction matches five precedents and is the one place we are strictly better than one of them.** Precedents for the rename-as-commit with a directory barrier: restic `local.Save` (`os.Rename` then `fsyncDir(dir)` under the comment "Now sync the directory to commit the Rename", definition in `local_unix.go`); sled `snap.{:016X}.generating` → rename with a CRC trailer; git-annex `setJournalFile` (`withOtherTmp` + `moveFile` under the comment "The file in the journal is updated atomically"); cargo `write_atomic` (`TempFileBuilder` + `persist`); borg `write_index` (`flush_and_sync` then `os.replace`); redb's savepoint/header path. The counter-example is duplicacy, which does `.tmp` + `Sync()` + `Rename` and **no directory fsync at all**, and tolerates a lost rename by returning nil. **Verdict: our `checkpoint()` sequence is correct as written and matches the majority; no change — and the duplicacy counter-example is worth one sentence in the design doc, since it is the proof that the parent-dir barrier is load-bearing rather than ceremonial.**

**(e) Dual-slot metadata commit is the real alternative we declined — and it is worth a paragraph, not a rewrite.** LMDB (`mm_txnid` parity), redb (128-byte slots + `PRIMARY_BIT` god byte, "redb relies on the fact that this is a single byte to perform atomic commits"), and jammdb (two `Meta` pages, max `tx_id` wins behind an FNV-1a self-hash) all answer "what is the commit?" with *one atomic, self-verifying write to a fixed offset*, which needs **no replay scan at all**: recovery is a comparison of two integers. sanakirja generalises it to N versioned root pages. The cost is a fixed on-disk page format and a full-DB checksum walk on the slow path (redb's default open-after-crash repair, 1583–1590). Our JSONL WAL pays the opposite cost: an unbounded replay scan and a tail-repair problem, in exchange for an auditable, human-readable, append-only R5 台账 (`ledger.jsonl` is a *product* artifact, not just an implementation detail), per-line corruption isolation, and forward-compatible skipping (`FORMAT_V` + unknown-kind counting, git-annex's stated rationale verbatim). **Verdict: the JSONL choice is defensible on grounds the dual-slot systems cannot claim (legibility + R5 audit + unknown-format tolerance), and the design doc should say exactly that rather than implying the JSONL log is strictly better.**

**(f) Two independent corroborations of choices already made.** rclone's `RemoveExisting` (rename aside, cleanup closure that restores on failure and removes only on success) is the production shape of our quarantine-by-`renamex_np(RENAME_EXCL)` instead of `unlink` — and its companion length guard (1230–1238) is a small detail we do not have: when the existing leaf name already exceeds 100 bytes rclone **truncates the leaf** so the 9-byte random suffix still fits, rather than refusing the move. git-annex's private-journal split (`RegardingUUID`/`regardingPrivateUUID`/`privateUUIDsKnown`, `PossiblyStaleJournalledContent`) keeps a class of data out of the shared branch, at the storage layer — the same instinct as our `CandDto` path-blind chokepoint (`src/agent.rs`), but implemented in the journal rather than in the LLM boundary.

## Port backlog

Ranked. "Exact target" names the symbol in *our* repo that changes.

1. **CRC-gate the torn-tail test** — borrow borg `scan()`/`recover_segment`'s rule that a boundary is only credible after a checksum validates, and sled's XOR-complement trick so an all-zero tail can never validate. Target: `src/execute.rs::wal_has_torn_tail()` (line 222) and the call site of `sanitize_wal_tail()` (line 231), reusing `src/ledger.rs::crc_of` + `classify`. Risk **low**, size **S**. Why: this is the single place where our design is weaker than git-annex *and* every checksummed peer; a false "not torn" silently empties `RecoveryReport::torn_tail` while a false "torn" currently costs a truncated good tail. Cheap, contained, and directly testable with the existing `tests/crash_injection.rs` kill-point harness.
2. **Resync instead of truncate on mid-file WAL damage** — borrow borg's byte-advance (`d = d[1:]`) as the *last-resort* policy when a WAL line fails its CRC but later lines validate, keeping `sanitize_wal_tail`'s truncate-park behaviour only for a genuine tail. Target: `src/ledger.rs::scan_file` (used by `replay`/`checkpoint` at lines 664/709) and the `LineKind::Wal` arm. Risk **med**, size **M**. Why: today a single bad line in the middle of a WAL costs everything after it; borg, borg-master and git-annex all recover the remainder. Must preserve the SPEC §5.2 "no poisoning" guarantee, which is why this is med-risk.
3. **Give the WAL a generation salt** — borrow SQLite's `Salt-1` increment / `Salt-2` randomization per checkpoint. Target: `src/ledger.rs::checkpoint()` (line 664) — put a salt pair in the WAL's first record (or in a new header line) and require matching salts on replay, so a stale/duplicated WAL cannot be replayed into a fresh ledger. Risk **low**, size **S**. Why: our checkpoint *truncates* rather than rotates identity, so a crash that loses the truncate-and-rename mid-flight is currently distinguishable only by `seq` arithmetic; SQLite solved exactly this 20 years ago in 32 bytes.
4. **Expose chain-break accounting** — borrow SQLite's "checksums are cumulative, so a gap is visible" as an *observation*, not a gate. Target: `src/execute.rs::RecoveryReport` (line 100) — add a chain-break counter populated from `src/ledger.rs::replay` (line 709). Risk **low**, size **S**. Why: `prev_crc` is written and never read; making it observable costs nothing and converts a dead field into a lost-record detector. Explicitly *not* a refusal gate (see verdict (b)).
5. **Explicit aborted-intent kind in the WAL** — borrow sled's `MessageKind::Canceled` ("should be skipped during recovery") and okaywal's `Recovery::Abandon`. Target: `src/ledger.rs::{WAL_KIND_INTENT, WAL_KIND_RESULT}` (lines 154–155) plus the `DanglingIntent` derivation in `src/execute.rs::recover()` (line 1004). Risk **med**, size **M**. Why: today an intent whose FS mutation never ran is inferred from the filesystem (quarantine target missing) rather than recorded; a marker written before the mutation makes `DanglingIntent` a journal fact instead of a probe, and matches how both sled and okaywal encode "ignore this".
6. **Leaf-name-length guard on quarantine suffixes** — borrow rclone's `>100 byte` branch: when the quarantine target's leaf name is already long, truncate the leaf so the op-id suffix still fits instead of producing a rename that fails at the filesystem's NAME_MAX. Target: `src/execute.rs::apply` (line 532) / the quarantine path builder. Risk **low**, size **S**. Why: we append op-id material to quarantine names on paths that can already be long; rclone's guard is two lines and prevents a rename that fails only at the target filesystem's limit.
7. **Marker-last completion for multi-step restore** — borrow cargo's `.cargo-ok` (write the marker only after success; an unparsable marker means "start over"). Target: `src/execute.rs::restore` (line 861). Risk **med**, size **M**. Why: restore is the only multi-record operation; a marker makes "did the last restore finish" answerable without replaying. Lower-ranked because our WAL already carries a `result` record per operation, which is most of the same information.

## Risks & open questions

1. **The torn-tail test is the only non-checksum boundary decision in our durability path** (backlog #1). Until it is fixed, an adversarially-shaped or zero-padded tail can present as "clean", and `RecoveryReport::torn_tail` under-reports. Open question: is a false "clean" worse than a false "torn"? A false "torn" truncates a good tail (recoverable via the `.torn` sidecar); a false "clean" hands the bytes to `classify`, which counts them corrupt — so both are contained, but neither is *reported* correctly today.
2. **`F_FULLFSYNC` cost is unmeasured in-tree.** Every system examined here that skipped per-record sync did so by moving the durability boundary to a single commit write (redb's god byte, jammdb's meta page, LMDB's meta page). Our boundary is per-intent. If the design doc claims "crash-safe", it should state the measured per-intent cost, or state that the guarantee is per-intent and the batch size is 1. Note 08 §Risks already estimated ~4 ms/sync; that number was not re-verified this session (UNVERIFIED as a measurement, though the F_FULLFSYNC mechanism itself is verified in note 08 §2).
3. **Directory fsync errno tolerance.** restic's `fsyncDir` swallows `ENOTSUP`, `ENOENT`, `EINVAL` and macOS `ENOTTY` (ExFAT); our `sync_boundary()` propagates every error from `dir.sync_all()`. On an ExFAT or SMB-backed target that makes an otherwise-successful apply fail at the last step. Open question: should `sync_boundary()` adopt restic's tolerance list, and if so, must the tolerance be recorded in the report so a design-doc reader can see when durability was *not* obtained?
4. **`saved`/`torn` sidecar growth.** `sanitize_wal_tail` writes `<path>.torn` and nothing in the examined corpus prunes a sidecar (git-annex removes the journal file after staging; cargo wipes the whole directory). Open question: is a `.torn` file ever cleaned up, and is it surfaced to the user?
5. **No analogue for `RENAME_EXCL` semantics in the corpus.** borg, restic, cargo and duplicacy all use plain overwrite-`rename`; only our `renamex_np(RENAME_EXCL)` refuses to clobber. That makes our quarantine move *strictly stronger* than every precedent, but it also means there is no upstream code to borrow for the failure path (`EEXIST` → what?). This is a genuine gap in the literature this note could not close.
6. **Checksum strength.** Our crc32 is the same family as borg/sled/okaywal, and redb's doc block is explicit that a non-cryptographic checksum is defeatable by an attacker who controls write payloads *and* can crash the process. Our threat model (a local cleanup tool with a 72 h grace window and a typed-byte-count purge gate) makes that acceptable — but the design doc should say so rather than leaving "crc32" unexplained.
7. **UNVERIFIED items carried into the design doc as unresolved**: `okaywal`'s `LogFileWriter::flush()` body; `wal-rs`'s segment-level sync calls; sanakirja's `mmap.flush` → `msync` mapping; cargo's fingerprint path for git-source `cargo-ok` (all `src/core/compiler/...` guesses 404'd); the crates.io top-level `crate.license` field (returns `undefined` — per-version `license` is the authoritative field); redb 4.2.0 (latest) and sanakirja 2.0.0-beta.3 (latest) were **not** inspected — this note describes redb 2.6.0 and sanakirja 1.4.3 only.
