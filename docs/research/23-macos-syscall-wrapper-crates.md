## Findings

### 1. Rename with flags — `renamex_np` / `RENAME_EXCL` / `RENAME_NOFOLLOW_ANY`

Our `rename_no_replace` (`src/execute/macos.rs:58`) calls `libc::renamex_np(from, to, RENAME_EXCL | RENAME_NOFOLLOW_ANY)` (L64). Verdict: **no published crate wraps the flag combination we need; one maintained crate wraps half of it.**

- **libc 0.2.189** declares `renamex_np` (`src/unix/bsd/apple/mod.rs:4761`) and `renameatx_np` (L4762), plus `RENAME_SWAP` L3324 and `RENAME_EXCL` L3325. Word-boundary grep over the whole 184,777-byte file: **`RENAME_NOFOLLOW_ANY` = 0 hits, `RENAME_RESOLVE_BENEATH` = 0 hits.** The SDK (`sys/stdio.h`) defines them at L39/L40, which is why we define both locally. This gap is the reason `rename_no_replace` is raw `libc`.
- **rustix v1.1.4 DOES wrap `renameatx_np` on macOS** — correcting note 05 §Sources row `rustix`. `src/fs/at.rs:296` `pub fn renameat_with<P, Q, PFd: AsFd, QFd: AsFd>(old_dirfd, old_path, new_dirfd, new_path, flags: RenameFlags) -> io::Result<()>` (doc `#[doc(alias="renameatx_np")]`), dispatched by `src/backend/libc/fs/syscalls.rs:594` where a `weak!{ fn renameatx_np(...) }` dlopen-probes the symbol (macOS < 10.12 fallback: plain `rename` only when `flags.is_empty()` and both dirfds are `AT_FDCWD`, else `io::Errno::NOSYS` at L620). **But** the apple `RenameFlags` bitmap (`src/backend/libc/fs/types.rs:534-544`) has exactly two members: `EXCHANGE` = `RENAME_SWAP`, `NOREPLACE` = `RENAME_EXCL`. There is no `NOFOLLOW_ANY`, and the type is `#[repr(transparent)] c_uint` with `const _ = !0`, so the only way to pass the extra bit is `RenameFlags::from_bits_retain(0x10)`. Using `renameat_with` therefore buys nothing we don't already have and costs a `weak!` probe.
- **nix v0.31.3** `RenameFlags` is `#[cfg(all(target_os = "linux", target_env = "gnu"))]` (`src/fcntl.rs:449`) with only `renameat2` (L475) — **Linux-only, unusable on macOS.** Note 05 said this; confirmed at the pinned tag.
- **Roadmap column of our own table:** `trash` 5.2.8 performs no rename at all (verified: zero `rename*` occurrences in `src/macos/mod.rs`), and crates.io keyword search `renamex` returns only CLI *renamers*.

The SDK header (`sys/stdio.h` L35–40) also carries `RENAME_SECLUDE 0x1`, `RENAME_SWAP 0x2`, `RENAME_EXCL 0x4`, `RENAME_RESERVED1 0x8`, `RENAME_NOFOLLOW_ANY 0x10`, `RENAME_RESOLVE_BENEATH 0x20` — i.e. the full set we partially re-derive, and `RENAME_RESERVED1` is the one we do not define.

### 2. BSD file flags — `st_flags`, `chflags`, `UF_*`/`SF_*`

Our `lstat_flags` (`execute/macos.rs:89`) reads `lstat(p)?.st_flags as u32`; `set_hidden` (L78) ORs `UF_HIDDEN` in via `libc::chflags` and never clears; `classify/macos.rs::probe_flags` (L38) does its own `libc::lstat` + `st.st_flags` (L44–45). Verdict: **nix is the only crate with a typed `chflags`, and its flag bitmap is missing four of the six flags we use.**

- **libc 0.2.189**: `pub struct stat` L312 with `st_flags: u32` L331; `chflags(path, c_uint)` L4427 and `fchflags(fd, c_uint)` L4428. **No `lchflags`** (0 hits). Constants present: only `UF_IMMUTABLE` L3859 and `UF_HIDDEN` L3868 out of the ones we use — **`UF_DATAVAULT`, `SF_RESTRICTED`, `SF_NOUNLINK`, `SF_DATALESS`, `SF_FIRMLINK` all 0 hits.** Confirms why `classify/macos.rs:31-35` re-declares them.
- **nix v0.31.3 DOES wrap `chflags`** — correcting note 05, which listed `FileFlag` but not the function. `src/unistd.rs:4018`:
  ```rust
  #[cfg(bsd)]
  pub fn chflags<P: ?Sized + NixPath>(path: &P, flags: FileFlag) -> Result<()>
  ```
  gated by `feature!{ #![all(feature = "fs")] }` (L4011–4012) and implemented as `libc::chflags(cstr.as_ptr(), flags.bits())` (L4020). `feature = "fs"` is not in nix's `default = []` (`Cargo.toml:60` under `[features]` L57; `fs = []` is L66), so it must be opted into. There is **no `fchflags`/`lchflags` wrapper** anywhere in the crate.
- **nix's `FileFlag` is not usable as our flag vocabulary.** `src/sys/stat.rs:69-152` is `#[cfg(bsd)] libc_bitflags!`; on macOS (`type_of_file_flag = c_uint`, L64, `#[cfg(any(apple_targets, target_os = "openbsd"))]`) it offers `SF_APPEND`, `SF_ARCHIVED`, `SF_IMMUTABLE`, `SF_SETTABLE`, `UF_APPEND`, `UF_COMPRESSED` (apple), `UF_HIDDEN`, `UF_IMMUTABLE`, `UF_NODUMP`, `UF_OPAQUE`, `UF_SETTABLE`, `UF_TRACKED` (apple). **`SF_NOUNLINK` (L87) and `UF_NOUNLINK` (L123) are `#[cfg(freebsdlike)]` — freebsd/dragonfly only, NOT available on macOS**, even though the SDK defines `SF_NOUNLINK 0x00100000` for Darwin (`sys/stat.h:342`). Absent entirely on macOS: `SF_DATALESS`, `UF_DATAVAULT`, `SF_RESTRICTED`, `SF_FIRMLINK`, `SF_SYNTHETIC`, `SF_SUPPORTED`, `UF_SETTABLE`-as-mask. So `nix::unistd::chflags` can express `set_hidden` (UF_HIDDEN) but cannot express our classification mask at all.
- **nix `FileStat` is literally `libc::stat`**: `src/sys/stat.rs:5` `pub use libc::stat as FileStat;` (the `src/lib.rs:5` reference in note 05 is wrong — `lib.rs` L5 is prose in the module doc), and `stat` L214 / `lstat` L225 / `fstat` L236 / `fstatat` L248 all return `FileStat`. So `nix::sys::stat::lstat(p)?.st_flags` reaches the same field with no extra unsafe — but it is the same FFI call we already make, wrapped.
- **rustix has no `chflags`, no `fchflags`, and no `FileFlag` type** (grep over the whole v1.1.4 tarball's `src/`: `chflags` = **0 hits**, `FileFlag` = **0 hits**). **rustix's `Stat` on macOS IS libc's stat** — `src/backend/libc/fs/types.rs:975` `pub type Stat = c::stat;` under `#[cfg(not(any(linux_like, target_os = "hurd", target_os = "netbsd")))]`, re-exported through `src/fs/constants.rs:6` `pub use backend::fs::types::*` (hence `crate::fs::Stat`). macOS takes the **libc backend**: `build.rs:108-118` `let libc = feature_use_libc || cfg_use_libc || os != "linux" || …`, so `os == "macos"` makes `libc` true and `use_feature("libc")` runs at L125 (the `linux_raw` branch L126-133 is unreachable), with `use_feature("apple")` at L152. So `rustix::fs::lstat(p)?.st_flags` compiles and works — the real rustix gap is *writing* flags, not reading them. Note 05's phrasing ("no macOS rename-with-flags") conflated the two.
- **The SDK `sys/stat.h` table** (re-read this session, so the values below are primary, not quoted from 05): `UF_SETTABLE 0x0000ffff` L310, `UF_NODUMP 0x1` L311, `UF_IMMUTABLE 0x2` L312, `UF_APPEND 0x4` L313, `UF_OPAQUE 0x8` L314, `UF_COMPRESSED 0x20` L320, `UF_TRACKED 0x40` L324, `UF_DATAVAULT 0x80` L326, `UF_HIDDEN 0x8000` L330, `SF_SUPPORTED 0x009f0000` L335, `SF_SETTABLE 0x3fff0000` L336, `SF_SYNTHETIC 0xc0000000` L337, `SF_ARCHIVED 0x00010000` L338, `SF_IMMUTABLE 0x00020000` L339, `SF_APPEND 0x00040000` L340, `SF_RESTRICTED 0x00080000` L341, `SF_NOUNLINK 0x00100000` L342, `SF_FIRMLINK 0x00800000` L351, `SF_DATALESS 0x40000000` L359.

### 3. Bulk directory metadata — `getattrlistbulk`

Our scan reaches this through dua-core's walker (`src/scan/platform.rs`); the hand-rolled part is only the BSD-flag re-probe in `classify/macos.rs::probe_flags`, because **dua-core 4.0.0 does not surface `st_flags` on `Entry::metadata`**. Verdict: **the only standalone crate is too thin; the borrowable artifact is a file, not a dependency.**

- **`getattrlistbulk` 0.1.0** (quivent, MIT OR Apache-2.0, MSRV 1.70, published 2026-01-18, single release ever — `Cargo.toml:39` license, L14 `rust-version`). ### 4. APFS clonefile and clone detection

None of `clonefile`/`clonefileat`/`fclonefileat` appears in our tree; clone detection is read-only via `dir.clone_id.is_some()` → `EvidenceKind::ApfsClone` in `classify_dir` (L205 region). Verdict: **two maintained safe wrappers exist for *creating* clones; the only maintained *detection* path is dua-core's decode.**

- **libc 0.2.189**: `clonefile(src, dst, flags: u32)` L4919, `clonefileat(...)` L4920, `fclonefileat(srcfd, dst_dirfd, dst: *const c_char, flags: u32)` L4927. Note the flags parameter is `u32`, matching the SDK's `CLONE_*`, and there are no `CLONE_*` constants in libc.
- **rustix 1.1.4** wraps the fd variant: `src/fs/at.rs:447` `#[cfg(apple)] pub fn fclonefileat<Fd: AsFd, DstFd: AsFd, P: path::Arg>(src, dst_dir, dst, flags: CloneFlags)`, with `CloneFlags: u32` at `src/backend/libc/fs/types.rs:401` exposing **only `NOFOLLOW = 1` and `NOOWNERCOPY = 2`** (plus `const _ = !0`, so `from_bits_retain` covers the rest). The SDK's `clonefile.h` set is larger (`CLONE_ACL 0x4`, `CLONE_NOFOLLOW_ANY 0x8`, `CLONE_RESOLVE_BENEATH 0x10`), so rustix's coverage is partial but the `bitflags` escape hatch is present. rustix also exports `fcopyfile` + `copyfile_state_alloc/free/get_copied` (`src/fs/fcopyfile.rs:34/50/66`), re-exported at `src/fs/mod.rs:91` — the non-clone copy path with ACL/STAT preservation.
- **`reflink-copy` 0.1.30** (MIT/Apache-2.0, `Cargo.toml:38`; published 2026-06-18) hand-declares the symbol instead of using libc's: `src/sys/unix/macos.rs:18-23` `extern "C" { fn clonefile(src: *const c_char, dest: *const c_char, flags: c_int) -> c_int; }` with a local `const CLONE_NOOWNERCOPY: c_int = 0x0002;` (L16) and `// const CLONE_NOFOLLOW: c_int = 0x0001;` commented out (L15). `pub fn reflink(from, to)` L25 → `clonefile(src, dest, CLONE_NOOWNERCOPY)` L29, mapping `-1` to `io::Error::last_os_error()`. **Note the `c_int` ABI mismatch against libc's `u32`** — harmless in practice but it shows the crate prefers its own declaration. Its own TODO (L21) admits the missing weak linkage. Educational value: this is the exact 36-line shape of what we would write; the crate adds nothing over `libc::clonefile` + our own `cstr` helper.
- **`clonetree` 0.0.2** (MIT, `Cargo.toml:25`; only 2 releases; published 2025-12-06) does **not** call `clonefile` itself. Its `src/lib.rs:349 fn clone_tree_single_call` delegates: `reflink(src, dest)` L366 from `reflink-copy` (import L88 `use reflink_copy::{reflink, reflink_or_copy}`). `CloneStrategy::{Auto, FullTraversal, SingleCall}` L212, `Options::glob` L242 / `strategy` L248, `clone_tree` L256, and a non-macOS stub returning `Error::SingleCallUnsupported` L164/338. So clonetree = traversal/policy layer; the syscall belongs to reflink-copy. Relevant to disk tooling only as prior art for "clone a tree, then dedupe".

### 5. File identity without opening — `st_dev`/`st_ino`, and firmlinks

Our `lstat_identity` (`execute/macos.rs:98`) returns `(st.st_dev as u64, st.st_ino as u64)` from a raw `libc::lstat`; `lstat_dev` (L104) is the volume check used before a quarantine rename and again around the `SF_DATALESS` refusal (`execute.rs:414-423`). Call sites: `execute.rs` L276, L346, L1205, L1214, L1234. Verdict: **the available crate APIs all open the file, which this repo must not do; std already gives the same pair with zero syscalls of its own.**

- **`same-file` 1.0.6** (BurntSushi, `Unlicense/MIT`, published 2020-01-11): `src/unix.rs:60` `Handle::from_path` = `Handle::from_file(OpenOptions::new().read(true).open(p)?)` — it **opens the file for reading** and keeps the `File` (`pub struct Handle { file: Option<File>, is_std: bool, dev: u64, ino: u64 }` L9–16). `dev`/`ino` are private; equality is `PartialEq` on the pair (L31–33). A disk janitor must never open a candidate it may not have read permission for, and opening changes atime-cache/`UF_TRACKED` behaviour, so this is **explicitly not borrowable** — recorded so the rejection is on the record.
- **`file-id` 0.2.3** (notify-rs, MIT OR Apache-2.0, MSRV 1.77, published 2025-08-03; `Cargo.toml:29` license, L14 `rust-version`): single-file crate, `pub enum FileId { Inode { device_id, inode_number }, … }` `src/lib.rs:38`, `FileId::new_inode` L87, and exactly one path API: `pub fn get_file_id(path) -> io::Result<FileId>` L117, whose unix body is `fs::metadata(path)?` then `FileId::new_inode(metadata.dev(), metadata.ino())` (L120–122). **`fs::metadata` follows symlinks.** The crate's own source has **zero occurrences of `symlink_metadata` or `no_follow`** (verified by grep over the tarball: 0 hits). The no-follow variant `get_file_id_no_follow` exists **only on `notify-rs/notify` `main`** (`file-id/src/lib.rs:138-146`, `fs::symlink_metadata`), and `file-id/CHANGELOG.md` head still reads `## file-id 0.2.4 (unreleased)` with only MSRV/`#[must_use]` changes; the workspace manifest pins `file-id = { version = "0.2.3", path = "file-id" }`. **Never cite `get_file_id_no_follow` as 0.2.3 API.**
- **What we actually have, verified this session**: `std::os::unix::fs::MetadataExt::dev()`/`ino()` on `fs::symlink_metadata(path)` returns the same `(dev, ino)` pair with no open. The repo already has the raw form; the "wrapper" answer here is std's own trait, not a crate.
- **Firmlinks.** duas's `SF_FIRMLINK` const L21 and its bulk-lookup escape hatch (above) are the only maintained detection code. nix exposes the non-firmlink path resolver: `src/fcntl.rs:800` `F_GETPATH_NOFIRMLINK(&'a mut PathBuf)` (apple-gated, impl L934–936 via `libc::fcntl(fd, libc::F_GETPATH_NOFIRMLINK, buf)`), alongside `F_GETPATH` L794 → impl L913–915. rustix has the plain one only: `src/fs/getpath.rs:12 pub fn getpath<Fd: AsFd>(fd) -> io::Result<CString>`, exported at `src/fs/mod.rs:94` under `#[cfg(all(apple, feature = "alloc"))]`. Both require an open fd, so neither fits `lstat_dev` — but `F_GETPATH_NOFIRMLINK` is the typed way to answer "what real path does this fd have", which is the firmlink question we instead answer by comparing `st_dev`.

### 6. Durable sync — `F_FULLFSYNC` / `F_BARRIERFSYNC`, and `F_NOCACHE`

Our `sync_dir` (`execute/macos.rs:113`) is `fs::File::open(p)?.sync_all()`; the ledger does the durability-critical work through `Store::open`/`wal_write`/`sync_boundary` (`src/ledger.rs:445`, `L640`, `L646`). Verdict: **std already issues `F_FULLFSYNC`; the wrappers exist and are worth naming explicitly rather than adopting.**

- **Verified at the Rust source, not inferred:** `library/std/src/sys/fs/unix.rs` at tag `1.91.0`, `fn fsync` L1229, `#[cfg(target_vendor = "apple")] fn os_fsync(fd) { libc::fcntl(fd, libc::F_FULLFSYNC) }` L1233–1235; the identical apple branch for `fn datasync` L1247–1249. So `File::sync_all()` **and** `File::sync_data()` both map to `F_FULLFSYNC` on Darwin — which is exactly what `src/ledger.rs` L612/L640 and its module doc (L25 "std maps to `F_FULLFSYNC` on apple") claim. Our repo's comment is correct.

### 7. xattr, quarantine evidence, Resource-Fork and FinderInfo

`classify/macos.rs::quarantine_evidence` (L269) calls `xattr::get(path, "com.apple.quarantine")` L270 — the crate is already a declared dependency (`Cargo.toml` `[target.'cfg(unix)'.dependencies] xattr = "1.6.1"`, comment `[05][11] com.apple.quarantine probe`). - **`xattr` 1.6.1** (Stebalien, MIT OR Apache-2.0, `Cargo.toml:31`, published 2025-09-21). ### 9. The `objc2` route (and why `trash` is not a rename wrapper)

**`trash` 5.2.8** (ArturKovacs, `MIT`, MSRV 1.85.0, `Cargo.toml:40`/L14; published 2026-09-08 — the most actively maintained crate surveyed here). ## Risks & open questions

1. **`src/classify/macos.rs:32-33` carry two wrong SDK constants** (details in §2). `UF_DATAVAULT = 0x1000_0000` should be `0x00000080`; `SF_RESTRICTED = 0x0000_0800` should be `0x00080000`. Both are consumed by `classify_dir`'s block mask (L205) and `flag_name` (L280–290). The failure mode is a **false negative** (a genuinely restricted file is not recognised as write-blocked), never a false-positive delete, and neither const touches the quarantine safety path. Reported here as an observation; correcting them is outside this lane's file boundary.
2. **`classify/macos.rs:21`-style duplication is the root cause.** `execute/macos.rs:21` and `classify/macos.rs:33` both define `SF_RESTRICTED` with different values. Two definitions of one bit in one crate is the defect pattern; the fix for row 1 is arguably a single shared const module, but that is a design call, not a research finding.
3. **`extattr` 1.0.0 is `GPL-2.0-only`** (`Cargo.toml:25`) and dead since 2022-12-09. Our crate declares `edition = "2024"` and has no `license` field of its own yet. Adding it would be a licence conflict for a redistributed binary. Recorded so it never gets pulled in by a future dependency sweep.
4. **`file-id`'s no-follow API is unreleased.** `0.2.3` has `fs::metadata` (follows symlinks) only; `get_file_id_no_follow` lives on `main` and `file-id/CHANGELOG.md` still heads with `## file-id 0.2.4 (unreleased)`. Any code citing it as a 0.2.3 API is citing an unpublished API.
5. **rustix's apple `RenameFlags` cannot express our quarantine move** (`EXCHANGE`/`NOREPLACE` only; `backend/libc/fs/types.rs:534-544`), so `rename_with`/`renameat_with` are not drop-ins for `rename_no_replace`. The only ways through would be `from_bits_retain(RENAME_NOFOLLOW_ANY | RENAME_EXCL)` or `from_bits_truncate`, at which point raw `libc` is simpler and honest about being `unsafe`.
6. **dua-core's `.crate` ships no `LICENSE` file.** Its MIT claim rests on `Cargo.toml:26` inside the tarball plus the crates.io record. Both agree, but there is no in-tarball licence text to quote in the design doc's dependency table.
7. **`resource-fork` 0.3.10 was reviewed by reading `src/lib.rs` only** — its write path (`set_position` + a `Write` impl) was not exercised, and it is fd-only, so it needs an opened `File` we would not open on a candidate.
8. **`clonetree` 0.0.2 has no changelog read at source** (only its two crates.io versions: 0.0.1 2025-06-09, 0.0.2 2025-12-06). Treat its `SingleCall` strategy as unverified. It is reference-only anyway; the syscall belongs to `reflink-copy`.
9. **`getattrlistbulk` 0.1.0 is a single release** (2026-01-18) with no successor to migrate to. If we ever depend on it directly we are depending on a one-shot crate.
10. **`finder_info` 0.2.3 is edition 2018 and last released 2021-08-06** — five years stale. Any `com.apple.FinderInfo` need is vendoring, not depending. Its `kIsInvisible` (`0x4000`) is the Finder-flag mirror of `UF_HIDDEN`, which is the only reason it appears at all.
11. **`setiopolicy_np` has no wrapper anywhere** — 0 hits in libc 0.2.189's apple module, and crates.io `q=iopolicy` returns an empty result set. Note 04 already documented this; re-verified here at the pinned tag. The `extern "C"` declaration remains the only route, and we currently have no call site.
12. **Currency, not a recommendation:** our `Cargo.toml:16` pins `dua-core = "=4.0.0"`; crates.io `max_stable_version` is now **4.1.0 (2026-09-12)**. The macOS module we care about is byte-identical between the two, so the only thing a bump would buy is the CPU-vs-wall `probe_metadata` heuristic.
13. **Open question I could not close at source:** whether `RENAME_NOFOLLOW_ANY` is honoured by every filesystem we can quarantine on (HFS+ vs APFS vs network mounts). The SDK documents the flag (`sys/stdio.h:39`) but no OSS crate or test suite in this survey exercises it, so there is no upstream behaviour evidence to cite — only our own `tests/syscall_tests.rs`.
