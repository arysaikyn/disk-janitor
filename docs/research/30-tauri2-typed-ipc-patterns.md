## Findings

### A. `tauri::ipc::Channel<T>` — source internals (tauri 2.11.5)

Read from `/tmp/tauri5115/tauri-2.11.5/src/ipc/channel.rs` (extracted from `https://static.crates.io/crates/tauri/tauri-2.11.5.crate`). This is the primitive all of our progress UI rides on (7 command args in `src-tauri/src/commands.rs`).

- **Wire format = a string, not an object.** `pub struct Channel<TSend = InvokeResponseBody>` (line 50) has `impl<TSend> Serialize for Channel<TSend>` (line 88) whose body is `serializer.serialize_str(&format!("{IPC_PAYLOAD_PREFIX}{}", self.inner.id))` (line 93) — with `pub const IPC_PAYLOAD_PREFIX: &str = "__CHANNEL__:"` (line 28). So when the frontend passes a `Channel` inside the invoke args object, Tauri serializes it as `"__CHANNEL__:7"` and the Rust side rehydrates it. (**verified at source**)
- **Manual `Deserialize`, for exactly that reason.** Lines 197-205 implement `Deserialize` by hand, with the error text `expected a string in the \`__CHANNEL__:ID\` format`. `Channel` is `Serialize`-only by derive; a wrong-shaped arg produces this message. (**verified at source**)
- **`CommandArg` impl** at line 300 (`impl<'de, R: Runtime, TSend> CommandArg<'de, R> for Channel<TSend>`) deserializes via `JavaScriptChannelId::from_str` — i.e. `Channel<T>` is only usable as a **top-level command argument**, never nested inside a struct/`Option` field. This is the mechanical reason convertia's comment records "`on_scan` is NON-OPTIONAL — a FORCED deviation" from its own `onScan?` spec (their `bindings.ts` doc, line ~43). Our `start_scan(channel: Channel<ScanProgress>)` has the same property: making it optional would be impossible without a wrapper struct. (**verified at source** for the impl; convertia quote **verified at source** from their generated file)
- **Two delivery paths with size thresholds.** Line 37 `MAX_JSON_DIRECT_EXECUTE_THRESHOLD: usize = 8192`; line 39 `MAX_RAW_DIRECT_EXECUTE_THRESHOLD: usize = 1024`; line 32 `FETCH_CHANNEL_DATA_COMMAND = "plugin:__TAURI_CHANNEL__|fetch"`; line 30 `CHANNEL_PLUGIN_NAME = "__TAURI_CHANNEL__"`. Small payloads ride the direct eval path; large ones are queued (`ChannelDataIpcQueue`, line 46) and fetched. **Consequence for us: channel *ordering* is preserved but *delivery mechanism* changes with payload size** — harmless for our small `ScanProgress`/`ExecProgress`/`AgentProgressMsg` deltas, but it means a channel payload can never be assumed to be synchronous. (**verified at source**)
- **Drop-detection exists.** Line 77 `on_drop: OnDropFn` on the inner struct and line 213 `pub fn new<F: Fn(InvokeResponseBody) -> crate::Result<()> + Send + Sync + 'static>` — a `Channel` can be constructed with a callback, which is how a *dropped* channel (webview navigated away) can be observed Rust-side. We do not use this; our cancel paths rely on `cancel_scan`'s explicit command instead. (**verified at source**)
- **`send` signature** (line 292): `pub fn send(&self, data: TSend) -> crate::Result<()>`; `pub fn id(&self) -> u32` (line 287). `drain_exec(&mut ex, rx, &channel)` in our `commands.rs` passes `&Channel<ExecProgress>` into a private helper — that works because the helper does not need `CommandArg`, only `send`. (**verified at source**)
- **Nested-channel escape hatch.** Line 119 `pub struct JavaScriptChannelId(CallbackFn)` and line 132 `impl JavaScriptChannelId` with `channel_on<R, TSend>(&self, webview) -> Channel<TSend>` — for the case where a channel arrives inside a JSON object rather than as a top-level arg. Relevant only if a future command wants an options struct carrying a channel. (**verified at source**)
- **Channel payload types join the codegen export when `tauri/specta` is on.** Lines 56-61: `#[cfg(feature = "specta")] const _: () = { #[derive(specta::Type)] #[specta(remote = super::Channel)] struct TAURI_CHANNEL<TSend>(PhantomData<TSend>); }`. That is the only reason the generated TS can write `Channel<ScanProgress>` instead of `any`. (**verified at source**)
- **Tauri excludes injected args from the codegen surface** — `/tmp/tauri5115/tauri-2.11.5/src/lib.rs:1102-1133` implements `FunctionArg` returning `None` for `State<'_, T>`, `AppHandle`, `Window`, `Webview`, `WebviewWindow` under `#[cfg(feature = "specta")]`. That is what lets a command take `State<'_, ScanState>` without that argument appearing in bindings. Our `purge_plan(plan_id, typed_bytes, channel, state)` would therefore export as a **3-argument** JS function if codegen were adopted. (**verified at source**)

The derive's `event_name` option (`tauri-specta-macros/src/lib.rs:24,41,54`) overrides it. So a typed-event migration would **rename** any event whose frontend `listen("…")` string does not match the Rust type name. (**verified at source**)

### C. Command organization in real OSS apps (7 apps read at source)

Our situation is the outlier: **all 17 commands in one 1891-line `src-tauri/src/commands.rs`** (`grep -c "#\[tauri::command\]"` = 17, `grep -n "^pub async fn"` gives 17 anchors, first at line 65, last at 1700; plus `mod demo`, three inline `#[cfg(test)]` modules, and 10 private pipeline helpers).

What the surveyed apps do instead:

| App | Layout | One file? |
|---|---|---|
| Ne-IA/convertia | `src-tauri/src/ipc/{intake,planning,conversion,system}.rs` + `ipc/mod.rs`; all registered in one `collect_commands!` at `lib.rs:266` under group comments | one file **per command group**, group noted inline in the registration |
| dohooo/helmor | `src-tauri/src/commands/{common,companion_commands,editor_commands,editors,feedback_commands,forge_commands,kimi_provider_commands,local_llm_commands,mod,provider_commands,repository_commands,script_commands,session_commands,settings_commands,slack_commands,system_commands,terminal_commands}.rs` — 17 modules for one app | one file **per command**, plural `commands/` dir |

| basharovV/musicat | `src-tauri/src/db/commands.rs` | one file, but co-located with its domain (`db/`) |
| kasper9n/kadium | `src-tauri/src/{data,api,settings,db}.rs` — top-level domain modules, no `commands/` dir (tree listing read; the `generate_handler!` registration itself was not opened) | one file per **domain**, in a flat `src/` |

**The load-bearing fact for a refactor**: the JS-side command name is the **plain function name**, not the module path. `collect_commands!` strips `::<…>` and accepts `module::fn` paths (rc.25 `macros.rs`, verified above), and Tauri's own `generate_handler!` ignores the module prefix when resolving — convertia registers `crate::ipc::intake::drain_intake` and the generated surface is `commands.drainIntake(...)` (their `bindings.ts`, verified at source). **Therefore splitting `commands.rs` into modules is a zero-wire-change refactor**: `main.rs`'s `tauri::generate_handler![commands::is_demo, …]` becomes `commands::scan::is_demo, …` and nothing on the JS side moves. (**verified at source** for the macro semantics + convertia's generated names)

### D. Error-type-to-frontend: three canonical shapes, all better than `Result<_, String>`

Our current state (verified by direct read/grep): **26 `Result<…, String>` sites in `src-tauri/src/commands.rs`**, 45 `map_err`/`Err(format!` sites, and 13 `catch` blocks in the frontend rendering `String(e)` (14 occurrences of `String(e)`), e.g. `app/src/routes/PlanReview.svelte:97-98`, `Review.svelte:72-73`, `Ledger.svelte:108-109`. Nothing the frontend receives is machine-readable: the purge-mismatch refusal (the one error that *should* drive a distinct UI state — the user typed the wrong byte count) arrives as an opaque string.

Three verified alternatives:

1. **helmor `CommandError { code, message }`** (`src-tauri/src/error.rs`, Apache-2.0, 1305★). `#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)] pub enum ErrorCode { Unknown, WorkspaceBroken, WorkspaceNotFound, ForgeOnboarding, BranchInUse, BranchNotFound }`; a `CodedError { code, source }` `StdError` wrapper riding the anyhow chain (the source explains why: anyhow's `ContextError` hides the context value from `source()`, so the code cannot be recovered from the chain without a carrier type); `pub fn coded(code) -> anyhow::Error` + `AnyhowCodedExt`; `impl Serialize for CommandError` emits `#[serde(rename_all="camelCase")] struct Payload<'a> { code: ErrorCode, message: &'a str }` via `extract_code(&self.0)` + `outermost_message(&self.0)`; `impl From<anyhow::Error> for CommandError` logs the **full chain** with `tracing::error!`/`warn!`. Their module doc, verbatim: "*Internal code keeps using `anyhow::Result<T>`. At the IPC boundary, `CommandError` serialises as `{ code, message }` — the frontend reads `code` to drive recovery UX … and `message` for display.*" `pub struct CommandError(anyhow::Error)` at error.rs:93, `impl From<anyhow::Error>` at error.rs:119. **The borrowable idea for us: the code enum is the recovery-UX contract; the message is display-only.** (**verified at source**)
2. **convertia `IpcError` + message catalog** (`src-tauri/src/outcome/mod.rs`, license UNVERIFIED/NOASSERTION). `use serde::Serialize; use specta::Type;` — the derive set is `Serialize` + `specta::Type` *specifically so the kind mirrors to `bindings.ts` rather than `any`*; `pub type ErrorKind = ConversionErrorKind` (a wire alias — their source explains a first-party `From<ConversionErrorKind> for ConversionErrorKind` would be an E0119 conflict with std's reflexive blanket impl, so the projection is the identity); `OutcomeMsg::Failure { text }` carries the surfaced string; a module-scoped `#![cfg_attr(not(test), expect(dead_code, reason = …))]` keeps the not-yet-emitted variants honest. Their per-command doc states the rule categorically: "*§0.4 'Error shape' is categorical: every command returns `Result<T, IpcError>`*". **Borrowable idea: one error enum + one message catalog, so the frontend switches on a closed set and never parses text.** (**verified at source**)
3. **Front-end discriminator** — convertia `src/lib/ipc/events.ts`: `isIpcError(value)` = `typeof value === "object" && value !== null && "kind" in value && typeof (value as {kind: unknown}).kind === "string"`, used to distinguish "the backend refused, here is a structured kind" from "the transport broke, this is opaque", and to decide whether to call `handlers.onRunFault?.()`. Wrapped in `try { return await commands.startConversion(…) } catch (fault) { if (!isIpcError(fault)) handlers.onRunFault?.(); throw fault; }`. (**verified at source**)
4. bilibili-video-downloader (MIT) uses the generated `Result` envelope instead: the TS call returns `{status:"ok", data}` or `{status:"error", error}`, and Rust `CommandError` carries `err_title` + `message` (their bindings.ts read at source; the Rust side was read in the earlier pass). Their generated file's `// @ts-nocheck` header is itself a data point: the generated surface is not type-checked by default.

**Contrast with our safety architecture.** Our purge gate's whole point is that a mismatch must refuse with zero side effects (`src/execute.rs:727`, `:8` — "typed byte count to equal the plan's quarantine total — mismatch refuses"). Today that refusal crosses the IPC boundary as a `String` indistinguishable from "ledger open failed" or "manifest missing", because `purge_plan`'s body calls `find_plan_strict(&plan_id)?` (returns `Result<_, String>`) and `ex.purge(typed_bytes, tx).map_err(|e| e.to_string())?`. **This is the single highest-value borrow in the note**: a `code` field would let `app/src/routes/PlanReview.svelte` (or the purge screen) render "wrong byte count — type it again" rather than dumping `String(e)`.

### E. Typed events: verified-but-avoidable

`tauri-specta` rc.25 supports `#[derive(tauri_specta::Event)]` + `collect_events![…]` + `Builder::events(…)` + `mount_events(app)` (`src/event.rs`, `src/builder.rs:193,348`), with `Event::listen/emit` accepting any `tauri::Manager`, and per-app scoping via the `EventRegistry` state. It is a real, working feature.

**But the two strongest adopters both refuse it, and for the same verified reason.** convertia, in-source, verbatim: "*`collect_events![]` (below) stays empty BY DECISION (P2.39): the §0.4.2 app:// events are RAW `app.emit`/TS `listen` events whose payload types register via `register_ipc_event_types` (a `collect_events!` entry would force an `any`-bearing `makeEvent` helper into bindings.ts)*", and again at lib.rs:244: "*the P2.22 Throw-to-avoid-any precedent applied to events*". Their `app://fault` / `app://intake` / `app://close-requested` events therefore stay raw `app.emit` on the Rust side, with payload *types* registered via `.types()` so the TS `listen` side mirrors a named type. The `any` they are avoiding is the rc.25 `MAKE_EVENT_IMPL_TS` `(payload: any)` we verified at js_ts.rs:1055-1056.

**For us this is moot in one direction and load-bearing in another**: `grep -rn "listen\|@tauri-apps/api/event" app/src` returns **no Tauri event listener at all** — our only `listen`-shaped hits are `app/src/lib/i18n.ts:601-618`'s plain `Set<() => void>` listener registry. We use **zero** Tauri events; all streaming is `ipc::Channel`. So typed events are not a gap in our app; they would be net-new surface with a known `any` defect. (**verified at source** for our zero-event state, for the rc.25 helper text, and for convertia's stated rationale)

### F. Svelte 5 runes consuming channels — the exact rules, and our two live shapes

Source: the official Svelte 5 docs listing (`https://svelte.dev/docs/svelte/llms.txt`, saved as `/tmp/svelte_llms.txt`, 17739 lines) — line anchors below are that file. (**verified at source**)

- **A plain `.ts` module cannot hold runes — this is structural, not stylistic.** Lines 137-139: "*Besides `.svelte` files, Svelte also operates on `.svelte.js` and `.svelte.ts` files. These behave like any other `.js` or `.ts` module, except that you can use runes. This is useful for creating reusable reactive logic, or sharing reactive state across your app (though note that you cannot export reassigned state)*". Lines 437-448 give the worked example: "*You can declare state in `.svelte.js` and `.svelte.ts` files, but you can only _export_ that state if it's not directly reassigned … `export let count = $state(0); export function increment() { count += 1; }`*". **Our `app/src/lib/i18n.ts` (666 lines, plain `.ts`) documents this exact constraint in its own header** — verbatim: "*NOTE on reactivity: plain `.ts` modules are not compiled by the Svelte compiler, so `$state` runes cannot live here. Components mirror the locale into a local `$state` via `onLocaleChange()` (see Sidebar.svelte)*". Its `listeners` registry (`i18n.ts:601-618`) is the resulting observer pattern. **A future `ipc.svelte.ts` would be the idiomatic home for shared streaming state, but our current shape (component-local `onMount` + local `$state`) does not need it.**
- **`$effect` teardown is the channel-lifecycle mechanism when a stream must be re-subscribed.** Lines 701-719: "*An effect can return a _teardown function_ which will run immediately before the effect re-runs … a) … b) when the component is destroyed*"; line 732: "*Teardown functions also run when the effect is destroyed, which happens when its parent is destroyed (for example, a component is unmounted) or the parent effect re-runs.*" **Our channels are created inside `onMount(async () => …)` and never explicitly torn down** (`app/src/routes/Scan.svelte:57`, `AgentPanel.svelte:81`, `PlanReview.svelte:161`, `Ledger.svelte:217`).
- **Why our current shape is nonetheless safe**: a `Channel` is a *per-invocation* object — `start_scan`'s `channel: Channel<ScanProgress>` arg is rehydrated Rust-side per call (`CommandArg` impl, §A), the handle is dropped when the command returns, and the channel's lifetime is bounded by the call. Unlike `listen()`, there is **no global listener registry to leak into**. So note 12's risk #7 ("audit every `listen()`") is **structurally already satisfied** for us: we have zero `listen()` calls. The residual risk is the `setTimeout`-driven `pulse` decay at `AgentPanel.svelte:85` and the `Promise.race` timeout at `Scan.svelte:86` (a 60 s timer that outlives a cancelled scan) — plain timers, not channel leaks. (**verified at source** for the code shape; the "no listener leak" reasoning is [INFERENCE] from §A's per-call rehydration, stated as such)
- **The frontend-side single-IPC-home discipline** (worth borrowing if our `app/src/lib/ipc.ts` grows): convertia confines every `@tauri-apps/api` import to `src/lib/ipc/**` and enforces it with an ESLint rule; `src/lib/ipc/commands.ts` is a 25-line barrel whose comment records a real footgun — it uses `export * from "./bindings"`, NOT `export type *`, because a type-only re-export "would silently drop the generated `commands` VALUE". helmor goes further and puts a **transport shim** in `src/lib/ipc.ts`: inside the Tauri webview it delegates verbatim to `@tauri-apps/api`'s `invoke`/`Channel`/`listen`; when served by a companion HTTP/SSE server it branches on the marker `window.__HELMOR_COMPANION__` and routes to `/rpc/{cmd}` / `/rpc-stream/{cmd}` / `/v1/stream`. Their doc explains the second reason for an explicit marker: jsdom is also "not Tauri", so branching on *the framework's own presence check* would silently route tests down the wrong path. **Our `app/src/lib/ipc.ts` already implements a two-transport shim by capability sniffing (`hasTauri()`), with the same demo-fallback purpose** — verified at `ipc.ts:425-454`: `invoke<T>` branches on `!hasTauri() || demoMode || await isDemoMode()`. helmor's explicit-marker refinement is the borrowable delta if a third transport ever appears. (**verified at source**)
- **The Channel-lifecycle home**: convertia's `src/lib/ipc/events.ts` is where channels live, and it carries a **stale-walk guard**: `consumeIntakeNudge()` sets `onScan.onmessage = (message) => { …dispatch({type:"scanTick", scanned: message.scanned}) }` guarded by comparing against the current `collectingId`, so a late tick from a superseded walk cannot move the UI. **Our `app/src/routes/Scan.svelte` has the analogous hazard**: `onMount` assigns `ch.onmessage` and the surrounding component tracks `canceled`; the 60 s `Promise.race` can resolve *after* a cancel. A `collectingId`-shaped guard is the concrete pattern to borrow. (**verified at source** for convertia's guard; the analogous hazard is [INFERENCE] from our code)

### G. Migration verdict

**Do NOT adopt `tauri-specta` now. DO adopt the error-shape pattern.** Four verified reasons against codegen today, one verified reason for the error pattern.

Against codegen, ranked by severity:

1. **Every version is a pre-1.0 RC and every adopter pins a *different* one.** `tauri-specta 2.0.0-rc.25` / `specta 2.0.0-rc.25` / `specta-typescript 0.0.12` (all `MIT`, read from crates.io `/versions` 2026-09-13) versus kadium (`tauri-specta = "=2.0.0-rc.21"` + `specta = "=2.0.0-rc.22"` + `specta-typescript = "0.0.9"`, and it *patches tauri from a fork branch*) and bilibili (rc.20 / 0.0.7). The crate's own README says use `=`. **There is no stable target to adopt; adopting means adopting one specific RC forever.**
2. **`-rc` version resolution is genuinely unsafe here.** `tauri-specta` rc.25's dependency edge is `tauri = { version = "2", features = ["specta"] }` (caret, read from the tarball), and `tauri 2.11.5`'s own `[dependencies.specta]` is `version = "^2.0.0-rc.16"` with `optional = true` (read from `/tmp/tauri5115/tauri-2.11.5/Cargo.toml`). So the *exporter* was built against `=2.0.0-rc.25` while the *runtime* accepts any `2.0.0-rc.*` ≥ rc.16 — a resolution that silently pairs an exporter with a specta it was not compiled against. Pinning `=` on all four crates is the only safe configuration, which is exactly what every adopter does.
3. **The published rc.25 emits `any` for events, so the "fix schema drift" premise is half-false.** js_ts.rs:1055-1056 `MAKE_EVENT_IMPL_TS` = `(payload: any)` / `__TAURI_EVENT.Event<any>`. convertia, the highest-structure adopter, deliberately keeps `collect_events![]` empty for this reason and registers payload types through `.types()` instead. (We have zero Tauri events, so this cost is theoretical for us — but it means codegen would *not* deliver end-to-end typing.)
4. **Codegen's type safety is opt-in per type, so a partial migration degrades to `any`.** There is no `collect_types!` in rc.25; every standalone type must be `.register::<T>()`-ed or reached from a command signature. convertia's own source warns a future argument reaching an unregistered type "would emit `any`". Combined with our `--demo-data` mirror (see Risks), a partial adoption is the *most likely* outcome and it produces exactly the drift symptom we were trying to fix.

Plus two practical costs: adopting means adding `#[specta::specta]` to all 17 `#[tauri::command]` fns (the macro docs' own example does), and `tauri/specta` + the three crates enter our dependency closure. If codegen is ever wanted, the cheap escape is convertia's dev-only trick — read from their `src-tauri/Cargo.toml` verbatim: `[dev-dependencies]` carries `specta-typescript = "=0.0.12"` and `tauri-specta = { version = "=2.0.0-rc.25", features = ["derive", "typescript"] }`, with the comment "*DEV-ONLY by design … under resolver 2 a feature requested only by a dev-dependency is NOT unified into the normal/release build, so the shipped MIT-core binary stays free of the TS-exporter code*". Their codegen is a **test** (`bindings_codegen`) driven by `cargo run -p xtask -- codegen`, and their `package.json` has **no** bindings npm script. That is the pattern to copy if bindings are generated at all.

For the error pattern: our 17 commands return `Result<T, String>`, the frontend renders `String(e)` at 14 sites, and the purge-mismatch refusal — the one error with a *distinct correct UI response* — is indistinguishable from an I/O failure. helmor's `{ code, message }` (Apache-2.0) and convertia's `IpcError`/`ErrorKind` + catalog both solve exactly this, at the cost of one enum plus one `impl Serialize`. **This is the recommendation.**

Interim (if even that is too much for the 9.13 deadline): a *minimal* version — keep `Result<T, String>` but prefix machine-readable tokens (`"E_BYTES_MISMATCH: …"`), letting the frontend `startsWith`-match. Strictly worse than an enum, strictly better than today, and ~20 lines.

### H. i18n

Note 12 already settled `svelte-i18n` 4.0.1 vs paraglide; **nothing here reopens that**. The only NEW, source-verified fact: our i18n module is a plain `.ts` (`app/src/lib/i18n.ts`, 666 lines) and therefore *cannot* hold `$state` — Svelte's own docs make the `.svelte.ts` extension the requirement (lines 137-139, quoted in §F), and our module header states the same conclusion independently. `getLocale`/`setLocale`/`onLocaleChange(fn): () => void`/`t`/`formatInt` is the correct shape for that constraint: an observer registry (`listeners = new Set<() => void>()` at line 601, subscribe at 615-619) with components mirroring into local `$state`. **If locale state ever needs to be shared without a component middleman, the fix is renaming to `i18n.svelte.ts` and using `$state` — not adopting a different i18n library.** Switching languages is therefore a no-IPC concern: it never touches the Rust boundary, and no channel re-subscription is required.

## Risks & open questions

1. **RC pinning is permanent and transitive.** Adopting codegen means pinning four crates with `=` (`tauri-specta`, `specta`, `specta-typescript`, and effectively `specta-serde`/`specta-util`) forever, because `tauri-specta`'s own edge is the caret `tauri = "2"` and `tauri 2.11.5`'s specta edge is the pre-release caret `^2.0.0-rc.16`. There is no stable target. Every adopter's differing pin set is evidence, not coincidence.
2. **`any` is unavoidable in the rc.25 typed-event path.** `MAKE_EVENT_IMPL_TS` (`(payload: any)`, `Event<any>`) is emitted whenever `collect_events!` is non-empty. Since we currently use **zero** Tauri events, codegen would buy us nothing on that axis and could *introduce* the helper if a typed event were ever added.
3. **The `--demo-data` mirror is a third drift surface, not a second.** `app/src/lib/ipc.ts` hand-mirrors the `commands.rs` DTOs **and** `demo()` must stay in sync with `mod demo` in `commands.rs` (the source comments in both files say so). Codegen can de-duplicate the *type* half only; the *value* half (`demo::purge_report`, the synthetic `{t:"finished"}` envelope) stays hand-written. A codegen migration that stops at types would leave demo-path drift equally unguarded — and the demo path is exactly what the recorded 课堂展示 demo runs on.
4. **Channels are outside the capability system.** `src-tauri/capabilities/main-cap.json` grants `core:default`, `dialog:default`, `opener:default`, `core:window:allow-start-dragging` — and nothing else; there is no channel-scoped permission because the `__TAURI_CHANNEL__` fetch commands are core-internal (`tauri 2.11.5/src/ipc/channel.rs:30-32`, verified). So a channel argument is governed only by the command that declares it. **This is correct by design but means "the popup is typecast" claims should be phrased as "the command is capability-scoped; its channel rides the command"** — relevant if the 设计文档's security section leans on capabilities.
5. **`ErrorHandlingMode` choice determines the frontend `catch` shape**, and it is a one-way door for every call site: `Result` wraps errors in `{status:"error"}` (bilibili) while `Throw` rejects (convertia). Our frontend already uses `try/catch` + `String(e)`, so `Throw` is the smaller diff — but adopting codegen at all is what forces the choice.
6. **`Channel<T>` cannot be optional.** Verified from the `CommandArg` impl (`channel.rs:300`) — it deserializes from a top-level string, so an `Option<Channel<T>>` argument is not expressible without a wrapper type. Any future "make progress reporting optional" idea in a design doc must not assume `onProgress?` is free.
7. **The i18n module cannot become reactive without a rename.** `app/src/lib/i18n.ts` is plain `.ts`; `$state` requires `.svelte.ts` (Svelte docs lines 137-139). Switching languages is correctly an in-webview concern that never crosses IPC — but if a future screen wants locale state *without* a component intermediary, the answer is renaming to `i18n.svelte.ts`, not a different i18n library.
8. **Open question (unresolved):** whether a partial codegen adoption is worth it for the ten `*Dto` types that already have exact TS mirrors (`VolumeDto`, `EvidenceDto`, `CandidateDto`, `ScanManifestDto`, `PlanEntryDto`, `PlanTotalsDto`, `PlanDto`, `LedgerEnvelopeDto`, `AgentSummary`, `SessionMeta`). A `ts-rs`/`typeshare` test-time pass could generate those ten `.d.ts` declarations without touching the command registry at all — no `#[specta::specta]`, no `Channel` typing, no `makeEvent`. Cost: a second annotation system (`#[derive(TS)]`) alongside serde. **Not verified against a working Svelte 5 + `ts-rs` setup in this lane** — flagged as worth a spike, not as a recommendation.
