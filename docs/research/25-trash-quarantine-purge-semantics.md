# Trash → Quarantine → Purge: Move, Restore & Collision Semantics in OSS — Research Note

Exact move/restore/collision/purge mechanisms — the functions, syscalls and guard predicates, not the product landscape — in the OSS trash, backup-prune and duplicate-deleter families, mapped onto our `Executor::{apply,purge,restore}` + `recover()` surfaces · researched 2026-09-13

Scope: the *mechanism layer* of file lifecycle — how a candidate becomes a moved object, what metadata records the undo, what happens when the restore target is occupied, and which predicate blocks a destructive step. Read: trash-rs 5.2.8, GNOME glib/gio, `rmw`, `gtrash`, restic, rmlint, jdupes, fclones 0.35.0, dupeGuru, BleachBit 6.0.4, GNU coreutils `shred`. ## Findings

### 1. The FreeDesktop trash family — four independent implementations of one spec

The XDG trash spec ("write metadata, then move") is implemented four times in the wild, and the four disagree on the two things that matter to us: *when* the metadata is written relative to the move, and *what* happens when the move cannot be a same-device rename.

| Project | Metadata written | Move | Cross-device | Collision on restore |
|---|---|---|---|---|
| trash-rs 5.2.8 | **before** the move; unlinked if the move fails | `std::fs::rename` | `copy_dir_all` / `fs::copy` + `remove_*` | `create_new(true)` probe → `Error::RestoreCollision`, **halts**, leaves `remaining_items` |
| gio (glib) | before the move; `g_unlink` on rename failure | `rename()` | **refuses**: `G_IO_ERROR_NOT_SUPPORTED`, "Unable to trash file %s across filesystem boundaries" | overwrites (`g_file_move` semantics) |
| rmw | before the move | `rename()` | **only** on `EXDEV` → `ficlone_move` | appends a **time-string suffix**, never overwrites |
| gtrash | before the move (`O_EXCL` claim) | `os.Rename` | n/a | `checkRestoreDup` → `"canceled: restore conflict detected"` |

**trash-rs `move_to_trash`** ([`src/freedesktop.rs:465`](https://raw.githubusercontent.com/Byron/trash-rs/836b6e50e6fc3cd0e6cbfd88f0b389b5e669432a/src/freedesktop.rs)) is the closest code analogue to our `Executor::apply`. It builds the in-trash name from the original filename, appends `.trashinfo`, and claims the info file with `OpenOptions::new().create_new(true).write(true).open(&info_file_path)` (`:509`) — i.e. the **existence check is the syscall**, exactly the property our `renamex_np(RENAME_EXCL)` gives us on the payload side. It then writes `[Trash Info]` + `Path=` + `DeletionDate={now.format("%Y-%m-%dT%H:%M:%S")}` (`:522`, `:529`) and only afterwards performs the move; `try_creating_placeholders` (`:598`) pre-creates the destination with `create_new(true)` (`:607`) so the `rename` cannot silently clobber. The `.<n>` unique-name loop in [`src/lib.rs`](https://raw.githubusercontent.com/Byron/trash-rs/836b6e50e6fc3cd0e6cbfd88f0b389b5e669432a/src/lib.rs) walks suffix revisions on `EEXIST`. `restore_all` (`:360`) probes the restore target with `OpenOptions::new().create_new(true).write(true).open(&original_path)` (`:396`) and on failure returns `Err(Error::RestoreCollision { path, remaining_items })` (`:406`) — a **hard stop**, not a skip. The variant `Error::RestoreTwins` (`src/lib.rs:205`, raised at `:540`) covers two trash items mapping to the same original path.

The ordering is the borrowable idea: metadata first, payload second, **unlink the metadata if the payload move fails**. Our WAL equivalent is `WalKind::Intent` written before the `renamex_np` call and `WalKind::Result` after it, with `recover()` doing exactly this reconciliation — so we already have the stronger version (see Port backlog row 1 for the one gap: our failure path leaves an intent rather than an explicit negative record).

**gio** ([`gio/glocalfile.c`](https://raw.githubusercontent.com/GNOME/glib/50d402c78a496e0fe51a846803a94b77285d6ab3/gio/glocalfile.c)) is the strictest: `if (global_stat.st_mode & S_ISVTX) != 0` at `:2040` and `:2331` refuses a `$topdir/.Trash` that lacks the sticky bit, `:2321` refuses "Trashing on system internal mounts", `:2616` returns `_("Unable to trash file %s across filesystem boundaries")` mapped to `G_IO_ERROR_NOT_SUPPORTED` — **gio has no copy+delete fallback at all**. It claims the info file with `g_open(infofile, O_CREAT | O_EXCL | O_CLOEXEC, 0666)` (`:2467`), removes directories only after `check_removing_recursively(file, TRUE, uid, ...)` (`:2129`) re-validates ownership of every descendant, and creates the per-user fallback root with `g_mkdir(trashdir, 0700)` (`:2347`, `:2361`). The macOS branch is [`gio/glocalfile-osx.m:69`](https://raw.githubusercontent.com/GNOME/glib/50d402c78a496e0fe51a846803a94b77285d6ab3/gio/glocalfile-osx.m): `if (![file_manager trashItemAtURL:url resultingItemURL:NULL error:&ns_error])` — the NSFileManager path, with **no Finder fallback** (contrast trash-rs below).

**rmw** ([`src/restore.c`](https://raw.githubusercontent.com/theimpossibleastronaut/rmw/d77b222eb5338fe484c48bc9460968e84d557bd6/src/restore.c)) has the most direct answer to our D-26 keep-both default. `move_back()` (`:63-83`) is a plain `rename(src, dest)` with a **fallback on `EXDEV` only** to `ficlone_move`; there is no `RENAME_NOREPLACE`, so the collision check is an explicit preceding `stat`: `if (path_status(dest) == EEXIST)` (`:142`) appends `st_time_var->suffix_added_dup_exists` and logs `verbose_printf(1, "Duplicate filename at destination - appending time string...\n")` (`:151`). Two guards we lack: `:104` refuses any source not under a known waste directory (`"'%s' is not in a Waste directory.\n"`) and `:112` `isdotdir(src_basename)` refuses `.`/`..`. `:167` recreates a missing parent with `rmw_mkdir(parent_dir)` — the same fix as our C2 (`fs::create_dir_all` on the original parent). `:197` makes dry-run skip every mutation. In [`src/purging.c`](https://raw.githubusercontent.com/theimpossibleastronaut/rmw/d77b222eb5338fe484c48bc9460968e84d557bd6/src/purging.c), `purge()` (`:232`) prints `purging is disabled ('%s' is set to '0')` when `expire_age == 0`; the per-item age comes from the `.trashinfo` **DeletionDate**, not mtime (`get_then_time` → `strptime(raw, "%Y-%m-%dT%H:%M:%S", &tm_then)`), and the gate is `double days_remaining = ((double) then + (SECONDS_IN_A_DAY * st_config_data->expire_age) - st_time_var->now) / SECONDS_IN_A_DAY;` then `bool want_purge = days_remaining <= 0 || want_empty_trash;` (`:299`). `do_file_purge()` (`:130`) removes the payload **then** the `.trashinfo`, warning `"You can remove the trashinfo file with '-offg'"` if the payload is already gone. [`src/topdir_trash.c`](https://raw.githubusercontent.com/theimpossibleastronaut/rmw/d77b222eb5338fe484c48bc9460968e84d557bd6/src/topdir_trash.c) is the most careful eligibility table found: `pseudo_fs_list` (`:60`, proc/sysfs/devtmpfs/devpts/cgroup*/bpf/securityfs/debugfs/tracefs/pstore/mqueue/hugetlbfs/fusectl/configfs/autofs/binfmt_misc/rpc_pipefs/nsfs/efivarfs) is never probed; `extra_exclude_list` (`:68`, tmpfs/overlay/squashfs/cifs/smbfs/smb3/`fuse.*`) never gets a *new* trash but an *existing* one is still honoured (`:97`); symlinks are skipped with `"%s is a symbolic link; ignoring per trash spec"` (`:212`) and missing sticky bit with `"%s lacks the sticky bit; ignoring per trash spec"` (`:215`); `mount_is_eligible` (`:101`) rejects read-only mounts and any mount failing `access(mount_path, W_OK)` (`:114`). **NFS is deliberately not excluded.**

**trash-rs on macOS** ([`src/macos/mod.rs`](https://raw.githubusercontent.com/Byron/trash-rs/836b6e50e6fc3cd0e6cbfd88f0b389b5e669432a/src/macos/mod.rs)) is included for contrast only — it is *not* a candidate mechanism for us. `:13` documents two implementations, `:23` `/// Use an `osascript`, asking the Finder application to delete the files.` (produces the Finder sound and the "Put Back" menu entry, `:26-27`) versus `NsFileManager` (faster, silent, and **no Put Back** because of a known macOS bug, `:30-42`); `:45-47` `DeleteMethod::default()` is `DeleteMethod::Finder`. ### 2. restic — the only project found that gates a bulk delete on a *paired* safety flag

restic's `forget`/`prune` pair is the closest OSS analogue to "grace window elapses → user types the byte count → we purge", and it is the source of the strongest borrowable guard pattern in this note: **a dangerous flag is only accepted when a second, narrowing flag is also present.**

[`cmd/restic/cmd_forget.go`](https://raw.githubusercontent.com/restic/restic/ba802d42b7294c98b62c16d1157ea3e80820c019/cmd/restic/cmd_forget.go): `:142` declares `--unsafe-allow-remove-all` ("allow deleting all snapshots of a snapshot group"), and the enforced pairing is at `:246`:

```go
return errors.Fatal("--unsafe-allow-remove-all is not allowed unless a snapshot filter option is specified")
```

reached from `:245` `if opts.SnapshotFilter.Empty()`. The baseline refusal (`:249`) is `"no policy was specified, no snapshots will be removed"` (`:254`) — **absence of a policy is a refusal, not a default**. Per-group floor at `:281`: `return fmt.Errorf("refusing to delete last snapshot of snapshot group \"%v\"", key.String())`, evaluated as `if !policy.Empty() && len(keep) == 0`. And the preview is a first-class code path, not a logging accident: `:334` `printer.P("Would have removed the following snapshots:\n%v\n\n", removeSnIDs)`. `--no-lock` is only honoured with `--dry-run`: `:190` `return errors.Fatal("--no-lock is only applicable in combination with --dry-run for forget command")`.

[`cmd/restic/cmd_prune.go`](https://raw.githubusercontent.com/restic/restic/ba802d42b7294c98b62c16d1157ea3e80820c019/cmd/restic/cmd_prune.go) repeats the same pairing at `:175` (`--no-lock` requires `--dry-run`), and adds a *tolerance* parameter that is the best available precedent for a grace window expressed as a quantity rather than a time: `:81` `f.StringVar(&opts.MaxUnused, "max-unused", "5%", "tolerate given `limit` of unused data ...")`. It is validated hard before any work: `:111` `"invalid value for --max-unused: %q"`, `:125` `"invalid percentage %q passed for --max-unused: %v"`, `:129` `"percentage for --max-unused must be positive"`, `:133` `"percentage for --max-unused must be below 100%"` — note that **`0%` and `100%` are both rejected**, so the parameter can never be turned into an unbounded delete. `:82` `--max-repack-size` bounds *total* work ("stop after repacking this much data in total"), and `:76` `--unsafe-recover-no-free-space` carries `"UNSAFE, READ THE DOCUMENTATION BEFORE USING!"` in its own help text. The dry-run flag is `:75` `f.BoolVarP(&opts.DryRun, "dry-run", "n", false, "do not modify the repository, just print what would be done")` and the exclusive lock is opened differently for dry runs: `:179` `openWithExclusiveLock(ctx, gopts, opts.DryRun && gopts.NoLock, printer)`.

The retention policy engine lives in `internal/data/snapshot_policy.go`: `ExpirePolicy{Last, Hourly, Daily, Weekly, Monthly, Yearly, Within, WithinHourly…WithinYearly, Tags}`, `Empty()`, `ApplyPolicy(list, p) (keep, remove, reasons)`, and `findLatestTimestamp` which **ignores future-dated snapshots relative to `time.Now()`** — a clock-skew guard directly relevant to our `undo.grace_expires_at` comparison. `-1` means "keep all"; `--keep-within` means "keep snapshots newer than `duration` relative to the latest snapshot", i.e. the window is anchored to the newest item, not to wall clock. Our `recover()` anchors differently (`if undo.grace_expires_at >= Utc::now() { continue; }`, `src/execute.rs:1053`) — a per-entry absolute deadline, which is strictly simpler and, unlike restic's relative anchor, cannot be moved by the arrival of new entries.

### 3. Duplicate deleters — four different answers to "which one survives, and what re-checks it first"

This family is structurally ours: a set of paths was chosen earlier, and a later phase performs the destructive action. All four re-verify something immediately before removal; **none of them re-verifies "the file still exists and is still the same inode" the same way**, so the union is worth having.

**fclones 0.35.0** ([`fclones/src/dedupe.rs`](https://raw.githubusercontent.com/pkolaczk/fclones/a74f90d293e05856d19a4c0ac2b29b46ef16cf23/fclones/src/dedupe.rs)) is the strongest fit for our two-phase `plan::build` → `Executor::apply` split, because the phases are separated by an on-disk artifact and share a timestamp. `:915` `pub fn dedupe<...>` documents "Calling this is perfectly safe - the function does not perform any disk changes", and lists its refusals: it rejects a whole group if metadata cannot be read or if any member "was modified after the `modified_before` configuration property"; it never emits a removal command for a file whose length no longer matches the scanned length, one matched by `retain_path`/`retain_name`, or one not matched by every `drop_path`/`drop_name`. The enforcement is `:846` `if was_modified(&files, max_timestamp, log)` inside `partition`, where `modified_before` is defaulted from the *previous scan's* timestamp so **anything touched between scan and delete is excluded automatically**. The keep floor is `:878` `let n = max(1, config.rf_over.unwrap_or(1));` followed by `assert!(to_retain.len() >= n || to_drop.is_empty());` (`:887`) — a `max(1, …)` so the floor can never be zero, plus a debug assertion.
`:959` `pub fn run_script<I>(script, should_lock, log) -> DedupeResult` documents the opposite contract from `dedupe`: "Calling this is going to change the contents of the file-system. No safety checks are performed ... On command execution failure, a warning is logged and the execution of remaining commands continues." The single-command undo primitive is `:278` `pub fn safe_remove<R>(path, f, log)`: it renames the victim to `temp_file(path)` (`:257`) **first**, runs `f` on the original path, and on `Err(e)` renames back, logging `"Failed to undo move from {} to {}: {}"` (`:291`) if even the undo fails; on success it removes the temp (`:301`). Destruction is therefore never "remove in place" but "rename away, attempt, restore on failure" — the same shape as our quarantine move, applied at single-file granularity. Collision is checked explicitly before any rename: `:180` `fn check_can_rename` with `:185` `"Cannot move {} to {}: Target already exists"`. Previews are *generated code*: `:376` and `:431` `pub fn to_shell_str(&self) -> Vec<String>`, and `src/main.rs` sets `dedupe_config.output = log_script(...)` when `--dry_run`, printing "Would process {} files and reclaim {}{} space" versus "Processed …" otherwise. [`fclones/src/config.rs`](https://raw.githubusercontent.com/pkolaczk/fclones/a74f90d293e05856d19a4c0ac2b29b46ef16cf23/fclones/src/config.rs) defines the knobs: `:589` `pub dry_run: bool`, `:604` `pub modified_before: Option<DateTime<FixedOffset>>`, `:614` `pub rf_over: Option<usize>` with `:259` `#[arg(long, conflicts_with("rf_over"), value_name("COUNT"))]` on its neighbour, and `:458-467` `pub fn rf_over(&self) -> usize`.

**rmlint** ([`lib/formats/sh.sh`](https://raw.githubusercontent.com/sahib/rmlint/d37815462a506e9edd022272530eb323324e50b8/lib/formats/sh.sh), emitted by [`lib/formats/sh.c`](https://raw.githubusercontent.com/sahib/rmlint/d37815462a506e9edd022272530eb323324e50b8/lib/formats/sh.c)) is the "generate a reviewable artifact, then run it" pattern. `original_check()` at `:157` is the pre-mutation predicate, run by every mutating branch (`:188`, `:213`): it aborts if the *original* has disappeared (`"Error: original has disappeared - cancelling....."`), if the *duplicate* has disappeared, if `[ "$1" = "$2" ]` ("original and duplicate point to the *same* path"), and — only under `DO_PARANOID_CHECK` — if `check_for_equality` (`cmp -s -- "$1" "$2"` for files, `"$RMLINT_BINARY" -p --equal %s --` for directories) now says "files no longer identical - cancelling". So **the default path validates existence of both endpoints; the `-p` flag escalates to content re-verification.** Every mutation is wrapped in `if [ -z "$DO_DRY_RUN" ]; then` (`:90/98/106/114/122/130/138`). The script carries hardlinks correctly: it skips when `rm_file_inode(self->last_original) == rm_file_inode(file)`. The gate is `ask()` (`:325`), which prints "This script will delete certain files rmlint found." / "It is highly advisable to view the script first!" then `read -r eof_check`; empty input or Ctrl-D exits 1 (`:338-343`). Default behaviour deletes the script after it runs (FOOT, `:412`: `if [ -z $DO_REMOVE ]` → prints "This script will be deleted after it runs"); `-x` keeps it, `-d` skips the ask, `-n` is a dry run implying `-d -x`.

**jdupes** ([`act_deletefiles.c`](https://raw.githubusercontent.com/h2oai/jdupes/a8b0812a7c54d21f910a15d8a90a9b5001a48e2c/act_deletefiles.c)) encodes the "never delete the whole set" invariant as a loop condition rather than an assert: `:100-101` in non-prompt mode sets `preserve[1] = 1; for (x = 2; x <= counter; x++) preserve[x] = 0;` (**the first file survives by default**), `:119` `if (!fgets(preservestr, INPUT_SIZE, tty)) preservestr[0] = '\n';`, `:122` `if (preservestr[0] == '\n') strcpy(preservestr, "a\n");` (**empty input keeps everything**), `:164` an invalid character prints `"error: invalid character '%c' in preserve answer; taking no action"` and `goto skip_deletion`, and `:211` `} while (sum < 1); /* save at least one file */`. Per-file staleness is re-checked immediately before each removal: `:220` `if (file_has_changed(dupelist[x]))` guards each `jc_remove`. The escalation ladder in [`jdupes.c`](https://raw.githubusercontent.com/h2oai/jdupes/a8b0812a7c54d21f910a15d8a90a9b5001a48e2c/jdupes.c) is the most explicit "confirm you understand" ceremony found: one `-T/--partial-only` prints a "BIG FAT WARNING … YOU WILL LOSE DATA", two `-T` prints "You passed -T twice ... HIT CTRL-C TO ABORT IF YOU AREN'T CERTAIN!" then runs `for (int countdown = 10; countdown > 0; countdown--) { fprintf(stderr, "%d, ", countdown); sleep(1); }`, three `-T` skips the reminder entirely ("You're a wizard"). Destructive modes are mutually exclusive at the option parser: `:601-609` rejects combining "Only one of --summarize, --print-summarize, --delete, --link-hard, --link-soft, --json, --error-on-dupe, or --dedupe may be used", and `:586` rejects `--summarize` with `--delete`. Dispatch is `:777-780`: `deletefiles(files, 0, 0)` with `F_NOPROMPT`, else `deletefiles(files, 1, stdin)`.

**dupeGuru** ([`core/app.py`](https://raw.githubusercontent.com/arsenetar/dupeguru/db097a030150b3d4ea9f492b85e7e4e4bcb3f789/core/app.py)) is the weakest of the four but shows the "ask once, then act blind" shape: `_do_delete` (`:226`) / `_do_delete_dupe` (`:234`) branch on `if direct_deletion:` → `shutil.rmtree`/`os.remove`, else `send2trash(str_path)  # Raises OSError when there's a problem` (`:245`), then optionally relink with `linkfunc = os.link if use_hardlinks else os.symlink` (`:246`) and `self.clean_empty_dirs(dupe.path.parent)` (`:281`). [`core/gui/deletion_options.py`](https://raw.githubusercontent.com/arsenetar/dupeguru/db097a030150b3d4ea9f492b85e7e4e4bcb3f789/core/gui/deletion_options.py) shows the consent model: `DeletionOptions.show(mark_count)` resets the flags, prompts `tr("You are sending {} file(s) to the Trash.").format(mark_count)`, and returns `self.view.show()` — cancel means no deletion at all. `supports_links()` feature-detects by calling `os.symlink()` and catching `TypeError` (supported) versus `NotImplementedError`/`OSError` (unsupported) — capability probing by attempted syscall, not by platform name. `core/engine.py` contains **no** `trash`/`unlink`/`os.remove` at all; deletion lives exclusively in `app.py`, i.e. a single choke point for the destructive verb.

### 4. The overwrite/irreversibility family — what "purge" means when the contract is *no undo*

Our purge is a `remove_dir_all`/`remove_file` behind a typed-byte-count gate; the window between "quarantined" and "purged" is 72 h, and after purge there is no undo by design. Two projects in this space have written down *exactly* what that costs, and both are worth quoting in the design doc rather than borrowing code from.

**GNU coreutils `shred`** ([`src/shred.c`](https://raw.githubusercontent.com/coreutils/coreutils/6ff3889887604fd4fd432edce336b4ac63d8ae5a/src/shred.c)) states the assumption and its counterexamples in the `--help` text itself (`:238-242`):

```
CAUTION: shred assumes the file system and hardware overwrite data in place.
Although this is common, many platforms operate otherwise.  Also, backups
and mirrors may contain unremovable copies that will let a shredded file
be recovered later.  See the GNU coreutils manual for details.
```

The `--remove=HOW` parameter (`:225-236`) enumerates the removal policies as an enum, not a boolean: `:111-126` `enum remove_method { remove_none = 0, /* the default: only wipe data. */ remove_unlink, remove_wipe, remove_wipesync }` with `'unlink' => use a standard unlink call.\n'wipe' => also first obfuscate bytes in the name.\n'wipesync' => also sync each obfuscated byte to the device.\nThe default mode is 'wipesync', but note it can be expensive.` The default is **not to remove at all** ("The default is not to remove the files because it is common to operate on device files like /dev/hda") — destructive removal is opt-in per invocation. `:309-341` has best-effort `fdatasync`/`fsync` helpers documented as "It is not an error if fdatasync and/or fsync is not supported", and the file header notes "If asked to wipe a file, this also unlinks it, renaming it in a clever way to try to leave no trace of the original filename." The header also flags the unresolved race we care about (`:67-68`): "Security: Is there any risk to the race between overwriting and unlinking a file?" **[INFERENCE]** For us the relevant takeaway is negative: on APFS/SSD, an overwrite pass is not a guarantee, so the note should not claim shred-style erasure anywhere; "purge" must be described as *directory-entry removal* with the byte count as the user's assertion of scope.

**BleachBit 6.0.4** (_read from source this session; its `Command.py` could not be fetched — see Risks_) is the project that most carefully avoids destroying something the user did not intend, and its two mechanisms are directly portable.
`bleachbit/ProtectedPath.py` ([source](https://raw.githubusercontent.com/bleachbit/bleachbit/e2455c9354f8da4270363b56182139bc25710fd7/bleachbit/ProtectedPath.py)) loads a declarative `protected_path.xml`, rejecting DTDs (`reject_xml_dtd`), with entries carrying `{path, depth (0=exact, 1=children, ..., None="any"), case_sensitive}` (`:96-104`). `check_protected_path(user_path)` (`:156`) first exempts `~/.cache`, `%temp%`, `%tmp%`, `/tmp` via `_check_exempt` (`:133`), then matches three ways: equality, **the user path is a parent of a protected path**, or the user path is a descendant within `depth` levels (`:200-210`, `if ((depth is None or depth > 0) ... if levels <= depth`). Two consequences we do not have today: a *parent-of-protected* match means selecting `/Users/x` is refused because `/Users/x/Documents` is protected, and `depth: None` means "any depth, forever". Matching is case-insensitive by default on macOS. `calculate_impact(path)` (`:216`) returns `{file_count, total_size, size_human}` and `get_warning_message(user_path, impact)` (`:260`) prints `"Warning: '%(path)s' may contain important files.\n\nImpact: %(files)d file(s), %(size)s\n\nAre you sure you want to add this path?"` (`:277`, `:289`) — **quantify, then confirm with the number in the prompt**. That is the same rhetorical move as our typed byte count, but applied at *selection* time rather than at *purge* time.
`bleachbit/FileUtilities.py` ([source](https://raw.githubusercontent.com/bleachbit/bleachbit/e2455c9354f8da4270363b56182139bc25710fd7/bleachbit/FileUtilities.py)) holds the syscall-level care. `:559` `def delete_file(path, shred)`, `:564` `def truncate_file(path)`, `:578` `def delete(path, shred=False, ignore_missing=False, allow_shred=True)` with the docstring "All links are removed without following the link" and `:596` `do_shred = allow_shred and (shred or options.get('shred'))`. `_delete_file_impl` (`:506`) demonstrates the **link-check-then-act** discipline: it calls `wipe_contents(path)` only `if shred and not is_hard_link(path)`, and re-checks after the overwrite. `truncate_file` runs under the same delete lock and uses `_open_nofollow_fd(path, os.O_WRONLY | os.O_TRUNC)` (`:365`) with the comment "No O_CREAT: if the file went away, do not recreate it as an empty one" — a `truncate` that cannot resurrect a deleted path. `_run_with_delete_lock` (`:91`) exists "to prevent race conditions where the parent directory is deleted while the function is running" (Windows-only in practice, `:96-98`). `_delete_path` (`:82`) dispatches by type, and directory removal refuses non-empty dirs with `"Directory is not empty: %s"` and reports `"Skipping mount point: %s"` on `EBUSY` when `os.path.ismount(path)` (Windows branch). `truncate_f` (`:1063`) is the fd-level form.
`bleachbit/Wipe.py` ([source](https://raw.githubusercontent.com/bleachbit/bleachbit/e2455c9354f8da4270363b56182139bc25710fd7/bleachbit/Wipe.py)) is the part with a real idea for us: **recovery of one's own interrupted work.** `wipe_path(pathname, idle=False)` (`:329`) allocates a free-space filler file named `empty_<random>`; `__random_string` (`:55`), `__valid_random_filename` (`:61`) and `detect_orphaned_wipe_files` (`:90`) form a closed loop — on the next run, any file in a configured shred drive that starts with `empty_`, is longer than 100 characters, has no extension, and samples as all-null-bytes is identified as *our own* orphan and reported. The detection criteria are written down explicitly and are deliberately conservative (all four must hold). `wipe_name(pathname1)` (`:290`) renames once to a same-length random name, retries up to 100 times, and **on `EACCES`/`EPERM`/`EROFS` falls back to the original name** rather than failing. `wipe_contents(path)` (`:228`) after a successful advanced overwrite reopens `wb` and re-checks `os.path.islink(path)` — `raise OSError(errno.EACCES, 'refusing to truncate a link', path)` — with the comment "file_wipe() checked before the wipe, so one could have been planted since". `sync()` (`:180`) calls `libc.sync()` via `ctypes` (`libc.so.6` on Linux, `libSystem.B.dylib` on macOS) — the raw-system-flush analogue of our `F_FULLFSYNC`. `fitrim(pathname)` (`:141`) issues an `FITRIM` ioctl (`fitrim_id = 0xC0185879`) over the whole device range after a free-space wipe, and `wipe_path` refuses to free-space-wipe a non-directory and warns `"Shred drive is world-writable; wiping there is unsafe: %s"` via `bleachbit.PathUtils.is_world_writable`. `bleachbit/CLI.py` ([source](https://raw.githubusercontent.com/bleachbit/bleachbit/e2455c9354f8da4270363b56182139bc25710fd7/bleachbit/CLI.py)) shows the CLI-side gating: `:289` `--no-delete-confirmation` (`dest="delete_confirmation"`, `action="store_false"`), `:245` `-s/--shred`, `:338` a validation loop over `('delete_confirmation', 'load_cleaners', ...)`, and `:417/:421/:434` where `--shred` is force-promoted for the free-space routine only.

## Risks & open questions

1. **No Rust secure-erase crate could be verified.** crates.io lookups this session: `trash-delete` does not exist; `wipe` 2.1.1 is a terminal-screen wiper; `shred` 0.16.1 has `license = null` and an unrelated description; `secure-delete` returned nothing. **UNVERIFIED** — treat as "no vetted crate" rather than "no crate exists". This supports the design-doc line that our purge is entry removal + honest byte accounting, not erasure.
2. **BleachBit `Command.py` could not be fetched** — the download was refused by the shell guard (see item 3 below) and only `FileUtilities.py`, `CLI.py`, `Wipe.py` and `ProtectedPath.py` were read. Any claim about BleachBit's per-command abort/`shred` decision loop that lives in `Command.py` is **UNVERIFIED**; the `--no-delete-confirmation` and `--shred` options *were* read directly from `CLI.py`, and the file-deletion path *was* read from `FileUtilities.py`.
3. **Reusing our own shell guard, for the record:** commands whose text pipes a downloader into a shell are blocked by the harness; downloads had to be issued as `curl -o <file>` and grepped in a separate call. crates.io requires a `User-Agent` header (403 without); the GitHub API needs a token for rate-limit headroom.
4. **Branch-HEAD citations are not releases.** restic, gtrash, rmw, rmlint, jdupes, BleachBit, dupeGuru, fclones, trash-rs, glib and coreutils URLs below are pinned to the HEAD SHA read this session; only `trash` (5.2.8), `fclones` (0.35.0) and BleachBit (6.0.4) had a version field readable from a manifest or source constant this session. For rmlint, jdupes, restic and glib the *version number* is therefore **not verified** — the SHA is the anchor.
5. **`fclones` as a dependency is a real decision, not a drop-in.** Its `dedupe` module is `mod dedupe;` (private) with selected re-exports at `fclones/src/lib.rs`, and the crate is binary-shaped (a `[[bin]]` plus a large CLI surface in `config.rs`). Adopting it pulls `bincode`, `blake3`, `byte-unit`, `console`, `clap_complete` and more. The honest read is *borrow the design*, adopt the crate only if the duplicate-detection path itself is ever built out.
6. **`rustix` loses one flag we use.** Apple's `RenameFlags` names only `EXCHANGE` and `NOREPLACE`; `RENAME_NOFOLLOW_ANY` (`0x10`, currently in `src/execute/macos.rs:18`) has no named constant. The bitflags "externally defined flags" escape (`const _ = !0`) suggests raw bits are passable, but that is **[INFERENCE]** from reading `src/backend/libc/fs/types.rs:549` — it was not exercised. Verify with a compile before proposing the swap.
7. **Open question — does our 72 h grace need a "shown to the user" marker?** rmw's `purge-time` file exists because an age-only rule can purge something the user never saw. Our `recover()` surfaces `ExpiredQuarantine` and never auto-purges, and purge additionally requires a typed byte count, so the failure mode is already closed. Worth stating explicitly in the design doc rather than adding a marker.
8. **Open question — collision suffix vs. halt.** We chose keep-both (`restore_keep_both`, `-1`…`-100`); trash-rs chooses to halt with `remaining_items`; gtrash cancels the whole batch. Our choice is the most forgiving but is also the only one that produces a *new path the user did not ask for*. The `RestoreReport.collided` list exists; the question is whether the GUI must surface it before the user next looks at the folder. `app/src/routes/*.svelte` was not read in this lane (restore-UX is note 17's ground).
9. **Prior-instance reads carried forward, not re-verified this session.** The rmlint `lib/formats/sh.c` handler-declaration line numbers and `lib/cmdline.c:766` (`rm_fmt_add(session->formats, "sh", "rmlint.sh")`), and restic's `internal/data/snapshot_policy.go` details, were read by an *earlier* research pass, not by this session. Treat those three citations as **second-hand within the corpus**.
