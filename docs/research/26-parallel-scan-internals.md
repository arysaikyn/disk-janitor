# Parallel Scan Internals — Hardlink Dedup, Size Semantics, Error Policy — Research Note
Code-level internals of ten OSS filesystem walkers, mapped onto `src/scan.rs` / `src/scan/platform/macos.rs` / `src/classify.rs` · researched 2026-09-13

Scope: traversal strategy, `(dev,ino)` hardlink dedup (exact insert condition), apparent-vs-allocated size, same-inode-reached-by-two-spellings, symlink-loop avoidance, and mid-walk error policy for dust 1.2.5, diskus 0.9.0, fclones 0.35.0, parallel-disk-usage 0.24.0, dua-core 4.0.0/4.1.0, gdu v5.34.3, ncdu 1.22, walkdir 2.5.0, ignore 0.4.33, jwalk 0.9.0, plus rayon `scope`. Every version and license below was read from the primary source (the repo's own `Cargo.toml`/`LICENSE`/`COPYING`, raw source files) on 2026-09-13; crates.io's `license` field is `null` for all of them, so licenses come from the repositories.

### Family 1 — own-pool walkers (dua-core, gdu, ncdu): the dedup designs that survive re-visits

**dua-core's `InodeFilter` is the most transferable design in this note, because it is the only one that was written for *overlapping roots*, which is exactly our `ScanOptions.roots: Vec<PathBuf>` shape.** `add_dev_inode` (`src/inodefilter.rs:149-173`) counts down from `nlink`: the first observation of a `(dev,ino)` inserts `nlinks - 1` and returns `true`; each later observation decrements and returns `false`; when the counter hits `1` it removes the entry (so a fully-link-consumed inode stops occupying memory). The unit test at the bottom of the file pins exactly this: `add_dev_inode((1,1),2)`→`true`, again→`false`, and a *separate* device `(2,1)` is tracked independently — evidence that the key is genuinely `(dev,ino)`, not ino.

The macOS-specific `add_directory` (`:102-142`) exists because `ATTR_DIR_LINKCOUNT` — the attribute dua-core reads through `getattrlistbulk` — **omits the synthetic `.` and `..` links**, so a bulk-enumerated directory can report `nlink == 1` where `stat(2)` would report more. dua's answer: on the first ambiguous observation, insert the marker `UNRESOLVED_DIRECTORY_LINKS = u64::MAX` (chosen because Darwin's `nlink_t` is 16 bits, so the marker cannot collide with a real count) and count the entry once; only when an overlapping root *revisits* that exact `(dev,ino)` does it pay for a `symlink_metadata` — and it validates the re-read with `.filter(|actual| (actual.dev(), actual.ino()) == dev_inode)` before trusting the count. That marker-plus-lazy-resolution pattern is directly relevant to us: our walker gets `md.nlink()` from the same bulk path and our `DirStat.nlink` is likewise possibly-understated for directories.

The APFS half (`mod apfs`, `:176-212`) keys on `(device, clone_id)`: `allocated_size()` returns the full `allocated_size()` only for the first observation of a clone stream, otherwise `allocated_size().saturating_sub(data_allocated_size())` — because "Clone identifiers cover only the data fork; resource forks remain private." Critically it guards the clone set with a separate `inodes: HashSet<(u64,u64)>` and returns `true` early for a re-visited inode, with the comment "Hard links and overlapping roots revisit one inode, not distinct cloned files." **We already carry `DirStat.clone_id` (`src/scan.rs:29`) and set it from `md.clone_id()` in the walker, but nothing consumes it.** This is the only place in the corpus that shows what consuming it correctly looks like.

dua's two `Options` flags (`skip_metadata`, `apfs_clone_metadata`) and `needs_tracking()` (`:17-41`) are the gate that keeps the filter off the hot path: `needs_tracking` returns `false` immediately for any entry that cannot affect another candidate's accounting, so a walk over non-hardlinked, non-cloned files allocates nothing.

**gdu's dedup is the counter-example.** `fs.HardLinkedItems` is `map[uint64]Files` — **keyed on inode number alone, with no device** (`pkg/fs/file.go:67`, comment "maps inode number to array of all hard linked items"). `File.Mli` is set to `stat.Ino` only when `stat.Nlink > 1` (`pkg/analyze/file_unix.go` `setPlatformSpecificAttrs`, and `getSyscallStats`). Two files on *different* filesystems that happen to share an inode number will collide: the second is treated as already-counted and contributes `(1, 0, 0)`. On a single-volume scan this is invisible; on our macOS box with `/` (firmlinked, same st_dev for both halves) plus a DMG or external volume enumerated in one run, inode numbers repeat freely. **This is a real defect class we must not copy** — and it is a concrete argument for `(dev,ino)` over ino in our own dedup.

**ncdu is the only single-threaded design here, and its `hlink_check` is the only one that solves the *aggregation* half of the problem rather than the *counting* half.** Dedup insertion is `stat_to_dir` (`src/dir_scan.c:117-127`): `FF_HLNKC` is set `if(!S_ISDIR(fs->st_mode) && fs->st_nlink > 1)`, and `buf_nlink = fs->st_nlink`. The hash/equality pair is `dev ^ ino` for the bucket and `dev == && ino ==` for equality (`src/dir_mem.c:39-40`), so the key is `(dev,ino)` even though the hash is XORed. What `hlink_check` (`src/dir_mem.c:61-90`) does next is the part worth reading: for each ancestor `par` of the new link, it walks the already-seen link chain `d->hlnk` and asks whether any previously-seen link to the same inode is a descendant of `par`; only if no ancestor of `par` has counted it does `par->size += d->size`. The source itself flags the cost ("XXX: This may not be the most efficient algorithm to do this"). This is precisely the semantics our `fold_subtree` (`src/classify.rs:221-232`) lacks: it sums a subtree without asking whether a hardlinked file in that subtree was already counted by a *different* branch.

Also worth keeping from ncdu: `dir_read()` slurps the whole directory into a `char*` buffer before walking it, with the stated reason "to avoid eating too many file descriptors in a deeply recursive directory" — the same fd-bounding concern walkdir solves differently (sliding `max_open` window) and we sidestep entirely by delegating to dua-core. And ncdu's macOS firmlink handling is explicit: `getattrlist` with `attrlist.forkattr = ATTR_CMNEXT_NOFIRMLINKPATH` sets `FF_FRMLNK`, which then excludes the entry from tag caching and from the size-counting branch.

### Family 2 — rayon-based walkers (dust, diskus, parallel-disk-usage, fclones): recursion shapes and the size-conflict assertion

**dust is the cleanest reusable recursion shape.** `walk_it` builds a synthetic `outer` `PendingDir` above the root so `finalize_chain` has a uniform parent to bubble into, then does exactly one `rayon::scope(|s| { s.spawn(move |s| walk_dir(s, root, walk_data)); })` per root (`src/dir_walker.rs:109-112`). Every descendant walk task is spawned flat into that single scope from inside `walk_dir`, so — the comment says it directly — "all descendant work runs as flat tasks inside it, so stack depth is O(1) regardless of tree depth." Completion is counted through `PendingDir` arcs; `finalize_chain` drains a child's `Node` into its parent once the child's counter reaches zero, and the top-level result is drained from `outer.children` after the scope returns. Our own cancel primitive is "drop the `RootWalk` iterator", which the dua-core docs define as "stop and join", so a scope-shaped recursion is not needed for shutdown — but dust's shape is the reason a scope-shaped recursion *cannot leak tasks past the scope*, which is the property `src/scan/platform/macos.rs` relies on when it `break`s out of the `for` loop with `iter` still alive.

**dust's dedup is gated on the size mode, and that gate is a correctness statement we should copy verbatim.** `clean_inodes` (`:129-136`):
```rust
if !walk_data.use_apparent_size
    && let Some(id) = x.inode_device
    && !inodes.insert(id)
{ return None; }
```
Under apparent-size accounting dust deliberately does *not* dedup, because summing `st_size` over N links to one inode is what an apparent-size total means. It also pre-sorts children by `sort_by_inode` before recursing, "so iteration order is predictable" — with the note "Sorting by inode is quicker than by sorting by name/size". Determinism under parallelism is a property our own `candidates_from_batch` claims ("Order-independent — batch ordering / streaming splits never change the result") but implements only by sorting the *output* by size then `path_hash` (`src/classify.rs:203-207`); dust gets determinism in the fold itself.

**dust's EINTR policy is the most defensible error design in the corpus.** `is_retryable` (`:452-454`) is *only* `ErrorKind::Interrupted`. `walk_dir` (`:266-300`) loops: `read_dir` failure → `record_error` → `if is_retryable { continue }` else break; if the directory opened, it collects entries into a `Vec` **first** and then scans that `Vec` for a retryable error, and on finding one it throws the whole `Vec` away and re-lists. The comment states the reason exactly: "Drain into a Vec before doing anything observable on `pending`. This is the load-bearing structural choice for retry safety: if we decide to retry, we throw the Vec away and re-list, with no spawned subdir tasks or pushed file nodes to roll back." The second comment is equally load-bearing: other (non-retryable) errors found in the same `Vec` are *not* recorded yet, because "recording them now would log phantoms when the retry succeeds cleanly." `record_error`'s buckets are listed in the master table; the runaway guard is `interrupted_error > 999` → a single `eprintln!` and give up on that directory.

**diskus shows the minimal-shared-state design and its cost.** Workers push `Message::SizeEntry(Option<UniqueID>, u64)` into one unbounded channel; a **single** receiver thread owns `let mut ids = HashSet::new()` and does `if ids.insert(unique_id) { total += size }` (`src/walk.rs:218-243`). Centralising the set means no synchronization, but it also means *every* entry crosses a channel — tolerable for `du -sh`, wasteful for a walker that must also hand rich `DirStat` records to a classifier. Its `generate_unique_id` gate is `metadata.is_file() && metadata.nlink() > 1` — **files only**, directories excluded — and the Windows branch returns `None` for everything, with the comment that Windows tooling "are not respecting hardlinks or junction points when determining the size of a directory" and a link to issue 32. Its per-entry error handling is the weakest here: `for child_entry in child_entries.flatten()` silently discards every `Err`, and the *only* trace of a problem is the aggregate `size_in_bytes() -> Result<u64, &[Error]>`.

**parallel-disk-usage contributes two things nothing else has: a typed key with conflict detection, and a dedup pass that runs *after* the tree is built.** `InodeKey{ino: InodeNumber, dev: DeviceNumber}` (`src/hardlink/hardlink_list.rs:26-33`) is the doc-comment'd "Internal key used to uniquely identify an inode across all filesystems", stored in a `DashMap` so many rayon workers can `add()` without a global lock. `add()` (`:132-171`) is a *checking* insert: on a repeat key it returns `Err(AddError::SizeConflict(SizeConflictError{ino, dev, recorded, detected}))` if the size disagrees, and `Err(AddError::NumberOfLinksConflict(...))` if `nlink` disagrees — the two error types are `#[derive(Display, Error)]` with messages like `"Size for inode {ino} on device {dev} changed from {recorded:?} to {detected:?}"`. Only `!stats.is_dir() && stats.nlink() > 1` is ever recorded (`src/hardlink/aware.rs`), so a normal file costs nothing. The caller **ignores** the error (`.ok(); // ignore the error for now`, `src/fs_tree_builder.rs`) but the information exists. Dedup is deferred: `DeduplicateSharedSize::deduplicate` collects `(size, paths)` per inode, then `par_deduplicate_hardlinks` (`src/data_tree/hardlink.rs`) recurses with `rayon::par_iter_mut`, filtering to links within the current subtree by `strip_prefix` and subtracting `*size * (number_of_links - 1)` from each ancestor. Doing dedup as a second pass over a finished tree — rather than as an insertion-time veto — is the structural alternative to dust's and diskus's designs, and it is the one that composes with an existing `fold_subtree`.

Its error surface is also the most reusable design: `ErrorReport<'a>{operation: Operation, path: &'a Path, error: io::Error}` plus `pub const SILENT: fn(ErrorReport) = |_| {}` (`src/reporter/error_report.rs`), with `Operation::{SymlinkMetadata, ReadDirectory, AccessEntry}` each exposing `name()` → `"symlink_metadata"`, `"read_dir"`, `"access entry"` (`src/reporter/error_report/operation.rs`). Every failure site calls `reporter.report(Event::EncounterError(...))` and then returns an empty `Info`/`None` — the walk always completes. `DeviceBoundary::{Cross, Stay}` (`src/device.rs`) is derived once from `--one-file-system`, and the root device is resolved *once* before the walk (`root_dev.is_none_or(|root_dev| get_device_id(&stats) == root_dev)`), with a `symlink_metadata` failure on the root reported and the whole tree degraded to a single file rather than an error.

**fclones is the identity-layer reference for path spellings.** Its walker is `rayon::scope` with one `scope.spawn` per entry, and `sorted_entries` deliberately puts files first and directories last so that a LIFO worker queue leaves dirs stealable — the same LIFO reasoning `ignore` states explicitly (below). It canonicalises roots through `absolute()` (`src/walk.rs:454-466`): `path.canonicalize()` for directories, and for files `parent.canonicalize()?.join(file_name)` — an explicit carve-out because canonicalising a file follows its symlink and would lose the name. Its `visited` dedup is a `DashSet<u128>` of `entry.path.hash128()` inserted **only when `follow_links`**, with the source comment "because inserting into a shared hash set is costly" — i.e. fclones does *not* dedup hardlinks at all (its job is finding duplicates, not sizing), and its device check is `FileId::new(path).device == dev` with `FileId{device: u64, inode: InodeId}` (`src/file.rs:201-214`), failing closed with `log_warn` when the id cannot be read.

### Family 3 — general walkers (walkdir, ignore, jwalk): loop detection and read-error-as-item

**walkdir's symlink-loop check is the only one in this corpus shaped like a stack walk over ancestors, and its conditional is the interesting part.** In `handle_entry`: `let is_normal_dir = !dent.file_type().is_symlink() && dent.is_dir();`, and `self.check_loop(dent.path())` is called only inside `follow()` — whose comment reads "The only way a symlink can cause a loop is if it points to a directory" — and only when `dent.is_dir()`. `check_loop` iterates `self.stack_path.iter().rev()` (deepest ancestor first) and, via `same_file::Handle`, compares the child handle against each `Ancestor` handle, producing `Error::from_loop(depth, ancestor, child)` on a match. Two consequences: loop detection is **conditional on following symlinks** (our walker never follows — dua-core "report[s] but never follow[s]" — so we inherit zero loop risk and pay zero detection cost), and `Ancestor` is constructed **before** `stack_list.push` precisely so a failing handle-open cannot leave the stacks inconsistent (comment: "We push this after stack_path since creating the Ancestor can fail"), with `stack_path.pop().expect("BUG: list/path stacks out of sync")` on the way out. The `same_file_system` check is on the directory path only (`if self.opts.same_file_system && dent.depth() > 0 { if self.is_same_file_system(&dent) { self.push(&dent) } }`) and compares `util::device_num(dent.path())` — `path.metadata().map(|md| md.dev())` on unix (`src/util.rs`) — against a `root_device` cached at construction, guarded by `.expect("BUG: called is_same_file_system without root device")`. Note it *descends* on `true`: `if is_same_file_system { push }`.

**ignore implements read-error-as-item and states the LIFO rationale.** `WalkParallel::threads()` = `available_parallelism().map_or(1, |n| n.get()).min(12)` when 0. `Stack::new_for_each_thread` builds `crossbeam_deque::Deque::new_lifo()` per worker with the comment: "Using new_lifo() ensures each worker operates depth-first, not breadth-first. We do depth-first because a breadth first traversal on wide directories with a lot of gitignores is disastrous (for example, searching a directory tree containing all of crates.io)." `Stack::pop()` is `self.deque.pop().or_else(|| self.steal())`; `steal()` scans from its own index and uses `steal_batch_and_pop` — a batch steal, not a single-item steal. The error design is the reusable part: `read_dir` returns `ReadDirResult{entries, errors}` and both are yielded as items, so a directory whose read *partially* succeeded still contributes its entries and its errors separately; the walk never aborts. `quit_now: Arc<AtomicBool>` + `active_workers: Arc<AtomicUsize>` simulate a priority channel for `WalkState::Quit`, whose own doc warns the action is "inherently asynchronous. It is possible for more entries to be yielded even after instructing the iterator to quit." `same_file_system` is resolved **per root**: `root_device` is computed with `device_num(&path)` only when the option is on, and a failure there yields `Error::Io(err).with_path(path)` then `continue` — one bad root does not sink the walk.

**jwalk** contributes only the `process_read_dir` callback shape (`WalkDirGeneric::<((usize),(bool))>`) and the "Entries streamed in sorted order" contract; it is otherwise note-04 territory (unmaintained, no device option). Its rayon dependency and `sort(true)` are the two API facts worth keeping.

### Family 4 — rayon `scope` semantics (read from docs.rs, not from memory)

`rayon::scope` docs, fetched 2026-09-13: "Creates a `fork-join` scope `s` and invokes the closure with a reference to `s`. This closure can then spawn asynchronous tasks into `s`. … When the closure returns, it will block until all tasks that have been spawned into `s` complete." And the cost warning that decides when *not* to use it: "`scope()` is a more flexible building block compared to `join()`, since a loop can be used to spawn any number of tasks without recursing. However, that flexibility comes at a performance price: tasks spawned using `scope()` must be allocated onto the heap, whereas `join()` can make exclusive use of the stack. Prefer `join()` (or, even better, parallel iterators) where possible." Two grounded implications: (1) dust's and fclones's one-`spawn`-per-directory designs heap-allocate one task per directory — acceptable because the alternative, recursive `join`, would make stack depth O(tree depth); (2) our walker needs none of it, because dua-core owns the pool and our cancel primitive is `Drop`. rayon 1.12.0's license is `MIT OR Apache-2.0`, read from its `LICENSE-MIT` ("Copyright (c) 2010 The Rust Project Developers") and `LICENSE-APACHE` files; crates.io reports `license` as `null` for every crate in this note.

### The production defect this note exists to close, stated precisely

`src/classify.rs::candidates_from_batch` builds `dirs: HashMap<PathBuf, DirStat>` and `aggs: HashMap<PathBuf, DirAgg>` **keyed by the joined path string** (`d.parent.join(&d.name)`), and `fold_file` adds every `Kind::File` entry's bytes to `aggs[&d.parent]` with no identity check. Two spellings of one directory — a root passed twice (`janitor scan /x /x`), a root plus a path under it, or two overlapping roots — therefore yield two `DirStat`s for one `(dev,ino)`, two `DirAgg`s, and **double-counted bytes** in whichever candidate wins. The walker cannot prevent it: its `descend` predicate can only reject a cancel flag, missing metadata, a non-directory, `md.dev() != first_dev`, or a globset match — it cannot know a directory was reached twice.

Downstream consequences are already bounded by identity-based dedup, and a scan-side fix must agree with them or the purge gate refuses: `src/plan.rs::build` keeps `seen_inodes: HashSet<(u64,u64)>` with `PlanEntry.inode: Option<(u64,u64)>` so a shared inode's bytes are counted once; `src/execute.rs::purge` **recomputes** `expected` by the same rule and refuses unless the operator's typed byte count equals it, freeing each inode once; `src/execute.rs::discover_quarantine_roots` already dedups path spellings via `macos::lstat_identity` with a string-keyed fallback. So the defect is not over-deletion — it is that the **plan's byte totals can disagree with what purge recomputes**, surfacing as an unexplainable "byte count does not match" refusal at the most safety-critical moment in the product. Implementing scan-side identity dedup with `(dev,ino)` — the same vocabulary as `lstat_identity` — is what makes the two agree, and it is the highest-value borrowing in this note.

## Risks & open questions

- **Do not dedup `app_bytes` by reflex.** dust deliberately *skips* dedup under apparent-size accounting (`if !walk_data.use_apparent_size && …`), because an apparent-size total legitimately counts every link. Our `app_bytes` is neither `du --apparent-size` nor a pure diagnostic — it exists to compute the sparse ratio `app_bytes > alloc_bytes * 4` (`src/classify.rs` step 4). Deduping it changes which files qualify as sparse; the choice must be made deliberately and documented, not inherited.
- **Scan-side dedup must match `plan::build` exactly or purge refuses.** `src/execute.rs::purge` recomputes `expected` from `PlanEntry.inode` with `seen_inodes` and refuses unless the operator's typed count equals it. Any scan-side rule that differs by even one inode turns the product's headline interaction ("type the exact byte count") into an unexplainable refusal. This is the single biggest correctness coupling in this note and it is a **hard** dependency between rows 1 and 5 of the backlog.

  **Scope of this coupling (verified 2026-09-13): it governs *candidate* inodes only.** A hardlinked file pair living inside a single directory candidate is invisible to both `plan::build` and `purge`, so the two sides agree on the inflated total and the mismatch never fires — the accepted number is *wrong*, not refused. That is precisely why backlog row 1 (an intra-candidate `(dev,ino)` fold in `candidates_from_batch`) is required, and why row 1 must land **before** any doc claims the receipt is exact.
- **`first_dev` is a live bug, not just a design smell** (backlog row 2). **Reproduced 2026-09-13** on a scratch APFS DMG (`/Volumes/DJTest`) with a second root on the boot volume: `scan --min-bytes 1 /Volumes/DJTest /tmp/djhl9` → 1 candidate (`/Volumes/DJTest/node_modules`); the same two roots reversed, `scan --min-bytes 1 /tmp/djhl9 /Volumes/DJTest` → 1 candidate (`/tmp/djhl9/.pnpm-store`). The second root is pruned silently, order-dependently, with no error and no `RootError` event. Code reading confirmed at `src/scan/platform/macos.rs` L70-74 (`first_dev` from `opts.roots.first()`) and L101 (`md.dev() != dev` in `descend`); `cross_filesystems: false` at `src/main.rs:631`.
- **Directory `nlink` from dua-core's bulk path is very likely understated on macOS** (dua's `ATTR_DIR_LINKCOUNT` comment is explicit that synthetic `.`/`..` are omitted), but dua's own filter is the only evidence I have that `ATTR_DIR_LINKCOUNT` is what our `md.nlink()` reflects. Our `DirStat.nlink` for `Kind::Dir` is currently unverified against `lstat`. UNVERIFIED as a fact about dua-core 4.0.0's macOS backend: I read dua's macOS attributes module in note 04's session, not this one, and I did not re-read `macos/attributes.rs` today to confirm which link-count attribute our pinned 4.0.0 requests.
- **`clone_id` semantics on non-APFS volumes** are unverified: I did not read what dua-core returns for `Entry::metadata().clone_id()` on HFS+/exFAT (likely `None`), so the "N clones → N× bytes" premise is unverified for anything but APFS. Do not claim it in the design doc beyond APFS.
- **`ncdu`'s `hlink_check` is flagged inefficient by its own source** ("XXX: This may not be the most efficient algorithm"), so it is a semantics reference, not a performance reference.
- **gdu's inode-only key is a hazard I am inferring the consequences of, not observing.** The code is unambiguous (`map[uint64]Files`, no device), and cross-volume inode reuse is a filesystem fact, but I did not construct a two-volume fixture proving a collision.
- **Versions drift under `master`.** All Rust source line citations in this note are from each project's default branch as fetched today, *except* dua-core, which I pinned to the tags `dua-core-v4.0.0` / `dua-core-v4.1.0`. gdu's source was read from `master` while the newest tag is `v5.37.0`, dust's from `master` at version 1.2.5, ncdu's from `master` (`configure.ac` says 1.22). Treat line numbers as accurate for the fetch date, not for the tagged release.
- **Open question for the design doc:** should a `(dev,ino)` seen-set live in the scan walker (streaming, O(inodes-with-nlink>1)) or in `candidates_from_batch` (batch-local, O(files))? Streaming placement catches the defect earlier but duplicates state across `ScanEvent::Batch` boundaries and risks disagreeing with the batch-local fold; batch-local placement is where the byte totals are actually produced and is what rows 1 and 4 assume. I did not resolve this — it is a design decision for the owner.
