# Rust LLM-Agent Frameworks & Data Boundaries (tool loops, retry, redaction seams) — Research Note

Which Rust agent frameworks have a *data-boundary* seam — a place where tool output can be rewritten or suppressed before the model sees it — and how each structures loop, tool registration, budget, and retry · researched 2026-09-13

Scope: read at source on **2026-09-13** (never from memory): `rig` (`0xPlaygrounds/rig`, crate graph `rig-core`/`rig-agent`, v0.42.0), `swiftide` (pinned at SHA `3736ce790b1d953f0ddbe2258d332d19545a6d47` — every `main` path 404s), `rmcp` (`modelcontextprotocol/rust-sdk` 3.3.0), `llm-chain` (sobelio), `kalosm`/floneum, `genai` (jeremychone/rust-genai), `async-openai` (64bit), `mistral.rs` (EricLBuehler), `candle` (huggingface), `ollama-rs` (pepperoni21). Licenses and versions were read from each repo's own `LICENSE`/`Cargo.toml` (raw file) **and** independently from the crates.io per-version API, or from the published crates.io tarball when the API `license` field was unusable. API shapes come from raw source on GitHub (or the tarball), never from docs.rs or memory. No code was written or ported; nothing was built or tested.

**Lane definition.** This note's differentiator is one column — the **redaction / path-anonymisation boundary**: does the framework give you a *seam* between "what the tool produced" and "what the model is shown", and is that seam enforced or opt-in? Everything else here exists to make that column legible.

## Findings

### rig 0.42.0 (0xPlaygrounds) — the only surveyed framework with a model-visible redaction seam

Licence **MIT**, verified twice: repo root `Cargo.toml` reads `license = "MIT"`, and `crates.io/api/v1/crates/rig-agent/0.42.0` returns `license: "MIT"`. Version 0.42.0, published 2026-08-17; `rig-core` and `rig-agent` are separate crates behind the `rig` facade.

**Loop shape — geniunely sans-IO, matching ours.** `crates/rig-agent/src/run/mod.rs` opens verbatim: *"A sans-IO, steppable, serializable state machine for the agent prompt loop."* `AgentRun` "owns every *decision* the agent loop makes — turn counting, tool-call validation, invalid tool-call recovery, chat-history threading, usage aggregation and final response construction — without performing any IO itself." The driver loop is `AgentRun::next_step() -> AgentRunStep`, with `AgentRunStep::{CallModel{prompt,history,turn}, CallTools{calls}, Done(response)}`, fed back through `AgentRun::model_response(ModelTurn)` / `AgentRun::tool_results(...)`. The module doc states: *"Because the machine never awaits anything, it is runtime-agnostic and the whole run state is `Serialize + Deserialize`."* This is the same shape as our `src/agent.rs::AgentRun::{next_step, feed_reply, execute_tools}`.

**Serializable-between-steps — and the sensitivity caveat is written down.** The module doc continues, verbatim: serialized run state "embeds the full conversation accumulated so far *and* every completed call's provider response (`CompletionCall::raw`, the value the model's raw method would have returned, serialized) — persisting it inherits whatever sensitivity the conversation content has and grows with each provider body; a driver that does not want the raw payloads persisted clears `raw` on its own copy before writing — and the serialization format **carries no cross-version stability guarantee yet: resume with the same rig version that suspended the run**." Contrast our `RunSnapshot::resume()` (`src/agent.rs:802`), whose only persisted payload is agenda/budget/counter state, never provider bodies.

**Runtime-agnostic hosting is explicit.** The same doc: "A host that does so (an ECS schedule, a job system) depends on `rig-agent` with default features off — that graph carries no async runtime, transport or MCP client (guarded), only rig-core and the futures vocabulary." The `examples/agent_no_tokio` example is that host in miniature (verified present in the examples listing).

**The redaction seam — `ToolResultAction::Rewrite`.** `crates/rig-agent/src/agent/hook.rs:1044`:

```rust
pub enum ToolResultAction {
    /// Keep the current presentation.
    Keep,
    /// Replace the effective presentation sent to the model and result-content
    /// telemetry.
    Rewrite(ToolOutput),
    /// Stop the run.
    Stop(String),
}
```

with `ToolResultAction::rewrite(result: impl Into<String>)`, whose doc adds: *"The tool's raw structured result remains unchanged."* End-to-end proof that this actually strips content before the model sees it lives at `tests/providers/anthropic/cassette/tool_result_rewrite.rs`: *"Verifies that a `ToolResultAction::Rewrite` hook redacts a tool's output before the model sees it, end-to-end through a real Anthropic round-trip"* — a fake `SECRET_SSN = "123-45-6789"` returned by a `get_user_record` tool is rewritten so it never reaches the model.

**The caveat that matters for us.** `crates/rig-agent/src/agent/engine/tests.rs` (test `rewrite_result_does_not_mask_the_structured_outcome`) comments verbatim: *"A `ToolResultAction::Rewrite` hook redacts the model-visible text, but a later policy hook still sees the tool's *raw* structured outcome — a rewrite changes only what the model sees, not the classification."* The test registers a redactor and then an observer hook, and asserts simultaneously `observer.outcomes() == ["error:not_found"]` and `observer.results() == ["[REDACTED]"]`. **So rig's boundary is presentation-only and opt-in per tool result. It is not an invariant.** Any framework consumer who forgets the hook sends the raw tool output to the provider. A repo-wide code search (`redact repo:0xPlaygrounds/rig path:crates`, 15 hits) finds only provider-auth `Debug` impls and unrelated matches — **there is no path/identifier redaction layer in rig at all**, and no scrubbing of model inputs analogous to our `scrub_text`.

**Pre-tool policy hooks.** `hook.rs:1002`: `pub enum ToolCallAction { Run, Rewrite(serde_json::Value), Skip(String), Stop(String) }`. `Skip`'s doc: *"Do not execute; return this feedback to the model."* The `AgentHook` trait (12 async methods: `on_run_start`, `on_run_settled`, `on_model_select`, `on_completion_call`, `on_completion_response`, `on_model_turn_finished`, `on_invalid_tool_call`, `on_tool_call`, `on_tool_result`, `on_text_delta`, `on_reasoning_delta`, `on_tool_call_delta`) is paired with `HookContext` + `Scratchpad`. `ModelTurnAction::{Continue, Retry(RetryRequest), Stop(String)}` carries `RetryRequest::{Repeat, Feedback}`, with the doc: *"Every retry consumes the run's existing total model-call budget. Rig does not impose a separate response-retry limit."* Tool-call rewrites are recorded via `ctx.record_tool_call_rewrite(internal_call_id, rewrite)`.

**Fail-closed policy example.** `examples/agent_with_approval_policy/src/main.rs` implements `on_tool_call` returning `ToolCallAction::run()` to allow and `ToolCallAction::skip(reason)` to deny, with the doc: *"the denial reason is fed back to the model as the tool result, so it can adjust (e.g. transfer a smaller amount or ask the user) rather than the run simply failing."* It is explicitly **fail-closed** ("any tool not explicitly allowed is denied") and explicitly **not a security boundary**: *"this is guardrail/UX logic, not a security boundary — enforce real authorization inside the tool."*

**Durable approval / invalid-tool-call recovery.** `examples/agent_with_durable_approval/src/main.rs` drives `next_step()` by hand, writes `serde_json::to_vec_pretty(&run)` to disk between `CallTools` and the next turn, and reloads with `serde_json::from_slice::<AgentRun>(...)`. It imports `rig_agent::run::{AgentRun, AgentRunStep, ModelTurn, ModelTurnOutcome}` and unwraps `ModelTurnOutcome::NeedsResolution(context)` in a `while` loop with `run.resolve_invalid_tool_call(InvalidToolCallAction::fail())?`. `call.preresolved_result` marks call slots already satisfied by that recovery. Approval verbs map onto tool-result content: approve → real output, deny → reason, edit → human-supplied JSON args, abort → stop.

**Error taxonomy with a single source of truth.** `crates/rig-core/src/tool/result.rs`:

```rust
pub enum ToolErrorKind { InvalidArgs, Timeout, Cancelled, NotFound,
                         PermissionDenied, RateLimited, Provider, Network, Other }
```

One `kind_defaults!` macro table carries `(stable name, default retryability, default model feedback)` per kind and emits three parallel accessors — the comment says exactly why: *"The macro emits the three parallel accessors from the single table so a new kind cannot update one and miss another."* E.g. `Timeout => ("timeout", Some(true), "tool execution timed out")`, `PermissionDenied => ("permission_denied", Some(false), "the tool denied the request")`. `ToolExecutionError` separates operator-facing `message()` from model-visible `model_output()`/`model_feedback()`, with `retryable() -> Option<bool>`; `ToolExecutionError::from_error<E>` calls `.redact_model_feedback()` so the model sees only the kind-level default string, never the underlying error text. `refused()` is hand-written (not in the `kind_ctors!` table) because it additionally sets a distinct refusal disposition.

**HTTP error header preservation.** `crates/rig-core/src/http_client/mod.rs:120`: `pub fn non_success_headers(&self) -> Option<&HeaderMap>`, doc verbatim *"Rig's bundled HTTP clients capture the full `HeaderMap` whenever a non-success status error is built from a live response, so rate-limit metadata such as `Retry-After` or `x-ratelimit-*` stays readable (rig#2210). This is the accessor a `retry::RetryPolicy` uses to honor a server-supplied backoff."* Its doc-example shows a `retry_after` function reading `http::header::RETRY_AFTER` off that header map. **This is the capability our `HttpChatClient` module doc says async-openai's typed error surface lacks** (`src/agent/http.rs:23-25`).

**Retry policy object.** `crates/rig-core/src/http_client/retry.rs`: `pub trait RetryPolicy { fn retry(&self, error: &Error, last_retry: Option<(usize, Duration)>) -> Option<Duration>; fn set_reconnection_time(&mut self, duration: Duration); }`, `pub struct ExponentialBackoff { start, factor, max_duration, max_retries }`, and `pub const DEFAULT_RETRY: ExponentialBackoff = ExponentialBackoff::new(Duration::from_millis(300), 2., Some(Duration::from_secs(5)), None);`. The trait name `set_reconnection_time` shows this is an **SSE-reconnect** policy, not a general HTTP-429 retry loop — do not mistake it for the latter.

### swiftide (bosun-ai) — pinned; a hook seam exists, but redaction is only image URLs

All `main` paths 404 on 2026-09-13; everything below is read at SHA `3736ce790b1d953f0ddbe2258d332d19545a6d47`. `swiftide-agents 0.32.1`, `swiftide-core 0.32.1` — **MIT**, both from the per-version crates.io endpoint; both published 2025-11-15 (0.32.0 was 2025-11-06), i.e. ~10 months behind rig.

**No retry loop at all.** `swiftide-integrations/src/openai/chat_completion.rs` (1,865 lines) classifies errors only: `LanguageModelError::permanent("Model not set")`, and tests asserting `TransientError` variants. There is **no status-code→retry mapping and no backoff loop** in the crate — note 07's finding that swiftide is the source of the `tool_retry_limit=3` *tool* retry cap (now our `src/agent.rs:33 TOOL_RETRY_LIMIT`) stands, but that is a tool-call cap, not an HTTP-retry policy.

**Boundary surfaces we can name.** `swiftide-core/src/tool_executor.rs`: `pub trait ToolExecutor: Send + Sync + DynClone { async fn exec_cmd(...); async fn stream_files(...) }`; `pub struct ScopedExecutor<E>` with `fn apply_scope<'a>(&'a self, cmd: &'a Command) -> Cow<'a, Command>` and `fn scoped_path<'a>(&'a self, path: &'a Path) -> Cow<'a, Path>`; a `trait ExecutorExt` of convenience ctors. `ScopedExecutor` is a **filesystem-scope isolation** boundary (commands are rewritten to run inside an allowed root) — it *is* path-aware by construction, which is the opposite of what we need; the borrowable idea is the *shape* (a wrapper that rewrites every command at one chokepoint), which is how we should think about `discover_quarantine_roots`' probe list rather than as a redactor. `swiftide-core/src/token_estimation.rs`: `pub trait EstimateTokens`, `pub struct CharEstimator`, impl `s.chars().count() / 4 + additional_tokens()`, and `pub trait Estimatable` for per-type extra tokens.

### async-openai 0.42.0 — the retry layer, and why an outer loop is a no-op

Licence MIT; newest tag `async-openai-v0.42.0` (released 09 Sep 2026). The repo-root `CHANGELOG.md` is a 404, so the **release page is the primary source**: its body reads verbatim *"What's Changed — [codex] Add max reasoning effort by @michaelfeil in #573; feat: spec sync by @64bit in #587"*. **So the 0.41.3→0.42.0 delta is a spec sync plus one request field — no retry or transport change**, which is why our `Cargo.toml` pin of `0.41.3` carries no behavioural risk if left alone.

The retry layer, re-read at source in `async-openai/src/middleware/retry/openai.rs`: `struct OpenAIRetryLayer { max_retries: usize }` with `impl Default { Self::new(3) }`; doc verbatim *"Retries `429`, `5xx`, and native reqwest connect errors with exponential backoff. This layer consumes response body to check if 429 is from rate limit (retryable) or insufficient quota (permanent)… This is why `SimpleRetryPolicy` is also available which doesn't consume response body."* On a 429 the layer clones the headers, extracts `retry_after(&headers)`, then awaits `response.bytes()` and parses `WrappedError`, returning permanently when `error.r#type == Some("insufficient_quota")` (`const INSUFFICIENT_QUOTA: &str = "insufficient_quota";`). This confirms our module doc's claim (`src/agent/http.rs:23-25`): the built-in layer already honors `Retry-After`, and because `OpenAIError`'s typed surface drops the header map, **an outer backon/tower loop could not honor `Retry-After` better — it would only add latency**. rig's `non_success_headers()` is the one design that would change that calculus, and it is a rig-side, not async-openai-side, capability.

### rig as a post-submission swap: verdict

The question is whether to replace our hand-rolled `src/agent.rs` + `src/agent/http.rs` with rig after submission. Concrete type-by-type accounting, all read at source today:

**What rig would give us that we do not have**

| rig symbol | our counterpart | delta |
|---|---|---|
| `AgentRun` / `AgentRunStep::{CallModel,CallTools,Done}` / `AgentRun::model_response` / `tool_results` | `AgentRun::next_step` / `feed_reply` / `execute_tools` / `RunState` | **none** — shapes are equivalent; ours is already the sans-IO rig-run pattern (module doc says so) |
| `ModelTurnOutcome::NeedsResolution` + `InvalidToolCallAction::{fail,retry,repair,skip}` + `PendingToolCall::preresolved_result` | we reject/mint ids (`reply_from_lenient_body` in `src/agent/http.rs`) but have **no explicit recovery action set** | **real gain** — a named, testable recovery policy for a malformed model turn |
| `serde_json::to_vec_pretty(&run)` → `from_slice::<AgentRun>` mid-loop (the `agent_with_durable_approval` pattern) | `RunSnapshot` / `persist_snapshot` / `load_snapshot` / `RunSnapshot::resume()` | **partial** — we have the boundary; rig additionally suspends *between* `CallTools` and the next turn with pending call state |
| `ToolResultAction::Rewrite(ToolOutput)` | `serialize_tool_result()` (`src/agent.rs:1186`) | **rig's is weaker**: opt-in, per-hook, presentation-only, and its own test suite documents that classification is unchanged |
| `AgentHook` (12 async methods) + `ToolCallAction::{Run,Rewrite,Skip,Stop}` + `HookContext::Scratchpad` | none (our `on_progress` callback is the only observation point) | **real gain** for observability: 12 named extension points vs one progress sink |
| `ToolExecutionError{message, model_output, retryable, refusal}` + `ToolErrorKind` single-table `default_retryable()`/`default_model_feedback()` | our `ToolOutput` + the retry predicate at `src/agent.rs:569` | **real gain** — an explicit operator/model feedback split and one table that cannot drift |
| default features off ⇒ no async runtime, transport, or MCP client | `llm` feature gating `dep:tokio`/`dep:async-openai` | equivalent in intent |
| `Error::non_success_headers()` exposing `Retry-After` to a `RetryPolicy` | our module doc says the typed surface drops headers, hence no outer retry loop | **real gain** — but it is rig's own HTTP client, so adopting it means adopting rig's transport |

**What a swap would cost**

1. **The path-blind invariant is ours alone.** rig has no `scrub_text`, no `leaks_path_identifiers`, no equivalent CI leak test. `serialize_tool_result()` being the *single* chokepoint is the load-bearing property of our design (module doc §"Path-blind invariant", three-part). Porting to rig means re-implementing that invariant as a `ToolResultAction::Rewrite` hook — a strictly weaker construction, since the invariant becomes a registration detail that a future contributor can forget.
2. **Persistence posture.** `AgentRun`'s serialized state embeds the full conversation **and every `CompletionCall::raw` provider body**, with the module doc warning that this "inherits whatever sensitivity the conversation content has" and that the format "carries no cross-version stability guarantee yet". Our `RunSnapshot` persists agenda/budget counters only, and `recover()` in `src/execute.rs` reconciles the WAL independently of it. A swap would put provider bodies into our session files, next to the append-only ledger we deliberately keep path-free.
3. **Churn.** `rig-run` → `rig-agent` is a *crate rename* landed in PR #2197 and recorded in `CHANGELOG.md`; `crates.io/api/v1/crates/rig-run` 404s. The 0.42.0 section of the changelog is dense with `[**breaking**]` items (removal of 53 `#[non_exhaustive]` attributes; `ToolSetBuilder`/`ToolSet::builder()` removed; `OneOrMany<T>`/`EmptyListError` removed; `CompletionResponse<T>` collapsed to a concrete `CompletionResponse`). Adopting rig means adopting that release cadence.
4. **We would re-open a green milestone.** M1–M5 landed 2026-09-10 with 91 tests default / 99 with `--features llm`, and the 9.13 submission grades on Rust quality (10 pts) and functional completeness (30 pts). A framework swap after submission buys no graded point and risks the regression surface of 8 `StopReason` variants, the kill -9 crash-injection tests, and the `--demo-data` Tauri gating that all sit on top of the current loop.

**Verdict: borrow patterns, do NOT swap.** The four-item borrow list is the `## Port backlog` below; each is a small, independently testable addition to code we already own. Note 07 left this open; note 29 closes it.

## Risks & open questions

1. **A framework swap would weaken the one invariant that is ours.** rig's redaction is `ToolResultAction::Rewrite` — opt-in, per-hook, and (by rig's own test) presentation-only. Ours is structural: `serialize_tool_result()` is the single chokepoint, `scrub_text` runs on every string leaf, and `leaks_path_identifiers` is the canonical leak set asserted by `leak_tests` + `tests/agent_tests.rs`. In a swap, "the LLM never sees paths" degrades from *invariant* to *convention*. This is the deciding argument against the swap, and it should be stated that way in the design doc.
2. **rig's persistence format is a secrecy hazard for a janitor tool.** `AgentRun`'s serialized state embeds the full conversation *and* every `CompletionCall::raw` provider body; the module doc says persisting it "inherits whatever sensitivity the conversation content has", and warns the format "carries no cross-version stability guarantee yet: resume with the same rig version that suspended the run". Our `RunSnapshot` stores only agenda/budget/counters. If we ever borrow the durable-suspension pattern, we must explicitly clear `raw` on the copy we write (rig's own doc says the driver must do this itself).
3. **Release churn is real and documented.** `rig-run` → `rig-agent` (PR #2197, in `CHANGELOG.md`) with `rig-run` 404ing on crates.io; the 0.42.0 section removes 53 `#[non_exhaustive]` attributes, removes `ToolSetBuilder`/`ToolSet::builder()`, removes `OneOrMany<T>`/`EmptyListError`, and collapses `CompletionResponse<T>` to a concrete type.
